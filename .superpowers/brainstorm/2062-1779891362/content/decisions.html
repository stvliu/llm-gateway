关键设计决策

每个决策提供 2 种方案，点击选择你的偏好

决策 1：OutboundTuner 如何获取 upstreamModelName

A

RoutingContext 携带字段（推荐）

在 RoutingContext record 中增加 modelName / upstreamModelName 两个 String 字段。RoutingResolver 组装时从 Model/ChannelModel 取出填入。

优点

  • OutboundTuner 零依赖，纯读取
  • RoutingContext 仍是值对象（无实体引用）
  • 数据流清晰：Resolver 组装 → Tuner 使用

缺点

  • RoutingContext 多两个字段
B

Tuner 自行查找

OutboundTuner 注入 ChannelModelGateway，通过 channelId + modelName 自行查找 ChannelModel 获取 upstreamModelName。

优点

  • RoutingContext 保持最小

缺点

  • Tuner 多一次 DB 查询
  • Tuner 承担查找职责（越权）
  • Resolver 查完的数据又要再查一次

决策 2：UPSTREAM_MODEL_NAME_RULES 存储位置

A

内置 Map 常量（推荐）

在 CatalogMaterializeService 中维护静态 Map，随版本更新。符合 spec 中"内置知识"的定位。

优点

  • 零运行时开销
  • 版本一致，无需额外配置
  • 按 spec 原设计实现

缺点

  • 修改需重新部署
B

@ConfigurationProperties 外部化

将映射规则抽取到 application.yml，通过 Spring 配置加载，支持运行时刷新。

优点

  • 无需改代码即可更新映射

缺点

  • 超出了 spec 设计的"内置知识"范畴
  • 外部配置增加了运维心智负担
  • 用户仍需在 ChannelModel 层面覆盖

决策 3：/v1/models 接口归属

A

新建 ModelDiscoveryController（推荐）

新建控制器，路径 /v1/models，专注模型发现用例，与后台 CRUD ModelController (/api/v1/models) 独立。

优点

  • 职责单一，与 OpenAI 兼容端点对应
  • 不影响后台管理 API
  • 鉴权逻辑独立（API Key vs 管理员）
B

并入 ModelController

在 ModelController 中增加路径 /v1/models 的兼容方法，复用 ModelService 查询。

优点

  • 复用已有 Service

缺点

  • /v1/models 和 /api/v1/models 混在一起
  • 鉴权逻辑混淆（API Key vs 管理员登录）
