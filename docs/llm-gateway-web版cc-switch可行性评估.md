# 把 LLM-Gateway 打造成 CC-Switch Web 网页版的可行性评估

## 一、产品定位对比

| 维度 | CC Switch | LLM Gateway |
|---|---|---|
| **目标用户** | 个人开发者 | 企业/团队 |
| **部署形态** | 桌面应用 (Tauri 2) | 服务器 (Spring Boot) |
| **核心价值** | 管理本地 CLI 配置，一键切换供应商 | 统一 API 入口，安全管控，多租户 |
| **配置管理** | 读写本地配置文件 (JSON/TOML) | 数据库集中存储，API 管控 |
| **代理模式** | 本地透明代理 (CLI→localhost→上游) | 远程网关 (Client→gateway→上游) |
| **MCP/Skills** | 深度支持 (统一管理 + 双向同步) | 不支持 |
| **企业特性** | 无 | 团队、RBAC、限流、审计、脱敏 |
| **设计规模** | 单用户 | 100 团队 / 10000 用户 / 10K QPS |

产品定位差异本质上是 **"个人工具" vs "企业基础设施"**，两者互补性很强。

## 二、功能重叠与差距矩阵

### 2.1 已重叠：可直接复用的模块

| 模块 | CC-Switch 实现 | LLM-Gateway 现状 | 对齐成本 |
|---|---|---|---|
| **供应商管理** | CRUD + 50+ 预设库 | Provider CRUD + Catalog 系统 | **低** — 增强 Catalog 预设即可 |
| **模型路由** | ProviderRouter → 上游转发 | RoutingResolver + ChannelSelector + ModelMatcher | **中** — 逻辑相似但架构不同，需适配多租户 |
| **请求代理** | Axum 代理服务器，转发 + 响应处理 | ChatDispatchService + OutboundTuner + 协议转换 | **高** — CC-Switch 的代理深度介入协议层 (thinking rectifier, SSE, body filter) |
| **用量统计** | 自定义 JS 脚本查询第三方余额 | TokenLimit + TokenUsedEvent 内置追踪 | **中** — 方案不同但可互补 |
| **熔断/故障转移** | CircuitBreaker + FailoverSwitch | Resilience 组件 (接口层，待实现) | **中** — CC-Switch 实现更完整，可参考移植 |
| **供应商预设库** | 50+ 内置 (官方/云厂商/聚合站) | Catalog 系统 | **低** — 补充预设数据即可 |

### 2.2 全部差距：LLM-Gateway 需新建的模块

| 模块 | CC-Switch 做法 | LLM-Gateway 差距 | 复杂度 |
|---|---|---|---|
| **MCP 服务器管理** | 统一管理 + 多工具双向同步 | 完全缺失 | **高** — 需从零设计 MCP 配置模型与同步引擎 |
| **Skills 管理** | 从 GitHub 发现/安装/同步 | 完全缺失 | **高** — 涉及 Git 操作、文件系统、多工具格式 |
| **Prompt 管理** | 模板增删改 + 多工具同步 | 完全缺失 | 中 |
| **会话浏览** | 扫描 CLI 工具本地会话文件 | 完全缺失 | **高** — 需理解各工具会话文件格式 |
| **节点测速** | 端到端延迟探测 | 完全缺失 | 低 — 可独立实现 |
| **WebDAV 云同步** | 配置跨设备同步 | 无需求 (Server 本身就是中心化) | 低 — 企业场景不需要 |
| **配置快照/备份** | 本地备份 + 恢复 | 无需求 (数据库自带) | 低 |

### 2.3 部分差距：需改造的模块

| 模块 | 差异 | 改造方向 |
|---|---|---|
| **供应商切换** | CC-Switch 写本地文件；LLM-Gateway 数据库切换 | LLM-Gateway 需新增"当前激活供应商"概念，并支持写远端 CLI 配置 |
| **代理服务器** | CC-Switch Axum 深度处理流；LLM-Gateway Spring MVC 标准路由 | LLM-Gateway 需要增强协议感知能力 (thinking budget, SSE 转发控制) |
| **UI** | CC-Switch React SPA，页面按 App 切换 | gateway-console 需参考其交互模式重写，增加 App 选择器 |

## 三、架构层面可行性

### 3.1 核心架构冲突

```
CC-Switch 架构 (个人本地方案)
┌─ 桌面应用 ───────────────┐
│ CLI 工具 ←→ 本地代理      │
│ (localhost:PORT)          │
│                           │
│ 配置写入 ~/.claude/        │
│ 配置写入 ~/.codex/         │
│ 会话扫描 ~/.claude/projects/  │
└───────────────────────────┘

LLM-Gateway 架构 (企业服务方案)
┌─ Server ───────────────────────┐
│ Client → API Gateway (443/80)  │
│                                 │
│ 数据库集中存储所有配置            │
│ 多租户隔离                       │
└─────────────────────────────────┘
```

核心矛盾：CC-Switch 的一半功能依赖**直接操作本地文件系统**（写配置、扫描会话、同步 MCP），这在 Server 架构里根本不存在。

### 3.2 方案选择：三种路径

#### 路径 A：纯 Web 化

把 CC-Switch 的个人本地功能全部转化为服务端功能：

| CC-Switch 本地操作 | 转化方案 | 可行性 |
|---|---|---|
| 写 `~/.claude/settings.json` | 提供 REST API + CLI 辅助工具 (`cc-switch-agent` 跑在开发者机器上) | **可行**，但需额外维护一个轻量客户端 |
| 扫描本地会话 | Server 无法扫描用户本机会话，改为追踪 LLM-Gateway 转发的请求日志 | **可行**，但丢失了 CLI 本地会话的上下文 |
| 本地代理 (localhost) | 改为远程 API 端点 (CLI 直接配置 upstream 为 LLM-Gateway URL) | **可行**，但失去了本地代理的低延迟 |
| 系统托盘切换 | Web UI 即可替代 | **完全可行** |

核心功能可 Web 化，但"本地配置写入"和"会话扫描"需要额外部署一个配套 Agent。

#### 路径 B：云 + 本地 Agent 混合

```
┌───────────── Web Admin (LLM-Gateway) ─────────────┐
│ 供应商库 / MCP 市场 / Skills 市场 / 用量大盘        │
│ 团队管理 / RBAC / 审计日志                          │
└────────────────────┬───────────────────────────────┘
                     │ REST API
┌───────────── Agent (在开发者机器上) ────────────────┐
│ 配置写入 ~/.claude/ 等本地文件                        │
│ MCP 配置双向同步                                      │
│ 本地会话扫描上传                                      │
│ 本地代理 (可选)                                       │
└─────────────────────────────────────────────────────┘
```

**适用场景**: 企业团队场景，兼顾集中管理和本地开发体验。Agent 可以是一个轻量级 Rust 或 Go 守护进程。

#### 路径 C：渐进式增强

不改动 LLM-Gateway 架构，**先做纯 Server 能力增强**：

1. 增强 Provider 预设库（复刻 CC-Switch 的 50+ 预设）
2. 增加 MCP Server 管理 API（存入数据库）
3. 增加 Skills 管理 API（存入数据库）
4. 增加 Prompt 模板管理
5. 前端 UI 参考 CC-Switch 重写

本地操作（写配置、会话）暂时不做，只做 Server 能做的部分。

## 四、技术可行性评估

### 4.1 正面因素（可行）

1. **供应商管理增强** — LLM-Gateway 已有 Provider/Catalog/Channel 等实体，扩展预设库和终端用户编辑界面很简单
2. **MCP/Skills 的数据层** — 新增几个数据库表就可以存储，Spring Data JPA 扩展成本低
3. **前端 UI 参考** — CC-Switch 的 React SPA 交互模式可以直接借鉴到 gateway-console
4. **请求路由已有基础** — 现有的 RoutingResolver + ChannelSelector 提供了很好的抽象，增强熔断/故障转移不难
5. **用量追踪系统** — 已有 TokenUsedEvent，扩展更多维度的统计仪表盘即可

### 4.2 困难因素（阻力大）

1. **协议层代理能力差距大**
   - CC-Switch 的 proxy 引擎深度介入协议流：思考预算修正 (thinking rectifier)、SSE 流过滤、响应体改写、Gemini shadow store
   - LLM-Gateway 的 routing 在请求层（选择往哪个上游发），响应基本透传
   - 填补这个差距需要重写响应处理管线，属于高复杂度工作

2. **配置写入模式完全不同**
   - CC-Switch ≈ 一键将供应商配置写入本地 CLI 文件
   - LLM-Gateway ≈ 用户通过 API Key 调用网关，网关自动路由
   - 这是两种完全不同的使用模式，不是"加个功能"就能对齐的

3. **会话管理无法复刻**
   - CC-Switch 读取 `~/.claude/projects/*/` 下的本地会话文件
   - Server 架构没有"本地会话"的概念
   - 最多能做到的是：LLM-Gateway 记录自己的转发日志作为"会话"替代品

4. **技术栈不同带来的移植成本**
   - Rust 的 Axum 代理引擎是基于 tokio 的异步流处理，极致灵活
   - Java + Spring Boot 是线程池 + Servlet 模型，处理 SSE 流的方式完全不同
   - 直接移植 proxy 模块的语义几乎不可能，需要按 Java 生态重新设计

## 五. 投入产出评估

### 5.1 建议优先级（按投入产出比排序）

| 优先级 | 功能 | 投入 | 产出 | 理由 |
|---|---|---|---|---|
| P0 | 增强供应商预设库 + UI | 2-3 周 | 高 | 最直观的价值，对两类用户都有用 |
| P0 | 新增 MCP 管理 API + 前端面板 | 4-6 周 | 高 | 差异化竞争力，CC-Switch 用户找不到替代品 |
| P1 | 新增 Skills 管理 API + 前端面板 | 3-4 周 | 高 | MCP 同系列，完成后形成掣肘 |
| P1 | Prompt 模板管理 | 2 周 | 中 | 简单易做，提升完成度 |
| P1 | 增强代理管线 (熔断/故障转移/thinking rectifier) | 6-8 周 | 高 | 提升网关质量，减少与竞品差距 |
| P2 | 响应流深度处理 (SSE 过滤、body filter) | 4-6 周 | 中 | 技术债高，优先级看实际需求 |
| P3 | 本地 Agent 配套工具 | 8-12 周 | 低→高 | 取决于是否决定做混合架构。不做 Agent 则不需要 |
| P3 | 会话管理（基于转发日志） | 3-4 周 | 低 | 与 CC-Switch 的本地会话体验差异大 |

### 5.2 建议策略

**不推荐**完整复刻 CC-Switch（路径 A）。理由是：

- 两者的产品灵魂不同 — 一个是**本地开发工具**，一个是**企业 API 网关**
- 强行融合会在两端都做不好

**推荐路径 C（渐进式增强）+ 有条件上路径 B**：

1. **第一季度**: P0 全部完成（供应商预设 + MCP 管理）— 快速建立"Web 版 CC-Switch"的认知
2. **第二季度**: P1 全部完成（Skills + Prompt + 代理增强）— 形成完整的统一管理体验
3. **第三季度**: 评估是否需要 Agent 方案（路径 B）— 取决于客户是否要求"写本地配置"和"会话管理"
4. 保留 LLM-Gateway 的核心企业特性（多租户、安全、审计），作为差异化优势

这意味着最终的 LLM-Gateway 不是"CC-Switch 的 Web 版"，而是 **"带 CC-Switch 管理能力的 AI 网关平台"**——它在企业场景下的价值远超个人工具。

## 六、总结

| 维度 | 评估 |
|---|---|
| **产品层面** | 高度互补，但定位不同。不应当复制，而应当借鉴 CC-Switch 的 UX 理念增强 LLM-Gateway 的管理后台 |
| **技术层面** | 60% 的功能可复用/参考，30% 需从零开发，10% 因架构冲突无法复刻 |
| **最大挑战** | 本地配置写入与会话扫描在 Server 架构中需要 Agent 模式才能实现 |
| **最小可行路径** | 不做代理层深度改造，先做 MCP/Skills/Prompt 管理 + 供应商预设增强 + UI 重写 |
| **最大差异化** | CC-Switch 没有企业特性（团队、RBAC、审计），LLM-Gateway 天然具备 |
| **建议** | 渐进式增强，不做完整复刻，保留企业定位 |
