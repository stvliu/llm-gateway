# LLM-Gateway 信息架构设计

> 本文档定义 LLM-Gateway 的核心概念模型、实体关系、业务术语及访问控制策略。

## 1. 核心概念

### 1.1 实体层次

```
Provider（供应商）
    └── Product（产品）
            ├── Product API Key（供应商侧密钥）
            ├── Models（模型列表）
            └── Endpoints（多协议 Base URL）

User（用户）
    └── User Team（用户-团队关联）
            └── User API Key（用户侧密钥）
                    └── 绑定 Product（产品访问权限）
```

### 1.2 概念定义

| 概念 | 定义 | 示例 |
|------|------|------|
| **Provider** | 大模型供应商，提供 AI 能力的厂商 | 火山方舟、百度、腾讯、DeepSeek |
| **Product** | 供应商提供的计费产品，包含一组模型和访问端点 | Coding Plan、Token Plan、按量计费产品 |
| **Product API Key** | 供应商侧认证密钥，用于调用供应商 API | 火山方舟 API Key、百度 API Key |
| **User API Key** | 用户侧访问密钥，用于访问 llm-gateway | `sk-xxx` 格式的用户密钥 |
| **Model** | 具体的 AI 模型标识 | `doubao-seed-code`、`deepseek-4.0-pro` |
| **Endpoint** | 按 API 协议区分的 Base URL | 原生协议、OpenAI 兼容、Anthropic 兼容 |

## 2. 产品类型

### 2.1 类型定义

| 产品类型 | 标识 | 特点 | 访问控制示例 |
|---------|------|------|-------------|
| **按量计费** | `pay_as_you_go` | 按实际使用量付费，无固定额度 | 产品人员可访问 |
| **Coding Plan** | `subscription_coding` | 订阅制，面向开发场景，有固定额度 | 开发者团队可访问 |
| **Token Plan** | `subscription_token` | 订阅制，按 Token 包计费，有固定额度 | 特定团队（如小龙虾）可访问 |

### 2.2 产品与协议关系

| 产品类型 | 支持协议 | 说明 |
|---------|---------|------|
| 按量计费 | `openai` | 兼容 OpenAI API 协议 |
| Coding Plan | `native`, `openai`, `anthropic` | 支持原生协议及双兼容协议 |
| Token Plan | `native`, `openai`, `anthropic` | 支持原生协议及双兼容协议 |

## 3. 实体关系

### 3.1 概念关系图

```
┌─────────────┐                    ┌─────────────────┐                    ┌─────────────────┐
│   Provider  │                    │      Team       │                    │      User       │
│   供应商    │                    │      团队       │                    │      用户       │
└──────┬──────┘                    └────────┬────────┘                    └────────┬────────┘
       │                                    │                                      │
       │ 1:N                                │ 1:N                                  │ N:N
       │                                    │                                      │
       ▼                                    ▼                                      ▼
┌─────────────┐                    ┌─────────────────┐                    ┌─────────────────┐
│   Product   │                    │  User API Key   │◄───────────────────│   User Team     │
│    产品     │                    │  用户侧密钥     │                    │  用户-团队关联  │
└──────┬──────┘                    └────────┬────────┘                    └─────────────────┘
       │                                    │
       │ 1:N                                │ N:1
       │                                    │
       ▼                                    ▼
┌─────────────┐                    ┌─────────────────┐
│Product API  │                    │   Usage Record  │
│    Key      │                    │   用量记录      │
│ 供应商密钥  │                    └─────────────────┘
└─────────────┘
```

### 3.2 关系说明

| 关系 | 类型 | 说明 |
|------|------|------|
| Provider → Product | 1:N | 一个供应商可提供多个产品 |
| Product → Product API Key | 1:N | 一个产品可配置多个供应商密钥（轮换、负载均衡） |
| Product → Model | 1:N | 一个产品包含多个模型 |
| User → Team | N:N | 一个用户可归属多个团队，一个团队可有多个用户 |
| Team → User API Key | 1:N | 一个团队可创建多个用户密钥 |
| User API Key → Product | N:1 | 一个用户密钥绑定一个产品 |
| User API Key → Usage Record | 1:N | 一个用户密钥产生多条用量记录 |

## 4. 访问控制模型

### 4.1 访问控制策略

```
用户 → 团队（角色）→ User API Key → Product（产品类型）
```

**核心原则**：
1. 用户归属于一个或多个团队
2. 团队角色决定可访问的产品类型
3. User API Key 绑定具体产品，实现细粒度权限控制
4. 网关只验证 User API Key，权限通过路由规则配置

### 4.2 场景示例

| 场景 | 用户 | 团队 | User API Key | Product | 访问权限 |
|------|------|------|--------------|---------|---------|
| 开发者访问 Coding Plan | 张三 | 开发团队 | sk-dev-001 | 火山方舟 Coding Plan | ✅ |
| 小龙虾访问 Token Plan | 李四 | 小龙虾团队 | sk-xlx-001 | 火山方舟 Token Plan | ✅ |
| 产品人员访问按量产品 | 王五 | 产品团队 | sk-prod-001 | 火山方舟按量产品 | ✅ |
| 开发者访问 Token Plan | 张三 | 开发团队 | sk-dev-001 | 火山方舟 Token Plan | ❌ |

### 4.3 多团队用户处理

**场景**：用户张三同时属于"开发团队"和"小龙虾团队"

**解决方案**：
- 张三拥有两个 User API Key
  - `sk-dev-001`：绑定火山方舟 Coding Plan
  - `sk-xlx-001`：绑定火山方舟 Token Plan
- 根据 API Key 前缀或命名区分用途

## 5. 密钥管理

### 5.1 双层密钥架构

```
┌─────────────────────────────────────────────────────────────┐
│                        用户侧                                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              User API Key (sk-xxx)                  │   │
│  │  - 用户访问网关的凭证                                │   │
│  │  - 绑定特定产品                                      │   │
│  │  - 可设置模型子集、额度限制                          │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                        网关层                                │
│  - 验证 User API Key                                        │
│  - 路由到对应 Product                                        │
│  - 选择 Product API Key                                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                        供应商侧                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │           Product API Key (供应商密钥)               │   │
│  │  - 调用供应商 API 的认证密钥                         │   │
│  │  - 支持多个 Key（轮换、负载均衡、故障转移）           │   │
│  │  - 加密存储                                          │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 Product API Key 用途

| 用途 | 配置方式 | 说明 |
|------|---------|------|
| **密钥轮换** | 添加新 Key，禁用旧 Key | 平滑切换，无停机 |
| **负载均衡** | 设置 `weight` | 多个 Key 按权重分配请求 |
| **故障转移** | 设置 `priority` | 主 Key 失败时自动切换备用 Key |

### 5.3 密钥安全策略

| 安全措施 | 实现方式 |
|---------|---------|
| 加密存储 | AES-256 加密 Product API Key |
| 哈希存储 | SHA-256 哈希 User API Key |
| 访问日志 | 记录 `last_used_at` |
| 权限隔离 | User API Key 只能访问绑定产品 |

## 6. 请求处理流程

### 6.1 完整流程

```
┌──────────────┐
│  用户请求    │
│  Header:     │
│  Authorization: Bearer sk-xxx
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  1. 认证     │  验证 User API Key
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  2. 鉴权     │  检查 Key 绑定的 Product、模型权限
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  3. 限流     │  检查 Key/Team 级别额度
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  4. 选密钥   │  根据 weight/priority 选择 Product API Key
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  5. 选端点   │  根据请求协议选择对应的 Base URL
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  6. 转发     │  调用供应商 API
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  7. 记录     │  写入用量记录
└──────────────┘
```

### 6.2 协议路由逻辑

| 请求协议 | 端点选择策略 |
|---------|-------------|
| 用户指定协议 | 优先使用 `endpoints[protocol]` |
| 未指定协议 | 降级到 `openai` 兼容协议 |
| 协议不支持 | 返回错误，提示可用协议 |

## 7. 扩展性设计

### 7.1 新增供应商

1. 在系统中注册新供应商
2. 创建对应产品
3. 配置 Product API Key
4. 无需修改代码结构

### 7.2 新增产品类型

1. 定义新产品类型标识
2. 配置访问控制规则
3. 无需修改实体关系

### 7.3 新增协议

1. 在产品端点配置中添加新协议
2. 实现协议适配器
3. 无需修改数据模型
