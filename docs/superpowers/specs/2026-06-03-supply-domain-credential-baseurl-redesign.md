# 供给域模型重构设计：Provider 级 BaseUrl + Credential 共享机制

## 背景

当前供给域模型中，BaseUrl 和 ApiKey 都绑定在 Channel 级别，无法跨 Channel 共享。这导致两个核心场景无法满足：

1. **火山引擎**：Coding Plan 需要共用默认计划的 ApiKey，Agent Plan 需要独立 ApiKey
2. **OpenAI/Anthropic/Gemini**：单一 BaseUrl 所有产品共享

## 核心决策

| 决策项 | 结论 |
|--------|------|
| ApiKey 归属层级 | Provider 级别，Channel 引用 |
| ApiKey 共享机制 | 区分 SHARED（共用）/ DEDICATED（专用），隐式继承 |
| BaseUrl 归属层级 | Provider 级默认值，Channel 可覆盖 |
| 套餐建模 | 不考虑，Channel = 产品，套餐视为产品规格 |

## 实体模型

### Provider（厂商）— 新增 baseUrl

```
Provider
  ├── id, code, name, logoUrl, websiteUrl, description
  ├── baseUrl              ← 新增：默认 BaseUrl（单协议厂商）
  ├── defaultEndpoints     ← 新增：多协议默认端点 JSON（多协议厂商）
  └── state
```

- 场景一（OpenAI）：`baseUrl = "https://api.openai.com"`，`defaultEndpoints = null`
- 场景二（Anthropic）：`baseUrl = "https://api.anthropic.com"`，`defaultEndpoints = null`
- 场景三（火山引擎）：`baseUrl = null`，`defaultEndpoints = [{"protocol":"OPENAI","url":"https://ark.cn-beijing.volces.com/api/v3"},{"protocol":"ANTHROPIC","url":"https://ark.cn-beijing.volces.com/api/v3/anthropic"}]`
- `baseUrl` 和 `defaultEndpoints` 互补：单协议厂商用 baseUrl，多协议厂商用 defaultEndpoints

### ProviderCredential（厂商凭证）— 替代 ChannelCredential

```
ProviderCredential
  ├── id
  ├── providerId       ← 归属厂商（替代原 channelId）
  ├── name
  ├── apiKeyPlain      ← Key 明文（查询时解密填充）
  ├── apiKeyPrefix     ← Key 前缀
  ├── keyAlias         ← 密钥别名
  ├── scope            ← 新增：SHARED（共用）/ DEDICATED（专用）
  ├── channelId        ← 专用 Key 指向 Channel，共用 Key 时 null
  ├── weight           ← 负载均衡权重
  ├── priority         ← 故障转移优先级
  ├── state            ← 凭证状态
  └── lastUsedAt       ← 最后使用时间
```

**scope 语义**：

| scope | 含义 | channelId | 使用场景 |
|-------|------|-----------|----------|
| SHARED | 厂商级共用 Key，所有 Channel 默认可用 | null | OpenAI/Anthropic 的 Key；火山引擎默认计划的 Key |
| DEDICATED | 产品级专用 Key，仅指定 Channel 可用 | 非 null | 火山引擎 Agent Plan 的独立 Key |

### Channel（产品）— 移除 credentialIds

```
Channel
  ├── id, providerId, name
  ├── billingMode, quotaLimit
  ├── priority, weight, timeout, maxRetries
  └── state
```

- Channel 不再持有 credentialIds
- 凭证通过 ProviderCredential 的 scope + channelId 隐式关联
- Channel 无专用 Key → 自动继承 Provider 的 SHARED Key

### ChannelEndpoint（产品端点）— 保持不变

```
ChannelEndpoint
  ├── id, channelId
  ├── protocol         ← OPENAI / ANTHROPIC / GEMINI / NATIVE
  ├── endpointUrl
  └── state
```

- Channel 有 Endpoint → 用自己的（覆盖 Provider.baseUrl）
- Channel 无 Endpoint → 路由时从 Provider.baseUrl + 入站协议自动生成

## 路由解析逻辑

### EndpointResolver 修改

```
1. 查 Channel 的 ChannelEndpoint（按入站协议匹配）
2. 有 → 用 Channel 自己的 Endpoint（覆盖）
3. 无 → 查 Provider.defaultEndpoints（按入站协议匹配）
4. 有 → 用 Provider 的默认端点
5. 无 → 从 Provider.baseUrl 按入站协议推导
6. 无 → 抛出 ResourceNotFoundException
```

### CredentialResolver 修改

```
1. 查 Channel 的 DEDICATED Key（scope=DEDICATED, channelId=当前Channel, state=ACTIVE）
2. 有 → 按 priority/weight 选择（保留现有默认优先+活跃回退逻辑）
3. 无 → 查 Provider 的 SHARED Key（scope=SHARED, providerId=当前Provider, state=ACTIVE）
4. 有 → 按 priority/weight 选择（同上逻辑）
5. 无 → 抛出 ResourceNotFoundException
```

## 场景验证

### 场景一：OpenAI

```
Provider: OpenAI
  ├── baseUrl = "https://api.openai.com"
  └── ProviderCredential: Key-1 (SHARED)

Channel: API 按量计费
  └── 无 Endpoint → 继承 Provider.baseUrl
  └── 无专用 Key → 继承 Provider SHARED Key-1
```

### 场景二：Anthropic

```
Provider: Anthropic
  ├── baseUrl = "https://api.anthropic.com"
  ├── ProviderCredential: Key-1 (SHARED)
  └── ProviderCredential: Key-2 (SHARED)

Channel: API 按量计费
  └── 无 Endpoint → 继承 Provider.baseUrl
  └── 无专用 Key → 继承 Provider SHARED Key

Channel: Pro 包月
  └── 无 Endpoint → 继承 Provider.baseUrl
  └── 无专用 Key → 继承 Provider SHARED Key

Channel: Max 包月
  └── 无 Endpoint → 继承 Provider.baseUrl
  └── 无专用 Key → 继承 Provider SHARED Key
```

### 场景三：火山引擎

```
Provider: 火山引擎
  ├── baseUrl = null
  ├── defaultEndpoints = [
  │     {"protocol":"OPENAI","url":"https://ark.cn-beijing.volces.com/api/v3"},
  │     {"protocol":"ANTHROPIC","url":"https://ark.cn-beijing.volces.com/api/v3/anthropic"}
  │   ]
  ├── ProviderCredential: Key-1 (SHARED)
  └── ProviderCredential: Key-2 (SHARED)

Channel: 默认计划（按Token计费）
  └── 无 Endpoint → 继承 Provider.defaultEndpoints（OPENAI + ANTHROPIC）
  └── 无专用 Key → 继承 Provider SHARED Key-1/Key-2

Channel: Agent Plan（包月，按燃料值计量）
  └── 无 Endpoint → 继承 Provider.defaultEndpoints（OPENAI + ANTHROPIC）
  └── ProviderCredential: Key-3 (DEDICATED, channelId=AgentPlan)

Channel: Coding Plan（包月，按调用次数计量）
  └── 无 Endpoint → 继承 Provider.defaultEndpoints（OPENAI + ANTHROPIC）
  └── 无专用 Key → 继承 Provider SHARED Key-1/Key-2（与默认计划共享）
```

## 数据库迁移

### 新增表

```sql
-- ProviderCredential（替代 channel_credentials）
CREATE TABLE provider_credentials (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    provider_id BIGINT NOT NULL,
    name VARCHAR(128) NOT NULL,
    encrypted_api_key VARCHAR(512) NOT NULL,
    api_key_prefix VARCHAR(32),
    key_alias VARCHAR(128),
    scope VARCHAR(16) NOT NULL DEFAULT 'SHARED',  -- SHARED / DEDICATED
    channel_id BIGINT,                             -- 专用 Key 时非 null
    weight INTEGER DEFAULT 1,
    priority INTEGER DEFAULT 0,
    state VARCHAR(16) DEFAULT 'ACTIVE',
    last_used_at TIMESTAMP,
    created_by BIGINT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_by BIGINT,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_provider_credential_provider FOREIGN KEY (provider_id) REFERENCES providers(id),
    CONSTRAINT fk_provider_credential_channel FOREIGN KEY (channel_id) REFERENCES channels(id) ON DELETE CASCADE,
    CONSTRAINT ck_credential_scope_channel CHECK (
        (scope = 'SHARED' AND channel_id IS NULL) OR
        (scope = 'DEDICATED' AND channel_id IS NOT NULL)
    )
);

CREATE INDEX idx_provider_credentials_provider ON provider_credentials(provider_id);
CREATE INDEX idx_provider_credentials_channel ON provider_credentials(channel_id);
CREATE INDEX idx_provider_credentials_scope ON provider_credentials(scope);
```

### 修改表

```sql
-- Provider 新增 baseUrl + defaultEndpoints
ALTER TABLE providers ADD COLUMN base_url VARCHAR(512);
ALTER TABLE providers ADD COLUMN default_endpoints TEXT;  -- JSON 数组
```

### 数据迁移

```sql
-- 1. 将 channel_credentials 数据迁移到 provider_credentials
--    通过 channel_id → channels.provider_id 获取 provider_id
--    原有 Key 绑定特定 Channel，迁移后设为 DEDICATED
--    管理员可后续手动将需要共享的 Key 改为 SHARED
INSERT INTO provider_credentials (provider_id, name, encrypted_api_key, api_key_plain,
    api_key_prefix, key_alias, scope, channel_id, weight, priority, state, last_used_at,
    created_by, created_at, updated_by, updated_at)
SELECT c.provider_id, ck.name, ck.encrypted_api_key, ck.api_key_plain,
    ck.api_key_prefix, ck.key_alias, 'DEDICATED', ck.channel_id, ck.weight, ck.priority, ck.state, ck.last_used_at,
    ck.created_by, ck.created_at, ck.updated_by, ck.updated_at
FROM channel_credentials ck
JOIN channels c ON ck.channel_id = c.id;

-- 2. 删除旧表
DROP TABLE channel_credentials;
```

## 页面交互设计

### 交互原则

- **BaseUrl 和 ApiKey 是厂商级资源**，管理入口在 Provider 详情页
- **Channel 是产品**，创建时可选择"继承厂商默认值"或"自定义覆盖"
- **隐式继承不需要配置**——Channel 无自定义 Endpoint/专用 Key 时自动继承

## 审阅修复记录

### P0-1: Provider.baseUrl 无法推导多协议端点

**问题**：单一 `baseUrl` 字段无法推导不同协议的端点路径（如火山引擎 OpenAI 和 Anthropic 端点路径不同）。

**修复**：Provider 新增 `defaultEndpoints` JSON 字段，与 `baseUrl` 互补：

```
Provider
  ├── baseUrl            ← 单协议厂商的默认地址（OpenAI/Anthropic/Gemini）
  ├── defaultEndpoints   ← JSON: [{"protocol":"OPENAI","url":"..."},{"protocol":"ANTHROPIC","url":"..."}]
  └── ...
```

- `baseUrl` 非空时：单协议厂商，所有 Channel 共享此地址，EndpointResolver 按入站协议拼接
- `defaultEndpoints` 非空时：多协议厂商，按协议匹配对应端点
- 两者互斥：`baseUrl` 优先，`defaultEndpoints` 作为多协议扩展
- Channel 的 ChannelEndpoint 仍可覆盖任意协议的端点

EndpointResolver 完整逻辑：
```
1. 查 Channel 的 ChannelEndpoint（按入站协议匹配）
2. 有 → 用 Channel 自己的 Endpoint（覆盖）
3. 无 → 查 Provider.defaultEndpoints（按入站协议匹配）
4. 有 → 用 Provider 的默认端点
5. 无 → 从 Provider.baseUrl 按入站协议推导
6. 无 → 抛出 ResourceNotFoundException
```

### P0-2: CredentialResolver 隐式继承时多 Key 选择逻辑

**问题**：SHARED Key 可能有多个，未说明如何选择。

**修复**：CredentialResolver 完整逻辑：
```
1. 查 Channel 的 DEDICATED Key（scope=DEDICATED, channelId=当前Channel, state=ACTIVE）
2. 有 → 按 priority/weight 选择（保留现有默认优先+活跃回退逻辑）
3. 无 → 查 Provider 的 SHARED Key（scope=SHARED, providerId=当前Provider, state=ACTIVE）
4. 有 → 按 priority/weight 选择（同上逻辑）
5. 无 → 抛出 ResourceNotFoundException
```

### P1-3: 删除 Channel 时 DEDICATED Key 的级联行为

**修复**：级联删除。专用 Key 的存在意义是绑定特定 Channel，Channel 不存在了 Key 也无意义。
在 provider_credentials 表的外键约束中使用 `ON DELETE CASCADE`。

### P1-4: 删除 Provider 时 SHARED Key 的约束

**修复**：删除 Provider 前校验：是否存在无 DEDICATED Key 的活跃 Channel？
若有，拒绝删除并提示"请先为以下产品配置专用 Key 或删除产品"。

### P2-5: apiKeyPlain 不应持久化

**修复**：provider_credentials 建表 DDL 移除 `api_key_plain` 列。
明文只在创建时传入、查询时从 `encrypted_api_key` 解密填充。

### P2-6: scope + channelId 一致性约束

**修复**：添加 CHECK 约束：
```sql
ALTER TABLE provider_credentials ADD CONSTRAINT ck_credential_scope_channel
CHECK (
  (scope = 'SHARED' AND channel_id IS NULL) OR
  (scope = 'DEDICATED' AND channel_id IS NOT NULL)
);
```

### P3-7: 有专用 Key 时共用 Key 的提示

**修复**：提示改为"此产品有专用 Key，优先使用专用 Key。共用 Key 作为故障转移备用。"
