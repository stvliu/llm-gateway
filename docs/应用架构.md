## 2. 层次定义

### 2.1 分层定义

| 层 | 解决什么问题 | 核心职责 |
|---|-------------|---------|
| **Adapter（适配层）** | 隔离**外部**变化 | 接入多端（Web/CLI/SDK），协议适配，数据格式转换 |
| **Application（应用层）** | 用例编排与跨域协调 | 编排用例流程，组合领域服务，管理事务边界 |
| **Domain（领域层）** | 业务规则与领域模型 | 封装业务规则，定义领域实体、领域服务、Gateway 接口 |
| **Infrastructure（基础设施层）** | 隔离**内部**变化 | 持久化实现，第三方 API 调用，技术细节 |
| **Common（公共组件）** | 跨层共享 | 基础异常、常量、通用工具 |

> **模块化说明**：P1 模块化重构后，`domain` / `infrastructure` 层的业务实现已按功能域下沉到各模块（gateway-provider / gateway-iam / gateway-usage / gateway-security / gateway-audit / gateway-alert / gateway-resilience / gateway-proxy / gateway-stats / gateway-protocol），每模块内部仍遵循「接口定义在 domain、实现走 Gateway 接口」的依赖倒置原则；HTTP 承载归 gateway-web（api/interceptor/advice），用例编排下沉到各功能域核心模块的 service 包，gateway-boot 仅保留启动装配（config/init/event + GatewayApplication）。JPA 持久化实现位于各域 `*-data` 绑定模块（如 providerdata / iamdata），自动装配位于各域 `*-starter` 模块（根包 `autoconfigure.<域>`）。

**层次关系**（HTTP 承载与启动装配）：

```
web ──调用──► 功能域核心模块（Domain Service / 应用服务）
                    │
              定义接口│
                    ▼
                ┌─────────┐
                │ gateway │ ← 接口在功能域核心模块
                └─────────┘
                    ▲
              实现接口│
                    │
        *-data 绑定模块 ──（JPA 持久化实现）
```

**禁止事项**：

| 层 | 禁止事项 |
|---|---------|
| **web** | 直接调用基础设施（应通过域模块应用服务） |
| **应用服务（域模块 service 包）** | 包含业务逻辑 |
| **domain** | 直接访问外部资源 |
| **infrastructure（`*-data` 绑定模块）** | 包含业务逻辑 |

### 2.2 分包原则

**模块 = 根包**：

```
HTTP 承载层（gateway-web，com.codingas.gateway.web）：
  web.api / web.interceptor / web.advice

启动装配（gateway-boot，com.codingas.gateway.boot）：
  boot.config / boot.init / boot.event

功能域模块（去除 domain/application/infrastructure DDD 前缀）：
  com.codingas.gateway.<域>           # 核心模块根包（如 .provider / .iam / .protocol / .proxy）
  com.codingas.gateway.<域>data       # JPA 绑定模块根包（如 providerdata / iamdata）
  autoconfigure.<域>                  # 自动装配模块根包（如 autoconfigure.provider）
```

详细规范见 `doc/constitution.md` §3.1 包名规范与模块化设计文档 §4.2 包名映射表。

```
┌─────────────────────────────────────────────────────────────────┐
│                        允许的依赖                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   web ──调用──► 功能域核心模块（Domain Service / 应用服务）      │
│                                              │                   │
│                                        定义接口│                  │
│                                              ▼                   │
│                                        ┌─────────┐              │

│                                        └─────────┘              │

│                                        实现接口│                  │

```

## 3. 关键场景

### 3.0 核心请求处理总览

**七阶段调用链路**：

```
请求入口 (gateway-web · web/api)
  │
  ▼
安全拦截链 (gateway-web · web/interceptor)
  │  Auth → RateLimit → IpBlock → DataMasking → ModelAccess
  ▼
ChatDispatchService (gateway-proxy proxy.chat)     ← 统一编排入口
  │
  │  ┌─ 前置阶段 ────────────────────────────────────────┐
  │  │  1. 校验：InboundValidator.validate(request)      │
  │  │     位置：gateway-protocol 插件（protocol-openai/anthropic）│
  │  │     （协议校验器实现，配合 gateway-protocol 插件）│
  │  │  2. 路由：RoutingResolver.resolve(identity, model)│
  │  │     位置：gateway-proxy（proxy.routing）          │
  │  │     ModelMatcher → ChannelSelector(strategy)      │
  │  │       → CredentialResolver → EndpointResolver    │
  │  │  3. 记录审计起点：auditGateway.logRequest(...)    │
  │  │     位置：gateway-audit                            │
  │  └──────────────────────────────────────────────────┘
  │
  │  ┌─ 转换阶段（仅跨协议时执行）───────────────────────┐
  │  │  4. 请求转换：protocolConverter.convertRequest() │
  │  │     位置：gateway-proxy（proxy.conversion         │
  │  │     ProtocolConversionFacade）                    │
  │  └──────────────────────────────────────────────────┘
  │
  │  ┌─ 调谐阶段 ────────────────────────────────────────┐
  │  │  5. 调谐：outboundTuner.tune(request, ctx)        │
  │  │     位置：gateway-proxy（proxy.conversion）       │
  │  │     职责：模型名替换、默认值填充、字段覆盖、      │
  │  │           敏感字段剥离                              │
  │  │     调谐必须按目标协议要求执行，而非入站协议       │
  │  └──────────────────────────────────────────────────┘
  │
  │  ┌─ 调用阶段 ────────────────────────────────────────┐
  │  │  6. 上游调用：upstreamClient.chat(request)        │
  │  │     位置：gateway-provider（provider.upstream）   │
  │  │     韧性包装：RetryPolicy + CircuitBreaker        │
  │  │     （gateway-resilience）                        │
  │  │     纯 HTTP 调用 + SSE 解析，不含业务逻辑         │
  │  └──────────────────────────────────────────────────┘
  │
  │  ┌─ 转换阶段（仅跨协议时执行）───────────────────────┐
  │  │  7. 响应转换：protocolConverter.convertResponse()│
  │  │     位置：gateway-proxy（proxy.conversion         │
  │  │     ProtocolConversionFacade）                    │
  │  └──────────────────────────────────────────────────┘
  │
  │  ┌─ 后置阶段 ────────────────────────────────────────┐
  │  │  8. Token 计量：publish TokenUsedEvent            │
  │  │     位置：gateway-proxy（proxy.chat               │
  │  │     ChatDispatchService）                         │
  │  │  9. 记录审计终点：auditGateway.logResponse(...)   │
  │  │     包含：duration、success/failure、Token 用量    │
  │  │     位置：gateway-audit                            │
  │  └──────────────────────────────────────────────────┘
  │
  ▼
响应返回
```

**链路铁律**：

| 规则 | 说明 |
|------|------|
| 转换先于调谐 | 跨协议时必须先转换为目标协议格式，再按目标协议要求调谐 |
| 调谐依赖路由 | OutboundTuner 必须在 RoutingResolver 之后执行 |
| 调用不含业务 | UpstreamClient 只做 HTTP 调用 + SSE 解析 |
| 韧性包装调用 | RetryPolicy 和 CircuitBreaker 包装在 UpstreamClient 外层 |
| 审计前后各记 | 调用前记录起点，调用后记录终点（含耗时） |
| 计量基于响应 | Token 计量从 ProtocolResponse 提取 |

**各阶段归属模块**：

| 阶段 | 归属模块 | 关键类 |
|------|--------|--------|
| 校验 | gateway-protocol（协议插件 protocol-openai/anthropic） | `OpenAIProtocolValidator`, `AnthropicProtocolValidator`（协议插件 `OpenAIProtocolAdapter` 等） |
| 路由 | gateway-proxy（proxy.routing） | `RoutingResolver`, `ModelMatcher`, `CredentialResolver`, `EndpointResolver` 等路由链组件 |
| 转换 | gateway-proxy（proxy.conversion） | `ProtocolConversionFacade`, `ProtocolStreamConverter`（协议转换门面，依赖 gateway-protocol 契约） |
| 调谐 | gateway-proxy（proxy.conversion） | `OutboundTuner`（配合 gateway-protocol 插件下的 OpenAITuner / AnthropicTuner） |
| 调用 | gateway-protocol（protocol.transport 接口 / 插件实现） | `UpstreamClient`, `UpstreamClientRegistry`（HTTP 实现位于 protocol-openai/anthropic 插件） |
| 韧性 | gateway-resilience | `CircuitBreaker`, `RetryExecutor`, `ChannelEndpointCircuitBreakerManager`, `FailoverEvent` 等 |
| 降级 | 规划中 | `DegradationService`（设计愿景，当前无对应实现） |
| 计量 | gateway-proxy（proxy.chat） | `ChatDispatchService` → 发布 `TokenUsedEvent` |
| 审计 | gateway-audit | `AuditGateway.logRequest()`, `AuditGateway.logResponse()` |

### 3.1 LLM 代理转发

**调用链**（对齐 §3.0 七阶段链路）：

```
请求 → OpenAIController / AnthropicController
    → ChatDispatchService.dispatch()
        → 1. InboundValidator.validate()              // 协议校验
        → 2. RoutingResolver.resolve()                // 路由解析
            → ModelMatcher → ChannelSelector → CredentialResolver → EndpointResolver
        → 3. auditGateway.logRequest()               // 审计起点
        → 4. ProtocolConverter.convertRequest()       // 跨协议请求转换（可选）
        → 5. OutboundTuner.tune(request, ctx)         // 出站调谐
        → 6. UpstreamClient.chat(request)              // 上游调用
            → RetryPolicy + CircuitBreaker 包装
        → 7. ProtocolConverter.convertResponse()      // 跨协议响应转换（可选）
        → 8. publish TokenUsedEvent                   // Token 计量
        → 9. auditGateway.logResponse()               // 审计终点
    → 响应
```

#### 3.1.1 SSE 流式处理架构

**场景说明**：对于 `stream: true` 的请求，网关需要支持 SSE（Server-Sent Events）流式响应，实现实时内容推送。

**SSE 流式处理流程**：

```
客户端请求（stream: true）
    ↓
[Adapter] OpenAIController / AnthropicController
    ↓
[Application] ChatDispatchService.dispatchStream()
    ↓
前置阶段（校验 → 路由 → 审计起点 → 转换 → 调谐）
    ↓
[Infrastructure] UpstreamClient.chatStream() ──建立上游连接──► Provider SSE
    │   韧性包装：RetryPolicy + CircuitBreaker
    ↓
    │   ┌─────────────────────────────────────────────────┐
    │   │              SSE 事件流                         │
    │   │  data: {"choices":[{"delta":{"content":"..."}}]} │
    │   │  data: {"choices":[{"delta":{"content":"..."}}]} │
    │   │  data: [DONE]                                   │
    │   └─────────────────────────────────────────────────┘
    ↓
[Domain] 跨协议 chunk 转换（ProtocolConverter，可选）
    ↓
[Adapter] 推送给客户端
    ↓
[Application] 后置阶段（Token 计量 → 审计终点）
```

**SSE 核心接口设计**：

```
┌─────────────────────────────────────────────────────────────────┐
│                      SSE 流式处理接口                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  [Adapter 层]                                                    │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  StreamController                                          │   │
│  │  - 接收 HTTP 请求                                          │   │
│  │  - 创建 SSE 连接                                           │   │
│  │  - 返回流式响应                                            │   │
│  └──────────────────────────────────────────────────────────┘   │
│                              │                                   │
│                              ▼                                   │
│  [Application 层]                                                │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  ChatDispatchService.dispatchStream(request, callback)    │   │
│  │  - 编排校验、路由、转换、调谐                                │   │
│  │  - 调用 UpstreamClient 建立上游连接                         │   │
│  │  - 通过 StreamCallback 推送数据                             │   │
│  └──────────────────────────────────────────────────────────┘   │
│                              │                                   │
│                              ▼                                   │
│  [Domain 层]                                                     │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  StreamCallback 接口（gateway-protocol/protocol）          │   │
│  │  - onChunk(chunk): 收到数据块时调用                        │   │
│  │  - onComplete(): 流式结束时调用                            │   │
│  │  - onError(error): 发生错误时调用                          │   │
│  └──────────────────────────────────────────────────────────┘   │
│                              │                                   │
│                              ▼                                   │
│  [Infrastructure 层]                                             │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  UpstreamClient.chatStream(request, callback)             │   │
│  │  - 建立与上游 Provider 的 SSE 连接                         │   │
│  │  - 解析 SSE 事件                                           │   │
│  │  - 通过回调传递给上层                                      │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**接口定义**：

### 3.3 限流与配额

**场景说明**：通过两级限流（本地限流 + 分布式限流）实现 Token 限额控制和请求限流。

**限流检查流程**：

```
请求 → ProxyService.proxy()
    → TokenLimitService.check()
        → 本地限流检查（JVM 内存）
            → 超限 → 返回 429 + Retry-After
        → 分布式限流检查（共享存储）
            → 超限 → 返回 429 + X-RateLimit-*
        → 记录 UsageRecord
    → 通过后继续路由
```

**Token 限额检查**：

```
TokenLimitService.checkLimit(userId, modelId)
    → TokenLimitGateway.findByUser(userId)
        → 检查是否超限（total_usage < limit）
    → 超限 → 抛出 QuotaExceededException
        → 返回 402 PAYMENT_REQUIRED
        → 错误码 QUOTA_001
```

**限流策略**：

| 维度 | 标准版 | 企业版 |
|------|--------|--------|
| **RPM** | 60/min | 600/min |
| **TPM** | 100,000/min | 1,000,000/min |
| **并发** | 10 | 100 |
| 本地限流 | 内存令牌桶 | 内存令牌桶 |
| 分布式限流 | 共享存储计数 | 集群共享存储 |

**重试策略**：

| 场景 | 策略 |
|------|------|
| **429 Rate Limit** | 指数退避：1s → 2s → 4s → 8s → 16s → 32s，最大 60s |
| **503 Service Unavailable** | 等待 5s 后重试，最多 3 次 |
| **504 Gateway Timeout** | 立即重试 1 次，失败后切换 Provider |

**层次归属**：

| 组件 | 归属模块 | 说明 |
|------|------|------|
| TokenLimitService | gateway-usage（usage.tokenlimit） | 限额服务编排 |
| RateLimitDomainService | gateway-usage（usage） | 限流规则处理 |
| TokenLimitGateway | gateway-usage（usage） | 接口 |
| TokenLimitGateway 实现 | gateway-usage（usage-data） | 分布式限流实现 |
| 本地限流器 | gateway-usage（usage-data） | JVM 本地限流（Redis 分布式限流） |

### 3.4 上游大模型异常处理

**场景说明**：调用外部 LLM Provider 时可能发生多种异常（限流、超时、服务不可用、网络错误等），网关需要提供统一的异常分类、重试、熔断、故障转移和降级机制。

#### 3.4.1 异常分类体系

**错误类型枚举 `ProviderErrorType`**（gateway-common：`com.codingas.gateway.common.enums`）：

| 类型 | 触发条件 | 是否可重试 |
|------|---------|-----------|
| `AUTHENTICATION_ERROR` | HTTP 401 API Key 无效 | 否 |
| `RATE_LIMIT_ERROR` | HTTP 429 限流（不含 quota 关键字） | 是（指数退避） |
| `QUOTA_EXCEEDED` | HTTP 429 + 错误体含 "quota" 关键字 | 否 |
| `TIMEOUT_ERROR` | HTTP 408/504 / SocketTimeoutException | 是（快速重试） |
| `INVALID_REQUEST` | HTTP 400 请求格式错误 | 否 |
| `UPSTREAM_ERROR` | HTTP 500/502/529 Provider 内部错误 | 是（固定等待） |
| `SERVICE_UNAVAILABLE` | HTTP 503 服务不可用 | 是（固定等待） |
| `CIRCUIT_OPEN` | 熔断器开启拒绝请求（网关自我保护） | 否（触发故障转移） |
| `NETWORK_ERROR` | IOException（连接/DNS/SSL 失败） | 是（默认指数退避） |
| `UNKNOWN_ERROR` | 其他未分类错误 | 按状态码判断 |

**异常映射流程**：

```
上游 HTTP 响应 / IOException
    │
    ▼
ErrorClassificationStrategy.classify(statusCode, responseBody)
    │  实现：OpenAIErrorClassifier / AnthropicErrorClassifier
    ▼
ProviderErrorType 枚举
    │
    ▼
ProviderException(errorType, message, traceId, model, provider, channelEndpointId, retryAfterSeconds)
```

#### 3.4.2 韧性组件架构

**装饰器模式：ResilientUpstreamClient 包装链**

```
原始 UpstreamClient（纯 HTTP 调用）
    │
    ▼  ResilientClientFactory.wrap()
┌────────────────────────────────────────────────┐
│  ResilientUpstreamClient                       │
│  ┌──────────────────────────────────────────┐  │
│  │ 1. 熔断检查：circuitBreaker.allowRequest │  │
│  │    → 熔断开启则抛出 CircuitOpenException │  │
│  │ 2. 舱壁隔离：Semaphore.tryAcquire()      │  │
│  │    → 并发超限则拒绝请求                  │  │
│  │ 3. 重试执行：RetryExecutor.execute()     │  │
│  │    → 按错误类型选择差异化退避策略        │  │
│  │ 4. Metrics 埋点：记录成功/失败/重试      │  │
│  └──────────────────────────────────────────┘  │
└────────────────────────────────────────────────┘
```

#### 3.4.3 熔断器状态机

每个 `ChannelEndpoint` 有独立的 `CircuitBreaker` 实例（`ChannelEndpointCircuitBreakerManager`）：

```
        ┌─────────────────────────────────────────────────────┐
        │                   状态转换图                          │
        │                                                      │
        │  成功次数 >= 阈值 ─────────┐                         │
        │       ▲                    ▼                         │
        │  ┌────────┐   失败率 >= 阈值   ┌──────┐              │
        │  │ CLOSED │ ──────────────►  │ OPEN  │              │
        │  └────────┘                   └──┬───┘              │
        │       ▲                          │ 超时 (openDurationMs)│
        │       │                          ▼                   │
        │       └─────────────── ┌──────────┐                 │
        │           成功探测     │ HALF_OPEN │                 │
        │                       └─────┬────┘                 │
        │                     失败探测 │ 或 超时(halfOpenTimeoutMs)│
        │                             └──► OPEN               │
        └─────────────────────────────────────────────────────┘
```

**配置参数**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| failureRateThreshold | 0.5 (50%) | 滑动窗口内失败率阈值 |
| slidingWindowSize | 10 | 滑动窗口大小（请求数） |
| openDurationMs | 30000 (30s) | OPEN 状态持续时间 |
| halfOpenMaxAttempts | 3 | 半开状态最大探测请求数 |
| halfOpenTimeoutMs | 10000 (10s) | 半开状态超时（无响应则重熔断） |

#### 3.4.4 差异化重试策略

`RetryExecutor` 根据 `ProviderErrorType` 选择退避策略：

| 错误类型 | 策略 | 参数 | 说明 |
|---------|------|------|------|
| `RATE_LIMIT_ERROR` | 指数退避 + 抖动 | 初始 2s, 倍率 2x, max 60s, jitter 25% | 尊重上游限流指令 |
| `TIMEOUT_ERROR` | 快速重试 | 500ms 固定, 最多 2 次 | 超时可能为瞬时 |
| `SERVICE_UNAVAILABLE` | 固定等待 | 5s 固定, 最多 3 次 | 给上游恢复时间 |
| `UPSTREAM_ERROR` | 固定等待 | 复用 503 策略 | 同上 |
| 其他可重试 | 默认指数退避 | 初始 1s, 倍率 2x, 最多 3 次 | 兜底策略 |

#### 3.4.5 故障转移（Failover）

**Key 级故障转移**（同一 Channel 下多个 API Key）：

```
callWithKeyFailover(RoutingContext ctx, ProtocolRequest req, String traceId)
    │
    ├── credentialResolver.resolveAll(channelId)  ← 获取所有 Key
    │
    ├── for each Key:
    │   ├── 检查熔断器是否可用 → 跳过熔断中的 Key
    │   ├── 创建 UpstreamClient（带当前 Key）
    │   ├── 用 ResilientClientFactory 包装韧性保护
    │   ├── 调用 client.chat(req)
    │   └── 失败 → 记录 failover.triggered Metrics → 尝试下一个 Key
    │
    └── 全部失败 → 抛出 ProviderException("所有 Key 均失败")
```

**流式 Key 故障转移**（异步回调链）：

```
streamWithCredential(ctx, req, credentials, credIndex, ...)
    │
    ├── 创建带 failoverCallback 的流式调用
    ├── onError 时（且未收到数据块）：
    │   ├── 记录 failover.triggered Metrics
    │   └── streamWithCredential(..., credIndex + 1, ...)  ← 递归下一个 Key
    └── 全部失败 → auditingCallback.onError("所有流式 Key 均失败")
```

#### 3.4.6 模型级智能降级（规划中）

> **状态说明**：模型级智能降级为设计愿景，当前代码中无对应实现（gateway-proxy 已具备 Key 级故障转移，模型级降级链待后续版本落地）。

**降级链机制**（规划中：gateway-proxy · proxy/degradation/）：

```
ChatDispatchService.dispatch() 捕获 ProviderException
    │
    ├── DegradationService.degrade(model, errorType)
    │   ├── 查找降级链配置：primary → [fallback1, fallback2, ...]
    │   ├── 遍历备选模型，跳过不可用的
    │   └── 找到可用备选 → 返回模型名，发布 DegradationEvent
    │
    └── 重新调度：dispatch(req.setModel(fallbackModel), ...)
        └── 最多 MAX_DEGRADATION_DEPTH=5 次降级
```

**降级链配置示例**：
```yaml
gateway:
  degradation:
    enabled: true
    chains:
      - primary: "gpt-4o"
        fallbacks: ["claude-sonnet-4", "gpt-4o-mini"]
        recovery:
          success-threshold: 3
```

**自动回切机制**：
- 定期（默认 60s）对降级中的模型执行健康检查
- 连续 N 次成功（success-threshold）后标记模型恢复
- 后续请求自动切回主模型

#### 3.4.7 舱壁隔离（Bulkhead）

`ResilientUpstreamClient` 使用 `Semaphore` 限制单个 Provider 的并发请求数：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| maxConcurrent | 50 | 单个 Provider 最大并发数 |
| acquireTimeout | 100ms | 获取许可超时时间 |

超出并发限制时返回 `CircuitOpenException("舱壁隔离拒绝请求")`，对应 Metrics 指标 `gateway.bulkhead.rejected`。

**Entity 关联设计原则**:

Domain Entity 应保持纯粹，关联关系通过 ID 引用而非对象引用：

| 原则 | 说明 |
|------|------|
| **统一使用 ID 引用** | Entity 只持有关联对象的 ID，不持有对象引用 |
| **按需加载关联数据** | 通过 Domain Service 或 Gateway 获取关联对象 |
| **避免隐式依赖** | 防止 N+1 查询问题和测试复杂度增加 |

**推荐模式**:

```java
// ✅ 推荐：使用 ID 引用
@Data
public class Model extends BaseEntity {
    private Long providerId;        // ID 引用
    private String displayName;
    // ...
}

// ❌ 不推荐：使用对象引用
@Data
public class Model extends BaseEntity {
    private Provider provider;      // 避免：对象引用带来隐式依赖
    private String displayName;
    // ...
}
```

**关联数据获取方式**:

```java
// 通过 Domain Service 获取关联对象
public class ModelDomainService {
    public Provider getProvider(Model model) {
        return providerGateway.findById(model.getProviderId());
    }
}
```

## 5. 扩展点说明

### 5.1 新增 Provider 扩展

新增一个 AI 模型提供商需要实现以下组件：

```
扩展步骤：
1. [协议插件] 新增协议插件模块（如需要新协议）
   └── gateway-protocol/protocol-xxx/（仿 protocol-openai / protocol-anthropic）
       XxxProtocolAdapter（协议格式 ↔ Canonical IR）+ AutoConfiguration（@ConditionalOnProperty）

2. [协议域] 定义协议契约与校验 / 调谐接口（如需要）
   └── gateway-protocol/protocol（protocol/contract|tuning|validation）

3. [协议插件] 实现入站校验 / 出站调谐
   └── gateway-protocol/protocol-xxx/XxxProtocolValidator.java、XxxTuner.java

4. [协议域] 实现 UpstreamClient（上游调用）
   └── gateway-protocol（protocol/transport 接口，HTTP 实现位于协议插件 protocol-xxx）

5. [协议域] 注册到 UpstreamClientRegistry
   └── gateway-protocol（protocol/transport/UpstreamClientRegistry.java）新增注册

6. [Config] 配置 Provider 元数据
   └── database: INSERT INTO providers (code, name, ...)（Flyway 迁移，gateway-boot db/migration）
```

**扩展接口定义**：

```
// 协议域：协议适配器 SPI（gateway-protocol/protocol，protocol 根包）
interface ProtocolAdapter {
    // 协议格式 ↔ Canonical IR 双向映射
    CanonicalChatRequest toCanonical(XxxRequest request);
    XxxResponse fromCanonical(CanonicalChatResponse response);
}

// 协议域：协议校验接口（gateway-protocol/protocol，protocol/validation/）
interface ProtocolValidator {
    void validate(ProtocolRequest request);
}

// 协议域：上游调用接口（gateway-protocol/protocol，protocol/transport/）
interface UpstreamClient {
    ProtocolResponse chat(ProtocolRequest request);
    void chatStream(ProtocolRequest request, StreamCallback callback);
}

// 协议域：注册表
class UpstreamClientRegistry {
    UpstreamClient getClient(String protocol, String baseUrl, String apiKey, int timeout);
    void register(String protocol, UpstreamClient client);
}

// 协议域：流式回调（gateway-protocol/protocol，protocol 根包）
interface StreamCallback {
    void onChunk(StreamChunkResult chunk);
    void onComplete();
    void onError(Throwable error);
}
```

**扩展实现要点**：

| 组件 | 职责 | 位置 |
|------|------|------|
| ProtocolRequest/Response | 协议数据契约 | gateway-protocol（protocol/contract/） |
| ProtocolAdapter | 协议格式 ↔ Canonical IR | gateway-protocol（protocol 根包 / protocol-xxx 插件模块） |
| ProtocolConversionFacade | 跨协议语义映射门面 | gateway-proxy（proxy/conversion） |

| XxxTuner | 出站调谐（协议级默认值） | gateway-protocol（protocol-xxx 插件） |
| UpstreamClient | 建立连接、发送请求、接收响应 | gateway-protocol（protocol/transport） |
| UpstreamClientRegistry | 管理上游调用客户端注册与获取 | gateway-protocol（protocol/transport） |

## 7. 安全设计详解

### 7.1 API Key 加密存储

**加密方案**：

```
┌─────────────────────────────────────────────────────────────┐
│                   API Key 加密存储                           │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  存储格式：IV:密文:Tag（Base64 编码）                        │
│                                                              │
│  【标准版】加密算法：AES-256-GCM                             │
│  ├── 密钥长度：256 位                                        │
│  ├── IV 长度：12 字节（每次随机生成）                        │
│  ├── Tag 长度：128 位                                        │
│  └── 编码：UTF-8 + Base64                                    │
│                                                              │
│  【企业版专属】加密算法：SM4-GCM（国密算法，规划中）          │
│  ├── 密钥长度：128 位                                        │
│  ├── IV 长度：12 字节（每次随机生成）                        │
│  ├── Tag 长度：128 位                                        │
│  └── 符合 GB/T 32907-2016 国家标准                           │
│  └── 当前无 Bouncy Castle 依赖，待后续版本落地              │
│                                                              │
│  加密流程：                                                  │
│  明文 API Key → 生成随机 IV → AES-GCM/SM4-GCM 加密 → 拼接存储│
│                                                              │
│  解密流程：                                                  │
│  存储格式 → 解析 IV/密文/Tag → AES-GCM/SM4-GCM 解密 → 明文   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**密钥管理**：

| 要点 | 说明 |
|------|------|
| 密钥来源 | 外部密钥管理服务（Vault、AWS KMS） |
| 获取时机 | 应用启动时获取，内存中缓存 |
| 轮换周期 | 90 天定期轮换 |
| 访问控制 | 限制密钥访问权限，审计访问记录 |

### 7.2 审计日志防篡改

**链式哈希设计**：

```
┌─────────────────────────────────────────────────────────────┐
│                   链式哈希结构                               │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  记录 N-1          记录 N            记录 N+1               │
│  ┌─────────┐      ┌─────────┐       ┌─────────┐            │
│  │ content │      │ content │       │ content │            │
│  │ hash_N  │ ───► │ prev=N  │ ───►  │ prev=N+1│            │
│  └─────────┘      │ hash_N+1│       │ hash_N+2│            │
│                   └─────────┘       └─────────┘            │
│                                                              │
│  哈希计算：hash_N = SHA256(hash_{N-1} + content_N + ts_N)   │
│                                                              │
│  完整性验证：                                                │
│  遍历所有记录，验证每条记录的 prev_hash 是否等于前一条的 hash │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**数据模型**：

```
AuditLog 实体：
├── id: Long                    # 自增主键
├── previous_hash: String       # 前一条记录的哈希
├── current_hash: String        # 当前记录的哈希（计算后填充）
├── content: String             # 审计内容（JSON）
├── created_at: Instant         # 创建时间
└── created_by: Long            # 操作人
```

**WORM 存储策略（规划中）**：

> **状态说明**：WORM 审计链与链式哈希为设计愿景，当前代码无对应实现（审计事件通过 gateway-audit 模块落库，防篡改链待后续版本落地）。

| 层面 | 措施 |
|------|------|
| 数据库 | 表权限设为 INSERT ONLY，禁止 UPDATE/DELETE |
| 应用 | 审计日志服务只提供写入和查询，不提供修改 |
| 备份 | 每日增量备份，永久保留 |
| 验证 | 定期运行完整性校验，检测篡改
