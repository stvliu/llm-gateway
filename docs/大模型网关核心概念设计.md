# 大模型网关核心概念设计

> 本文档是 LLM-Gateway 核心概念体系的总体设计，整合信息架构与数据架构，面向产品、开发与运维团队。

---

## 1. 定位

LLM-Gateway 是企业级 AI 模型 API 聚合分发与智能路由网关。核心价值：

- **聚合**：统一接入多家大模型供应商，屏蔽供应商差异
- **分发**：通过产品概念实现精细化权限控制和流量分配
- **路由**：智能选择最优渠道和密钥，保障可用性与成本效率

## 2. 核心概念体系

### 2.1 概念全景图

```
                          ┌─────────────────────────────────────────────────┐
                          │                   供应商侧                      │
                          │                                                 │
                          │  Provider ──1:N──► Product ──1:N──► ProductApiKey │
                          │  (供应商)       (产品)       (供应商密钥)         │
                          │                     │                           │
                          │                     ├── Models (模型列表)       │
                          │                     └── Endpoints (多协议端点)  │
                          │                                                 │
                          └─────────────────────────────────────────────────┘
                                           │
                                           │ UserApiKey 绑定 Product
                                           ▼
                          ┌─────────────────────────────────────────────────┐
                          │                   用户侧                        │
                          │                                                 │
                          │  User ──N:N──► Team ──1:N──► UserApiKey        │
                          │  (用户)      (团队)      (用户密钥)              │
                          │                                                 │
                          └─────────────────────────────────────────────────┘
                                           │
                                           │ 请求转发
                                           ▼
                          ┌─────────────────────────────────────────────────┐
                          │                   网关层                        │
                          │                                                 │
                          │  认证 → 鉴权 → 限流 → 选密钥 → 选端点 → 转发   │
                          │                                                 │
                          └─────────────────────────────────────────────────┘
```

### 2.2 概念定义

| 概念 | 定义 | 职责 | 示例 |
|------|------|------|------|
| **Provider** | 大模型供应商 | 提供AI能力的厂商，是产品的上层归属 | 火山方舟、百度、腾讯、DeepSeek |
| **Product** | 计费产品 | 供应商提供的计费单元，包含模型、端点、密钥 | Coding Plan、Token Plan、按量计费 |
| **ProductApiKey** | 供应商侧密钥 | 调用供应商API的认证凭证 | 火山方舟API Key、百度API Key |
| **Model** | AI模型标识 | 产品包含的具体模型 | `doubao-seed-code`、`deepseek-4.0-pro` |
| **Endpoint** | 多协议端点 | 按API协议区分的Base URL | 原生协议、OpenAI兼容、Anthropic兼容 |
| **Team** | 团队 | 用户组织单元，决定产品访问权限 | 开发团队、小龙虾团队、产品团队 |
| **UserApiKey** | 用户侧密钥 | 用户访问网关的凭证，绑定特定产品 | `sk-code-xxx`、`sk-token-xxx` |

## 3. 产品模型

### 3.1 为什么需要产品？

传统网关直接将模型与供应商绑定（Model → Provider），无法表达以下业务需求：

| 业务需求 | 传统模型 | 产品模型 |
|---------|---------|---------|
| 同一供应商多种计费方式 | ❌ 无法区分 | ✅ 按量/Coding/Token 三种产品 |
| 不同团队访问不同模型集 | ❌ 只能按模型名控制 | ✅ 按产品绑定控制 |
| 多协议不同Base URL | ❌ 供应商只有一个URL | ✅ 产品配置多协议端点 |
| 密钥按产品隔离 | ❌ 密钥挂在供应商 | ✅ 密钥挂在产品 |

### 3.2 产品类型

| 类型 | 标识 | 计费方式 | 额度 | 典型场景 |
|------|------|---------|------|---------|
| **按量计费** | `pay_as_you_go` | 按实际用量付费 | 无固定额度 | 通用产品人员使用 |
| **Coding Plan** | `subscription_coding` | 订阅制 | 固定Token额度 | 开发者编码场景 |
| **Token Plan** | `subscription_token` | Token包计费 | 固定Token包 | 特定团队专项使用 |

### 3.3 产品与协议

不同产品类型支持不同API协议，且每种协议的Base URL不同：

| 产品类型 | 支持协议 | 说明 |
|---------|---------|------|
| 按量计费 | `openai` | 仅兼容OpenAI协议 |
| Coding Plan | `native`, `openai`, `anthropic` | 支持原生及双兼容协议 |
| Token Plan | `native`, `openai`, `anthropic` | 支持原生及双兼容协议 |

**火山方舟示例**：

```json
{
  "native": "https://ark.cn-beijing.volces.com/api/coding/v3",
  "openai": "https://ark.cn-beijing.volces.com/api/v3",
  "anthropic": "https://ark.cn-beijing.volces.com/api/anthropic"
}
```

## 4. 双层密钥架构

### 4.1 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                        用户侧                                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              User API Key (sk-xxx)                  │   │
│  │  - 用户访问网关的凭证                                │   │
│  │  - 绑定特定产品                                      │   │
│  │  - 可设置模型子集、额度限制                          │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                        网关层                                │
│  - 验证 User API Key                                        │
│  - 路由到对应 Product                                        │
│  - 选择 Product API Key                                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                        供应商侧                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │           Product API Key (供应商密钥)               │   │
│  │  - 调用供应商 API 的认证密钥                         │   │
│  │  - 支持多个 Key（轮换、负载均衡、故障转移）           │   │
│  │  - 加密存储                                          │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 密钥对比

| 属性 | User API Key | Product API Key |
|------|-------------|----------------|
| **归属** | 用户/团队 | 产品 |
| **用途** | 访问网关 | 调用供应商API |
| **存储方式** | SHA-256哈希 | AES-256加密 |
| **数量** | 一个团队可有多个 | 一个产品可有多个 |
| **格式** | `sk-{type}-{random}` | 供应商原始格式 |
| **权限** | 绑定产品+模型子集 | 无权限概念，纯认证 |

### 4.3 Product API Key 多密钥策略

| 用途 | 配置方式 | 说明 |
|------|---------|------|
| **密钥轮换** | 添加新Key，禁用旧Key | 平滑切换，无停机 |
| **负载均衡** | 设置`weight` | 多个Key按权重分配请求 |
| **故障转移** | 设置`priority` | 主Key失败时自动切换备用Key |

## 5. 访问控制模型

### 5.1 控制链路

```
用户 → 团队（角色）→ User API Key → Product（产品类型）→ 模型子集
```

**核心原则**：
1. 用户归属于一个或多个团队
2. 团队角色决定可访问的产品类型
3. User API Key 绑定具体产品，实现细粒度权限控制
4. 网关只验证User API Key，权限通过路由规则配置

### 5.2 典型场景

**同一供应商，不同团队访问不同产品**：

| 场景 | 用户 | 团队 | User API Key | Product | 权限 |
|------|------|------|--------------|---------|------|
| 开发者编码 | 张三 | 开发团队 | sk-code-001 | 火山方舟 Coding Plan | ✅ |
| 小龙虾专项 | 李四 | 小龙虾团队 | sk-token-001 | 火山方舟 Token Plan | ✅ |
| 产品人员通用 | 王五 | 产品团队 | sk-pay-001 | 火山方舟 按量计费 | ✅ |
| 开发者越权 | 张三 | 开发团队 | sk-code-001 | 火山方舟 Token Plan | ❌ |

### 5.3 多团队用户

**场景**：张三同时属于"开发团队"和"小龙虾团队"

**解决方案**：
- 张三持有两个User API Key
  - `sk-code-001`：绑定火山方舟 Coding Plan
  - `sk-token-001`：绑定火山方舟 Token Plan
- 不同Key用于不同场景，互不干扰

## 6. 请求处理流程

### 6.1 七步流程

```
┌──────────────┐
│  用户请求    │  Authorization: Bearer sk-code-xxx
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  1. 认证     │  User API Key → SHA-256哈希 → 查库验证
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  2. 鉴权     │  Key绑定的Product → 模型权限校验
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  3. 限流     │  Key/Team级别额度检查
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  4. 选密钥   │  ProductApiKey → weight/priority策略选择
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  5. 选端点   │  Product.endpoints → 按协议选Base URL
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  6. 转发     │  调用供应商API
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  7. 记录     │  写入用量记录（input/output tokens, cost）
└──────────────┘
```

### 6.2 协议路由

| 请求协议 | 端点选择策略 |
|---------|-------------|
| 用户指定协议 | 优先使用`endpoints[protocol]` |
| 未指定协议 | 降级到`openai`兼容协议 |
| 协议不支持 | 返回错误，提示可用协议 |

## 7. 实体关系

### 7.1 关系矩阵

| 关系 | 类型 | 说明 |
|------|------|------|
| Provider → Product | 1:N | 一个供应商可提供多个产品 |
| Product → ProductApiKey | 1:N | 一个产品可配置多个供应商密钥 |
| Product → Model | 1:N | 一个产品包含多个模型 |
| Product → Endpoint | 1:N | 一个产品支持多个协议端点 |
| User → Team | N:N | 一个用户可归属多个团队 |
| Team → UserApiKey | 1:N | 一个团队可创建多个用户密钥 |
| UserApiKey → Product | N:1 | 一个用户密钥绑定一个产品 |
| UserApiKey → UsageRecord | 1:N | 一个用户密钥产生多条用量记录 |

### 7.2 关系图

```
┌─────────────┐                    ┌─────────────────┐                    ┌─────────────────┐
│   Provider  │                    │      Team       │                    │      User       │
│   供应商    │                    │      团队       │                    │      用户       │
└──────┬──────┘                    └────────┬────────┘                    └────────┬────────┘
       │                                    │                                      │
       │ 1:N                                │ 1:N                                  │ N:N
       │                                    │                                      │
       ▼                                    ▼                                      ▼
┌─────────────┐                    ┌─────────────────┐                    ┌─────────────────┐
│   Product   │                    │  User API Key   │◄───────────────────│   User Team     │
│    产品     │                    │  用户侧密钥     │                    │  用户-团队关联  │
└──────┬──────┘                    └────────┬────────┘                    └─────────────────┘
       │                                    │
       │ 1:N                                │ N:1
       │                                    │
       ▼                                    ▼
┌─────────────┐                    ┌─────────────────┐
│Product API  │                    │   Usage Record  │
│    Key      │                    │   用量记录      │
│ 供应商密钥  │                    └─────────────────┘
└─────────────┘
```

## 8. 数据模型

### 8.1 表清单

| 表名 | 职责 | 关键字段 |
|------|------|---------|
| `providers` | 供应商 | id, name, display_name, state |
| `products` | 产品 | id, provider_id, name, product_type, models(JSONB), endpoints(JSONB), quota_limit, state |
| `product_api_keys` | 供应商密钥 | id, product_id, name, api_key_encrypted, weight, priority, state |
| `users` | 用户 | id, email, name, state |
| `teams` | 团队 | id, name, description, state |
| `user_teams` | 用户-团队关联 | user_id, team_id, role |
| `user_api_keys` | 用户密钥 | id, team_id, owner_user_id, product_id, key_hash, key_prefix, models(JSONB), quota_limit, state |
| `usage_records` | 用量记录 | id, user_api_key_id, team_id, product_id, model, protocol, input_tokens, output_tokens, cost |

### 8.2 JSONB字段设计

**products.models** — 模型列表：
```json
["doubao-seed-code", "doubao-seed-1.6", "doubao-pro-32k"]
```

**products.endpoints** — 多协议端点：
```json
{
  "native": "https://ark.cn-beijing.volces.com/api/coding/v3",
  "openai": "https://ark.cn-beijing.volces.com/api/v3",
  "anthropic": "https://ark.cn-beijing.volces.com/api/anthropic"
}
```

**user_api_keys.models** — 可访问模型子集（为空=全部）：
```json
["doubao-seed-code", "doubao-seed-1.6"]
```

### 8.3 密钥安全

| 密钥类型 | 存储方式 | 字段 |
|---------|---------|------|
| Product API Key | AES-256加密 | `api_key_encrypted` |
| User API Key | SHA-256哈希 | `key_hash` |

## 9. 扩展性

| 扩展场景 | 操作 | 是否需要改代码 |
|---------|------|---------------|
| 新增供应商 | 注册供应商→创建产品→配置密钥 | ❌ |
| 新增产品类型 | 定义类型标识→配置访问规则 | ❌ |
| 新增协议 | 端点配置添加新协议→实现适配器 | ✅（仅适配器） |
| 新增团队 | 创建团队→添加用户→创建密钥 | ❌ |

## 10. 重构路线

采用增量重构（方案A），四阶段演进：

| 阶段 | 目标 | 关键动作 | 预计时间 |
|------|------|---------|---------|
| **1** | 新增Product层 | 创建Product/ProductApiKey实体，数据自动迁移 | 1周 |
| **2** | 新增Team体系 | 创建Team/UserTeam/UserApiKey实体 | 1周 |
| **3** | 切换路由逻辑 | 认证/路由切换到新架构，双写兼容 | 1周 |
| **4** | 清理废弃代码 | 删除GatewayApiKey、ProviderApiKey | 3天 |

**兼容性保障**：每个阶段可独立部署，旧功能不受影响，提供回滚脚本。
