# 容灾管理范式与控制台落地

> 状态：已落地，本文档为容灾架构的管理面设计文档，与实现对齐。
> 关联：`docs/容灾方案设计.md` 的管理面配套。把三层容灾栈机制（L0/L1）藏起来，给管理员暴露「应用级超时」+「渠道优先级」两个直接配置项。
> 实现参考：delta spec `openspec/changes/simplify-resilience-architecture/specs/resilience-console/`。
> 历史脉络：初版由 `resilience-architecture` change 落地「容灾画像档位 + 降级兜底开关」范式；`simplify-resilience-architecture` change 删 L2/画像/会话亲和/PinnedModel 后，管理范式简化为「应用 timeout + 渠道 priority」直接配置，不再有画像模板与档位推导。

## 一、管理核心原则：直接配而非选档位

容灾栈（L0/L1）是内部机制，管理员不直接操作。本 change 删除容灾画像实体与档位推导后，管理员面对的是两个直接配置项：

1. **应用级超时**——`Application.timeout`（0 用渠道默认，非 0 覆盖渠道默认）。直接在应用编辑表单配置，无档位推导。
2. **渠道优先级**——`ApplicationChannel.priority`（数值越小越先试）。在应用渠道授权页配置，定义 L1 转移先后次序。

管理员面对的是「给这个应用配多长超时、渠道按什么顺序试」，不是「选哪个容灾档位」。容灾栈对管理员完全藏起来——L0 Key 级与 L1 Channel 级转移对用户透明，无需配置。

> 与原范式的差异：原范式用「容灾画像档位（STANDARD/STRICT/AGGRESSIVE）+ 降级兜底开关」抽象，专家字段（会话亲和/模型锁定/超时/降级深度）由档位自动推导折叠在「高级」。本 change 删 L2/画像后，档位推导失去载体（L2 已删、会话亲和/模型锁定删除，只剩 timeout），不配独立实体。timeout 直接挂 Application，转移顺序直接挂 ApplicationChannel.priority，管理员直接配而非选档位。

## 二、两屏管理范式

### 屏1：容灾总览页（只读，10s 轮询）

回答「现在稳不稳」，只读不配置：

- **故障域拓扑**：Cluster 卡片视图，每卡显示成员渠道映射（渠道按 clusterId 归域）。Cluster 语义为「跨供应商故障独立性分组」——同卡渠道共因，跨卡渠道故障独立。**不再展示域级健康灯**（域级健康聚合 `ClusterHealthAggregator` 已删，健康状态看端点级熔断器）。
- **转移事件流**：最近 N 条 L1 转移记录——「from 渠道/端点 → to 渠道/端点、clusterId、errorType、decision（L1/NONE）、是否共因跳过、occurredAt」。前端 10s 轮询 `GET /api/v1/resilience/events`（分页 + `since`/`applicationId`/`clusterId` 过滤，按 `occurredAt` 倒序）。**新增「是否共因跳过」标记**展示，高亮共因跳过与耗尽事件。
- **耗尽告警**：候选全部耗尽（`exhausted=true`）事件高亮，提示该补供给侧。前端 10s 轮询 `GET /api/v1/resilience/events/exhausted`（`since` 默认最近 1 小时，`limit` 默认 50）。

> 事件发布与持久化见 `docs/容灾方案设计.md` 第八节：`ChannelFailoverInvoker` 经 `DomainEventPublisher` 发布 `FailoverOccurredEvent`，`FailoverEventListener` 用 `@EventListener` 同步持久化。clusterId 从 `RoutingContext` 直取（删原 ChannelGateway 反查）。

### 屏2：应用管理页（高频，timeout + 渠道 priority 配置）

管理员 99% 日常操作，在应用管理页配置应用级超时与渠道转移顺序：

- **应用级 timeout 配置**：直接在应用编辑表单配置 `Application.timeout`（0 用渠道默认，非 0 覆盖渠道默认）。保存到 `Application.timeout`，由 `RoutingResolver` 注入运行时。
- **渠道授权 priority 配置**：在应用渠道授权页配置各渠道 `ApplicationChannel.priority`（拖拽或数值排序，定义 L1 转移先后次序）。保存到 `ApplicationChannel.priority`。
  - 端点：`GET /api/v1/applications/{id}/channels`（返回含 priority 的渠道列表）、`PUT /api/v1/applications/{id}/channels`（先清空旧关联，再批量保存含 priority 的新关联，HTTP 204）。
  - 请求体：`{ "channels": [{ "channelId": 1, "priority": 1 }, { "channelId": 2, "priority": 2 }] }`
- **不再有容灾画像绑定入口**：原 `PUT /api/v1/applications/{id}/resilience`（绑 resilienceProfileId）端点删除，应用编辑页不再有「容灾模式档位」Select 与「高级」抽屉。

> 与原范式的差异：原屏3 是「写入式画像绑定」（选档位 → 推导画像专家字段 → 绑定画像）。本 change 删画像后，timeout 直接配在应用表单，priority 直接配在渠道授权页，无档位推导中间层。原屏2「画像模板页」整删（画像实体退场）。

## 三、应急操作（Channels 页）

复用既有熔断器，无新状态机。`CircuitBreaker` 的 `forceOpen`/`forceClose` 应急方法与自动熔断同语义，`HealthRouter` 自动过滤熔断端点。

| 操作 | API | 作用 | 场景 |
|------|------|------|------|
| 一键熔断 | `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-open` | 强制熔断器 OPEN，立即切断端点流量 | 怀疑端点质量差，主动摘除 |
| 一键恢复 | `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-close` | 强制熔断器 CLOSED 并重置窗口，立即恢复流量 | 端点修复，重新接入 |
| 状态查询 | `GET /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/state` | 返回 CLOSED/OPEN/HALF_OPEN | 查看当前熔断状态 |

规则：
- 一键熔断/恢复委托 `ChannelEndpointCircuitBreakerManager`，复用既有熔断器实例（`forceOpen` 无视滑动窗口直接置 OPEN，`forceClose` 置 CLOSED 并重置窗口）。
- 应急操作前校验端点归属（`endpoint.channelId == 传入 channelId`），避免误操作其他渠道的端点。
- 应急操作返回 `CircuitBreakerStateResponse`（含状态名）。

> **紧切域功能已移除**：原「紧切域」（`PUT /api/v1/channels/{id}/cluster`，改 channel.clusterId 切故障域）依赖域级亲和路由（`ClusterAffinityRouter`），本 change 删除域级聚合路由后该功能无意义，已移除。后续如需基于 Cluster 的应急操作，另开 change 重新设计。一键熔断/恢复保留（基于端点级熔断器，不依赖域）。

## 四、操作映射总表

```
管理员问                  去哪                    做什么
─────────────────────────────────────────────────────────
现在稳不稳?          → 容灾总览页             只看（10s 轮询，含共因跳过标记）
给新应用配超时       → 应用管理页编辑表单      配 Application.timeout（0 用渠道默认）
定义渠道转移顺序     → 应用管理页渠道授权页    配 ApplicationChannel.priority（越小越先试）
某端点有问题先摘掉   → Channels 页一键熔断      应急（force-open）
端点修复重新接入     → Channels 页一键恢复      应急（force-close）
查看端点熔断状态     → Channels 页状态查询      应急（state）
```

## 五、控制台页面改动清单（已落地）

| 页面 | 改动 | 复杂度 |
|------|------|--------|
| 容灾总览页 | 故障域拓扑（Cluster 跨供应商分组，删域级健康灯）+ 成员渠道映射 + 转移事件流（含共因跳过标记，10s 轮询）+ 耗尽告警 | 中 |
| 应用管理页 | 应用级 timeout 配置（编辑表单）+ 渠道授权 priority 配置（拖拽/数值排序） | 小 |
| Channels 详情 | 「一键熔断/恢复/状态查询」按钮（紧切域按钮移除） | 小 |

新增/变更后端 API（已实现）：
- `GET /api/v1/resilience/events` —— 转移事件流查询（分页 + `since`/`applicationId`/`clusterId` 过滤，事件含 commonCauseSkip）
- `GET /api/v1/resilience/events/exhausted` —— 耗尽告警查询（`exhausted=true`，默认最近 1 小时）
- `POST/PUT/GET /api/v1/resilience/clusters` —— 故障域 CRUD（字段瘦身：code/name/description/providerId + 审计）
- `GET /api/v1/applications/{id}/channels` —— 查询应用渠道授权（含 priority）
- `PUT /api/v1/applications/{id}/channels` —— 更新应用渠道授权（含 priority，HTTP 204）
- `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-open` —— 一键熔断
- `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-close` —— 一键恢复
- `GET /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/state` —— 状态查询

> 已删除的 API：`POST/PUT/GET /api/v1/resilience/profiles`（画像模板 CRUD）、`PUT /api/v1/applications/{id}/resilience`（画像绑定）、`PUT /api/v1/channels/{id}/cluster`（紧切域）。

## 六、关键取舍

1. **不暴露三层栈概念**：L0/L1 是内部机制，管理员只看「应用 timeout」+「渠道 priority」，不再有「容灾模式档位」抽象。
2. **删档位推导，直接配置**：原范式用档位（STANDARD/STRICT/AGGRESSIVE）推导专家字段，删 L2/会话亲和/PinnedModel 后档位无可推导字段，改为 timeout 与 priority 直接配置，降低心智成本。
3. **日常操作在应用管理页**：timeout 在应用编辑表单，priority 在渠道授权页，不强迫管理员学新交互。
4. **应急复用熔断器**：手动摘流量（force-open）与自动熔断同语义，无新状态机。紧切域随域级路由删除而移除。
5. **转移事件流轮询而非 SSE**：10s 轮询足够容灾可观测性实时性，实现简单，避免 SSE 连接管理复杂度。新增共因跳过标记区分真实失败转移与共因跳过转移。
