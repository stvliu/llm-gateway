# 容灾管理范式与控制台落地

> 状态：已落地，本文档为 `resilience-architecture` change 的最终管理面设计文档，与实现对齐。
> 关联：`docs/容灾方案设计.md` 的管理面配套。把四层容灾栈机制藏起来，给管理员暴露「容灾模式」档位 + 「降级兜底」开关，专家字段折叠。
> 实现参考：delta spec `openspec/changes/resilience-architecture/specs/resilience-console/`。

## 一、管理核心原则：选而非填

容灾画像有多个字段，但 99% 场景管理员不该看到它们。三个杠杆：

1. **好默认**——开箱即用的 `default` profile（`code='default'`），不配置也安全。应用未挂画像时解析链回退全局 default。
2. **模板化**——预设画像模板（default/strict/aggressive/batch），管理员克隆微调而非从零填。
3. **可视化**——容灾总览看状态与转移事件流，绑定关系在应用管理页加 Select。

管理员面对的是「给这个应用选哪个档位」，不是「逐字段配容灾」。会话亲和、模型锁定、超时等专家字段默认折叠，只在「高级」展开。

## 二、三屏管理范式

### 屏1：容灾总览页（只读，10s 轮询）

回答「现在稳不稳」，只读不配置：

- **故障域拓扑**：Cluster 卡片视图，每卡显示成员渠道映射 + 健康灯（HEALTHY 绿/DEGRADED 黄/DOWN 红）。一眼看到哪些渠道共因、哪个域挂了。健康状态由 `ClusterHealthAggregator` 实时聚合（全 CLOSED→HEALTHY，全 OPEN→DOWN，混合→DEGRADED，任一 HALF_OPEN 不判 DOWN）。
- **转移事件流**：最近 N 条 L1/L2 转移记录——「from 渠道/端点 → to 渠道/端点、errorType、decision、occurredAt」。前端 10s 轮询 `GET /api/v1/resilience/events`（分页 + `since`/`applicationId`/`clusterId` 过滤，按 `occurredAt` 倒序）。
- **耗尽告警双维度**：候选全部耗尽（`exhausted=true`）事件高亮，提示该补供给侧。前端 10s 轮询 `GET /api/v1/resilience/events/exhausted`（`since` 默认最近 1 小时，`limit` 默认 50）。

> 事件发布与持久化见 `docs/容灾方案设计.md` 第八节：`ChannelFailoverInvoker` 经 `DomainEventPublisher` 发布 `FailoverOccurredEvent`，`FailoverEventListener` 用 `@EventListener` 同步持久化（调用链无事务 + 未配 `@EnableAsync`，故同步而非异步）。clusterId 过滤基于冗余 `fromClusterId`/`toClusterId` 字段（Invoker 反查 `ChannelGateway` 填充）。

### 屏2：画像模板页（低频配）

策略库页，管理预设模板：

- 开箱模板：`default` / `strict`（严格型）/ `aggressive`（激进型）/ `batch`（批量型），由初始化数据（`V56__seed_resilience_profiles.sql`）写入。
- 画像 CRUD：`POST/PUT/GET /api/v1/resilience/profiles`（不提供 delete，default 为系统兜底禁删）。
- 管理员面向两字段：容灾模式档位（`STANDARD`/`STRICT`/`AGGRESSIVE`）+ 降级兜底开关。
- 专家字段（`enableSessionAffinity`/`sessionAffinityTtlMinutes`/`enablePinnedModel`/`pinnedModelId`/`timeout`/`degradationMaxDepth`）由档位自动推导（`ResilienceProfileApplier`），折叠在「高级」。
- 克隆画像模板微调：选档位 → 按档位推导专家字段生成新画像 → 在「高级」中微调。

### 屏3：应用管理页（高频，写入式画像绑定）

管理员 99% 日常操作，在应用管理页提供容灾模式档位选择与降级兜底开关：

- **写入式画像绑定**：管理员选容灾模式档位时，系统按档位推导画像专家字段，绑定对应档位的容灾画像到应用。
- 绑定端点：`PUT /api/v1/applications/{id}/resilience`（body `resilienceProfileId`，null 时解绑回退全局 default 画像）。
- 应用渠道授权：`PUT /api/v1/applications/{id}/channels`（见 `application-access-control` capability）。
- 绑定即生效，应用请求按该画像的容灾策略执行。

> 与设计探讨的差异：原探讨设想「复用现有 Keys/Teams 列表加下拉」。实现中 Team 整体移除（D1/D6），权限锚点改为 Application，画像绑定落在应用管理页（`PUT /applications/{id}/resilience`），而非 Keys/Teams 页。

## 三、应急操作（Channels 页）

复用既有熔断器，无新状态机。`CircuitBreaker` 新增 `forceOpen`/`forceClose` 应急方法，与自动熔断同语义，`HealthRouter` 自动过滤熔断端点。

| 操作 | API | 作用 | 场景 |
|------|------|------|------|
| 一键熔断 | `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-open` | 强制熔断器 OPEN，立即切断端点流量 | 怀疑端点质量差，主动摘除 |
| 一键恢复 | `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-close` | 强制熔断器 CLOSED 并重置窗口，立即恢复流量 | 端点修复，重新接入 |
| 状态查询 | `GET /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/state` | 返回 CLOSED/OPEN/HALF_OPEN | 查看当前熔断状态 |
| 紧切域 | `PUT /api/v1/channels/{id}/cluster`（body `clusterId`） | 将 `channel.clusterId` 改为目标故障域 ID | 主域故障，强制切备用域 |

规则：
- 一键熔断/恢复委托 `ChannelEndpointCircuitBreakerManager`，复用既有熔断器实例（`forceOpen` 无视滑动窗口直接置 OPEN，`forceClose` 置 CLOSED 并重置窗口）。
- 紧切域校验目标故障域存在；**不校验目标域健康**（是否跨域是运维决策）。
- 应急操作前校验端点归属（`endpoint.channelId == 传入 channelId`），避免误操作其他渠道的端点。
- 应急操作返回 `CircuitBreakerStateResponse`（含状态名），紧切域返回 HTTP 204。

## 四、容灾模式档位 → 底层字段推导映射

管理员只面对 2 个面向字段：`容灾模式`（三档位）+ `降级兜底`（开关+深度）。其余字段由档位自动推导（`ResilienceProfileApplier`），专家才覆盖。

### 面向管理员的两个字段

| 字段 | 取值 | 说明 |
|------|------|------|
| 容灾模式 | `STANDARD` / `STRICT` / `AGGRESSIVE` | 覆盖五场景的三档位 |
| 降级兜底 | `{enabled: bool, maxDepth: int}` | 由模式预填，可微调 |

### 三档位语义

- **STANDARD（标准）**：L1 全开 + L2 浅降级（深度 2）+ 渠道默认超时。通用默认，平衡可用性与质量。对应五场景里的「运营流程自动化」「多 agent 大脑」（agent 走会话亲和另配）。
- **STRICT（严格）**：L1 全开 + **L2 关闭** + 超时 60s。不可降级场景，宁可报错不可换模型。对应「Claude Code/CodeX」「agent 大脑（要求一致性时）」。
- **AGGRESSIVE（激进）**：L1 全开 + L2 深降级（深度 3）+ 短超时 15s。可用性优先，质量次之。对应「客服/HelpDesk」。

`BATCH`（批量）作为 STANDARD 的变体：QUEUED 转移 + COST_OPTIMIZED + 长超时，对应「IPD 文档生成」。转移模式（FAST/QUEUED）与成本策略本轮未实现，BATCH 当前等价于 STANDARD，待后续补充 `transferMode` 字段后生效。不单列档位以保持三档简洁。

### 档位 → ResilienceProfile 字段推导表（已实现，`ResilienceProfileApplier.apply`）

| Profile 字段 | STANDARD | STRICT | AGGRESSIVE | 备注 |
|------|------|------|------|------|
| `mode` | STANDARD | STRICT | AGGRESSIVE | 管理员面向字段 |
| `enableL2ModelDegradation` | true | **false** | true | STRICT 关 L2 |
| `degradationMaxDepth` | 2 | 0 | 3 | 「降级兜底」可微调 |
| `timeout` | 0（用渠道默认） | 60 | **15** | AGGRESSIVE 短超时 |
| `enableSessionAffinity` | 保留 base | 保留 base | 保留 base | agent 场景高级开启 |
| `sessionAffinityTtlMinutes` | 保留 base | 保留 base | 保留 base | 默认 30 |
| `enablePinnedModel` | 保留 base | 保留 base | 保留 base | STRICT 专家字段，高级开启 |
| `pinnedModelId` | 保留 base | 保留 base（启用后填） | 保留 base | 锁定模型 ID |

> L1 恒开（无 `enableL1ChannelFailover` 开关，L1 是核心容灾手段不可关）。`apply` 覆盖字段（`mode`/`enableL2ModelDegradation`/`degradationMaxDepth`/`timeout`），保留字段（`code`/`name`/`enableSessionAffinity`/`sessionAffinityTtlMinutes`/`enablePinnedModel`/`pinnedModelId`）。

> 与设计探讨的字段差异：原探讨设想 `transferMode`/`qualityFloor`/`costStrategy`/`clusterAffinity`/`errorRoutingOverride`/`pinnedModelCodes`（字符串列表）等字段。实现精简：这些字段未在本轮实现，`pinnedModelCodes` 改为 `pinnedModelId`（单一模型 ID + `enablePinnedModel` 开关），错误分流表统一由 `ErrorClassifier` 机制层处理（不提供应用级 `errorRoutingOverride` 覆盖）。

### 「降级兜底」开关与档位的联动

`降级兜底.enabled=false` 等价于 `enableL2ModelDegradation=false` + `degradationMaxDepth=0`，即任何档位都能用这个开关临时关闭 L2。`maxDepth` 在 `enabled=true` 时生效，由档位预填默认值，管理员可在 1–5 内微调。

## 五、操作映射总表

```
管理员问                  去哪                    做什么
─────────────────────────────────────────────────────────
现在稳不稳?          → 容灾总览页             只看（10s 轮询）
给新应用配容灾       → 应用管理页选档位        选容灾模式档位（写入式绑定）
客服要更激进降级     → 应用管理页选 AGGRESSIVE  选档位（不用进模板）
CodeX 要锁模型       → 应用管理页选 STRICT + 高级  启用 enablePinnedModel + 填 pinnedModelId
某端点有问题先摘掉   → Channels 页一键熔断      应急（force-open）
端点修复重新接入     → Channels 页一键恢复      应急（force-close）
主域挂了快切备用     → Channels 页紧切域        应急（PUT /{id}/cluster）
查看端点熔断状态     → Channels 页状态查询      应急（state）
```

## 六、控制台页面改动清单（已落地）

| 页面 | 改动 | 复杂度 |
|------|------|--------|
| 容灾总览页（新建） | 故障域拓扑 + 成员渠道映射 + 转移事件流（10s 轮询）+ 耗尽告警双维度 | 中 |
| 应用管理页（Teams 平移而来） | 写入式画像绑定 Select（档位）+ 高级抽屉（会话亲和/锁定模型/兜底深度） | 小 |
| Channels 详情 | 加「一键熔断/恢复/状态查询/紧切域」按钮 | 小 |
| 画像模板页（新建） | 画像模板 CRUD，专家字段折叠 | 中 |

新增后端 API（已实现）：
- `GET /api/v1/resilience/events` —— 转移事件流查询（分页 + `since`/`applicationId`/`clusterId` 过滤）
- `GET /api/v1/resilience/events/exhausted` —— 耗尽告警查询（`exhausted=true`，默认最近 1 小时）
- `POST/PUT/GET /api/v1/resilience/profiles` —— 画像模板 CRUD
- `POST/PUT/GET /api/v1/resilience/clusters` —— 故障域 CRUD
- `PUT /api/v1/applications/{id}/resilience` —— 绑定/解绑容灾画像（body: `{resilienceProfileId}`）
- `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-open` —— 一键熔断
- `POST /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/force-close` —— 一键恢复
- `GET /api/v1/channels/{channelId}/endpoints/{endpointId}/circuit-breaker/state` —— 状态查询
- `PUT /api/v1/channels/{id}/cluster` —— 紧切域

> 与设计探讨的差异：原探讨设想 `PUT /api/keys/{id}/resilience`（绑 Key）+ `PUT /api/teams/{id}/resilience-default`（团队默认）+ `POST /api/resilience/events`（SSE 或轮询）。实现中 Team 移除、权限锚点改 Application，画像绑定端点改为 `PUT /api/v1/applications/{id}/resilience`；转移事件流采用轮询（`GET`，非 `POST`/SSE），前端 10s 轮询渲染。

## 七、关键取舍

1. **不暴露四层栈概念**：L0/L1/L2 是内部机制，管理员只看「容灾模式」+「降级兜底」。
2. **三档位覆盖五场景**：STANDARD/STRICT/AGGRESSIVE + BATCH 变体，避免模式爆炸。
3. **日常操作在应用管理页**：画像绑定靠应用管理页 Select 档位（写入式），不强迫管理员学新交互。
4. **应急复用熔断器**：手动摘流量（force-open）与自动熔断同语义，无新状态机。
5. **转移事件流轮询而非 SSE**：10s 轮询足够容灾可观测性实时性，实现简单，避免 SSE 连接管理复杂度。
