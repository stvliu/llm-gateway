## 概述

本文档定义 LLM-Gateway 的业务概念和信息模型，为后续数据架构设计提供业务语义基础。

### 网关定位

LLM-Gateway 是大模型调用的**反向代理层**，本质职责：

- **代理转发**：将请求准确传递到目标 Provider
- **策略管控**：认证、限流、限额、审计

### 设计原则

| 原则 | 说明 |
|------|------|
| **网关不存储对话** | 不保存对话内容，不维护会话状态，不解析消息语义 |
| **统一入口** | 对外暴露 OpenAI 兼容端点，屏蔽下游 Provider 差异 |
| **策略集中管控** | 认证、限额、审计等策略在网关层统一执行 |

### 划域方法

按**业务能力**划分业务域——每个域回答一个核心问题，拥有独立的实体和生命周期。

## 核心业务链路

```
请求 → security(IP检测/脱敏) → iam(认证鉴权) → usage(限额限流) → proxy(查provider渠道路由转发) → usage(计量) → audit(记录) → 响应
                                                                     ↓
                                                     resilience(熔断/重试/故障转移) → alert(异常告警)
```

**请求处理流程**：

1. **security**：IP 威胁检测（黑白名单）、请求/响应敏感数据脱敏
2. **iam**：验证调用者身份（管理界面 Token 会话 / API 调用 API Key），判断是否有权限访问
3. **usage**：检查 Token 额度、RPM/TPM 限制
4. **proxy**：从 provider 域获取可用渠道，执行路由决策、协议转换、请求转发；调用异常由 resilience 域执行熔断、重试与故障转移
5. **usage**：记录实际 Token 消耗
6. **audit**：记录调用日志，满足审计需求
7. **alert**：异常情况触发告警通知；stats 域对调用数据进行聚合统计（读路径，支撑仪表盘）

## 1. proxy — 模型代理（核心域）

### 责任

回答"**怎么调模型？**"

以标准协议接收请求，选择最优上游渠道，完成调用并返回。

### 子能力

| 子能力 | 说明 |
|--------|------|
| 协议适配 | 接收 OpenAI/Anthropic 格式请求，验证参数（由协议域 gateway-protocol 插件化实现） |
| 路由决策 | 根据策略选择目标 Channel/Model |
| 协议转换 | OpenAI ↔ Anthropic 格式互转（由协议域转换规则实现） |
| 负载均衡 | 多 Channel 按权重分配流量 |
| 故障转移 | 主 Channel 失败自动切换备用（由 resilience 域支撑） |
| 熔断重试 | 连续失败时熔断，超时/错误自动重试（由 resilience 域支撑） |
| 流式传输 | SSE 流式响应的分块传输 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| RouteGroup | 路由分组 | 一组路由策略配置，支持负载均衡和故障转移 |
| RouteGroupChannel | 路由关联 | 路由分组与 Channel 的关联，含权重/优先级/健康状态 |
| SemanticCache | 语义缓存 | 相似请求的缓存条目，含请求向量、响应内容、TTL（设计愿景，规划中） |

### 实体关系

```
RouteGroup
├── 聚合 RouteGroupChannel（一个分组包含多个路由关联）
├── 配置负载均衡策略（权重分配）
├── 配置故障转移策略（备用 Channel）
└── 被调用请求引用

RouteGroupChannel
├── 关联 Channel（一个路由关联指向一个渠道）
├── 持有权重配置（用于负载均衡流量分配）
├── 持有优先级配置（高优先级优先使用）
├── 持有健康状态（由健康检查更新）
└── 当 Channel 不可用时自动跳过

SemanticCache（设计愿景，规划中；依赖 pgvector）
├── 存储请求向量（用于语义相似度匹配）
├── 存储响应内容（命中缓存时直接返回）
├── 持有 TTL 配置（缓存过期时间，默认 1 小时）
├── 持有相似度阈值（默认 0.95，可配置 0.80-0.99）
├── 持有命中率统计（用于评估缓存效果）
├── 支持用户隔离（跨用户缓存不共享）
└── 流式请求可配置跳过缓存
```

## 2. provider — 供给域（模型广场）

### 责任

回答"**有哪些可用？**"

管理上游模型提供商、渠道、模型、目录及其凭证（提供方资源供给）。

### 子能力

| 子能力 | 说明 |
|--------|------|
| Provider 管理 | 模型提供商（OpenAI、Anthropic 等） |
| Channel 管理 | 渠道实例（一个 Provider 可有多个 Channel） |
| Model 管理 | 模型列表和元数据 |
| Catalog 管理 | 模型/产品目录与计划（PlanCatalog），供选型与发现 |
| Upstream 管理 | 上游连接配置（Endpoint、凭证引用） |
| ProviderApiKey 管理 | Provider 调用凭证，支持多 Key 轮换 |
| 健康检查 | 定期检测 Channel 可用性 |
| Product 管理（设计愿景） | 供应商提供的计费产品，包含模型列表和访问端点 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| Provider | 模型提供商 | 模型服务提供方，如 OpenAI、Anthropic |
| Channel | 渠道 | Provider 的具体调用实例，含 BaseURL、API Key、优先级、权重 |
| Model | AI 模型 | 具体的大模型，如 gpt-4o、claude-sonnet-4 |
| Catalog | 目录 | 模型/产品目录（PlanCatalog），供选型与发现 |
| Upstream | 上游 | 上游 Provider 连接配置（Endpoint、凭证引用） |
| ProviderApiKey | Provider 凭证 | 网关调用 Provider 的凭据，管理员配置，支持多 Key 轮换、默认 Key 保护、优先级调整、自动故障转移 |
| Product | 产品（设计愿景） | 供应商提供的计费产品，包含一组模型和访问端点 |

### 实体关系

```
Provider
├── 提供多个 Product（一个供应商可提供多个计费产品）
├── 配置多个 Channel（一个 Provider 可有多个调用实例）
├── 标识官网、API 文档链接
└── 由管理员创建/启用/禁用

Product
├── 归属一个 Provider（产品不能独立存在）
├── 包含多个 Model（产品定义可用模型列表）
├── 配置多协议端点 Endpoints（原生/OpenAI/Anthropic）
├── 标识产品类型（pay_as_you_go / subscription_coding / subscription_token）
├── 持有额度限制（订阅产品的 Token 额度）
├── 可被 UserApiKey 挂载（用户凭证挂载应用实现访问控制）
└── 产品类型决定可访问的团队

Channel
├── 归属一个 Provider（渠道不能独立存在）
├── 配置 BaseURL（可使用代理地址）
├── 关联多个 ProviderApiKey（支持多 Key 轮换）
├── 配置 Key 选择策略（PRIORITY_FIRST / ROUND_ROBIN / WEIGHTED）
├── 持有优先级/权重（用于路由决策）
├── 持有健康状态（由健康检查更新）
└── 可被 RouteGroupChannel 引用

Model
├── 必须归属一个 Provider（模型不能独立存在）
├── 可归属一个 Product（模型属于特定产品）
├── 标识模型能力（上下文长度、多模态、Tool Use 支持）
└── 可被路由关联引用

ProviderApiKey
├── 用于访问一个 Channel（凭证绑定到特定渠道）
├── 支持多 Key 轮换（自动选择可用 Key）
├── 支持默认 Key 保护（不能删除最后一个 Key）
├── 支持优先级可视化调整（前端拖拽排序）
├── 加密存储（当前：AES-256-GCM；企业版 SM4-GCM 国密算法为规划中）
├── 状态：ACTIVE / DISABLED / EXPIRED / RATE_LIMITED / OVERQUOTA / ERROR / DELETED
├── 持有 RPM/TPM 限制（上游 Provider 限制）
├── 持有单 Key RPM/TPM 限制（独立限流，可配置）
├── 持有成功/错误计数（用于健康检测）
├── 持有恢复时间（被禁用后的自动恢复时间点，默认 300 秒）
├── 持有禁用原因（INVALID_KEY / RATE_LIMITED / OVERQUOTA / ERROR / MANUAL）
├── 失效时由健康检查自动禁用，恢复时自动启用
└── 支持自动故障转移（Key 失效时切换到备用 Key）
```

### Provider vs Product vs Channel

```
Provider（抽象提供商）        Product（计费产品）              Channel（具体渠道实例）
─────────────────           ──────────────────             ────────────────────
OpenAI                      Coding Plan                     渠道1: OpenAI 官方 (key-1, 优先级100)
                            Token Plan                      渠道2: OpenAI 代理 (key-2, 优先级50, base_url=代理地址)
                            按量计费
Anthropic                   Coding Plan                     渠道3: Anthropic 官方 (key-3)
```

- **Provider**：抽象的模型服务提供方
- **Product**：供应商的计费产品，定义模型列表、协议端点和额度，是访问控制的锚点
- **Channel**：具体的调用实例，拥有独立的 BaseURL、API Key、优先级、权重，是负载均衡和故障转移的前提

## 3. iam — 身份与访问

### 责任

回答"**谁能调？**"

管理调用者身份（User）、应用（Application）与凭证（UserApiKey），控制谁能以什么条件访问哪些资源。

### 子能力

| 子能力 | 说明 |
|--------|------|
| 身份认证 | 管理界面 Token 会话认证（Sa-Token）；API 调用走 API Key 认证 |
| 用户管理 | 系统用户（User）的创建、启用/禁用、角色分配 |
| 应用管理 | 应用（Application）与渠道授权（ApplicationChannel）管理，作为权限锚点 |
| 凭证管理 | 用户凭证（UserApiKey）的创建、过期、撤销，凭证挂载应用 |
| 角色权限 | 管理员/普通用户权限判断（简化双角色模型） |
| 团队管理（设计愿景） | 用户组织单元，决定可访问的产品类型 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| Application | 应用 | 权限锚点，用户凭证挂载的应用；通过 ApplicationChannel 继承渠道访问权限 |
| User | 系统用户 | 网关使用者，通过 role 字段区分管理员（ADMIN）和普通用户（USER） |
| UserApiKey | 用户凭证 | 用户调用网关的凭证（sk-xxx 格式），归属用户并挂载应用，用户自管理 |
| Team | 团队（设计愿景） | 用户组织单元，决定可访问的产品类型 |
| UserTeam | 用户-团队关联（设计愿景） | 用户与团队的多对多关联，含团队角色 |
| UserOAuth | 用户 OAuth 身份（规划中） | 用户的第三方 OAuth 身份标识 |
| License | 许可证（设计愿景） | 企业版授权管理 |

### 实体关系

```
Team（设计愿景，规划中）
├── 拥有多个 UserTeam（团队成员关联）
├── 决定可访问的产品类型（团队角色 → 产品类型映射）
├── 可创建多个 UserApiKey（团队级凭证管理）
└── 由管理员创建/管理

User
├── 持有 role 字段（ADMIN/USER 双角色）
├── 创建多个 UserApiKey（用户持有自己的凭证）
├── 创建多个 Application（应用作为权限锚点）
├── 操作产生 AuditLog（谁做了什么）
├── 登录触发身份认证（Sa-Token 会话）
└── 密码 BCrypt 加密存储

UserTeam（设计愿景，规划中）
├── 关联 User 和 Team（多对多）
├── 持有团队角色（owner / admin / member）
└── 主键为 (user_id, team_id)

UserApiKey（历史文档中称 GatewayApiKey）
├── 被 User 创建（用户生成自己的 Key）
├── 挂载一个 Application（应用为权限锚点，通过 ApplicationChannel 继承渠道访问权限）
├── 用于 API 请求认证（携带在请求头中，/v1/ 路径由 API Key 认证处理）
├── keyHash（SHA-256）用于认证验证，不可还原
├── keyPlain 加密存储（AES-256-GCM），详情展示时解密
├── 创建时返回原始密钥（仅一次，用户需自行保存）
└── 验证方式：请求密钥 → 计算哈希 → 对比存储哈希

UserOAuth（规划中）
├── 归属一个 User（用户可有多个 OAuth 身份）
├── 存储 OAuth 提供商标识（GitHub/Gitee/飞书/钉钉等）
├── 存储第三方用户标识（OAuth ID）
├── 存储 OAuth 令牌（加密存储，用于 API 调用）
└── 支持解绑和重新绑定

License（设计愿景，规划中）
├── 企业版授权凭证（RSA 签名验证）
├── 包含授权方信息（签发者）
├── 包含被授权方信息（企业名称）
├── 包含有效期（签发时间、过期时间）
├── 包含功能列表（ENTERPRISE、SM_CRYPTO、AUDIT_WORM 等）
├── 包含限制配置（最大用户数、最大节点数）
├── 启动时验证签名和有效期
├── 到期前 30/7/1 天发送告警
└── 过期后降级为标准版功能
```

### 访问控制策略

```
用户 → UserApiKey → Application（权限锚点）→（ApplicationChannel）→ Channel
```

**核心原则**：
1. 用户创建自己的 UserApiKey，挂载到具体应用
2. Application 为权限锚点，通过 ApplicationChannel 继承渠道访问权限
3. 网关只验证 UserApiKey（哈希比对），权限通过应用-渠道授权和路由规则配置
4. 团队-产品访问控制模型（Team/Product）为设计愿景（规划中）

### 访问控制场景

> **说明**：以下场景基于团队-产品模型（Team/Product），为设计愿景示例；当前实现以 UserApiKey → Application 授权为准。

| 场景 | 用户 | 团队 | GatewayApiKey | Product | 访问权限 |
|------|------|------|--------------|---------|---------|
| 开发者访问 Coding Plan | 张三 | 开发团队 | sk-dev-001 | 火山方舟 Coding Plan | ✅ |
| 小龙虾访问 Token Plan | 李四 | 小龙虾团队 | sk-xlx-001 | 火山方舟 Token Plan | ✅ |
| 产品人员访问按量产品 | 王五 | 产品团队 | sk-prod-001 | 火山方舟按量产品 | ✅ |
| 开发者访问 Token Plan | 张三 | 开发团队 | sk-dev-001 | 火山方舟 Token Plan | ❌ |

### 多团队用户处理

**场景**：用户张三同时属于"开发团队"和"小龙虾团队"

**解决方案**：
- 张三拥有两个 GatewayApiKey
  - `sk-dev-001`：绑定火山方舟 Coding Plan
  - `sk-xlx-001`：绑定火山方舟 Token Plan
- 根据 API Key 前缀或命名区分用途

### 角色权限边界

> **简化设计说明**：企业内部网关场景下，两种角色已满足权限控制需求。无需独立的 Role、Permission、UserRole 表，用户表直接包含 `role` 字段。

| 角色 | 权限范围 |
|------|---------|
| **ADMIN** | 全部管理权限：Provider/Model/Channel/Product 管理、用户管理、团队管理、系统配置、日志查看 |
| **USER** | 个人权限：管理自己的 API Key、调用 API、查看自己的用量和日志 |

## 4. security — 安全与威胁

### 责任

回答"**有什么风险？**"

识别并阻断恶意流量（IP 威胁检测），保护请求/响应中的敏感数据（数据脱敏）。

### 子能力

| 子能力 | 说明 |
|--------|------|
| IP 威胁检测 | IP 黑名单（IpBlocklist）全局检测，命中返回 403 |
| 数据脱敏 | SensitiveDataRule 对请求/响应中的 PII 进行检测与脱敏 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| IP 黑名单 | IpBlocklist | 系统屏蔽的 IP 地址（支持 IP/CIDR） |
| 敏感数据规则 | SensitiveDataRule | PII 检测与脱敏规则定义 |

### 实体关系

```
IpBlocklist
├── 被系统全局应用（所有请求都检查）
├── 由管理员配置
├── 支持 IP/CIDR 格式
└── 命中时返回 403

SensitiveDataRule
├── 被应用到请求/响应进行脱敏
├── 包含检测规则（正则、关键词）
├── 定义脱敏方式（掩码、哈希、删除）
└── 覆盖 PII 类型：手机号、身份证、邮箱、银行卡等
```

## 5. usage — 用量管控

### 责任

回答"**能调多少？**"

计量每次调用的 Token 消耗，按层级限制用量（TokenLimit/配额），执行限流（RPM/TPM），防止超额使用。

### 子能力

| 子能力 | 说明 |
|--------|------|
| Token 计量 | 分别统计输入/输出 Token |
| Token 限额 | 用户/Key/用户×渠道多级限制 |
| 用量事件 | 记录用量事件，供统计聚合 |
| 请求限流 | RPM/TPM 令牌桶控制 |
| 预扣与结算 | 请求前预扣，实际消耗后调整 |
| 超限策略 | 拒绝/降级/切换 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| TokenLimit | Token 限额 | 用户/Key/渠道的 Token 用量上限 |
| RateLimitConfig | 限流配置 | RPM/TPM 请求次数限制 |
| UsageRecord | 用量记录 | API 调用消耗的 Token 统计记录（计量视角） |

### 实体关系

```
TokenLimit
├── 约束 User（用户级限额）
├── 约束 UserApiKey（Key 级限额）
├── 可选约束 Channel（用户×渠道限额）
├── 超限时触发预设策略（REJECT → 402 / DOWNGRADE / SWITCH）
├── 支持周期重置（天/周/月/总量）
└── 预扣机制：请求前预估用量并冻结

RateLimitConfig
├── 约束 UserApiKey（Key 级 RPM/TPM）
├── 超限时返回 429 + Retry-After 头
├── 独立于 TokenLimit（两种不同的限制机制）
└── 支持 RPM（每分钟请求数）和 TPM（每分钟 Token 数）

UsageRecord
├── 归属 UserApiKey（记录 Key 的用量）
├── 记录输入 Token 数量
├── 记录输出 Token 数量
├── 用于限额计算和报表生成
├── 支持按时间聚合（天/周/月统计）
├── 由 proxy 域执行调用后产生
└── 职责边界：计量视角，关注 Token 数量消耗
```

### 限额层级

```
TokenLimit 层级关系
├── 用户级: User（单用户总限额）
├── Key 级: UserApiKey（单个凭证限额）
└── 用户×渠道级: User × Channel（精细化配额控制，企业版）
```

## 7. alert — 告警通知

### 责任

回答"**出了什么问题？**"

定义异常条件，发现问题后通知责任人。

### 子能力

| 子能力 | 说明 |
|--------|------|
| 规则定义 | 告警触发条件 |
| 模板管理 | 通知格式模板 |

### 实体

| 业务对象 | 英文名 | 说明 |
|------|--------|------|
| AlertRule | 告警规则 | 告警触发条件定义 |
| AlertTemplate | 告警模板 | 通知格式模板 |
| AlertNotification | 告警通知 | 告警发送记录 |

### 实体关系

```
AlertRule
├── 定义触发条件（阈值、表达式）
├── 关联 AlertTemplate（使用模板格式化通知）
├── 由业务事件触发（调用日志、用量数据、健康检查结果）
├── 触发后产生 AlertNotification
├── 可属于不同业务场景：
│   ├── 安全告警（登录异常、额度超限）
│   ├── 路由告警（Channel 不可用、失败率上升）
│   ├── 供给告警（Key 余额不足、模型下线）

└── 支持静默期配置（避免重复告警）

AlertTemplate
├── 定义通知格式（标题、内容结构）
├── 被多个 AlertRule 引用（模板复用）
├── 支持多种渠道（邮件、Webhook、短信）
├── 包含变量占位符
└── 支持多语言（中文/英文）

AlertNotification
├── 由 AlertRule 触发产生
├── 使用 AlertTemplate 格式化
├── 记录：
│   ├── 触发时间
│   ├── 告警内容
│   ├── 通知渠道
│   ├── 发送状态（成功/失败）
│   └── 确认状态（已确认/未确认）
└── 可被用户确认（Ack）
```

### 告警场景

| 场景 | 触发条件 | 级别 |
|------|---------|------|
| Channel 失败率 | >5% (5 分钟内) | WARN |
| Channel 失败率 | >20% (5 分钟内) | ERROR |
| Token 限额使用率 | >80% | WARN |
| Token 限额耗尽 | ≥100% | ERROR |
| 平均延迟 | P95 > 500ms | WARN |

```
└─────────────────────────────────────────────────────────────────────────────┘
```

> 补充：Channel 调用失败产生 FailoverEvent（resilience 域）；CallLog/UsageRecord 聚合为 Stats（stats 域，仪表盘读路径）。

### 业务一致性约束

| 约束 | 说明 |
|------|------|
| RouteGroup 必须关联至少一个 RouteGroupChannel | 路由分组不能为空 |
| RouteGroupChannel 引用的 Channel 必须存在 | 路由关联必须指向有效渠道 |
| Channel 必须归属于一个 Provider | 渠道不能独立存在 |
| Product 必须归属于一个 Provider | 产品不能独立存在 |
| Model 必须归属于一个 Provider | 模型不能独立存在 |
| ProviderApiKey 必须关联一个 Channel | 凭证不能独立存在 |
| UserApiKey 必须归属于一个 User | 凭证不能是无主之物 |
| UserApiKey 必须挂载一个 Application | 凭证必须挂载可访问的应用 |
| TokenLimit 必须指定限制类型和周期 | 限额不能无限制 |
| AuditLog.previous_hash 必须指向前一条记录 | 形成链式校验（规划中，WORM 未落地） |
| AlertRule 必须关联一个 AlertTemplate | 告警必须有格式化模板 |

### 错误分类

| 错误域 | 核心问题 | 错误类型 |
|--------|---------|---------|
| **proxy** | 代理转发失败 | Provider 调用超时、响应格式错误、连接失败 |
| **provider** | 资源不可用 | 无可用 Channel、所有 Channel 均不可用 |
| **iam** | 访问被拒绝 | 认证失败、授权失败 |
| **security** | 威胁拦截 | IP 被屏蔽、敏感数据规则拒绝 |
| **usage** | 用量超限 | Token 限额超限、请求限流触发 |
| **resilience** | 上游故障 | 熔断触发、重试耗尽、故障转移失败 |
