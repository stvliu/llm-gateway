## 概述

本文档定义 LLM-Gateway 的业务概念和信息模型，为后续数据架构设计提供业务语义基础。
LLM-Gateway 的本质是：
- 路由 — 选择 Provider/Model
- 代理 — 转发请求到 LLM Provider
- 控制 — 认证、限流、审计

**设计原则**：
- 网关核心职责：**大模型调用的 路由+代理+控制**
- 网关不保存对话内容，不维护会话状态，不解析消息语义

**网关核心问题**：

| 业务域 | 核心问题 | 说明 |
|--------|---------|------|
| **router** | **怎么路由？** | 路由决策、供应商选择 |
| **proxy** | **怎么转发？** | 代理转发、请求发送 |
| **supply** | **有什么可用？** | Provider、Model、ProviderApiKey 管理 |
| **security** | **谁能访问？** | 认证、授权、脱敏、IP 控制 |
| **quota** | **可以用多少？** | 限额、限流、用量记录 |
| **audit** | **谁做了什么？** | 操作审计、调用记录 |
| **alert** | **出了什么问题？** | 告警规则、通知发送 |

## 会话业务域删除说明

> **删除时间**：v2.0
> **删除原因**：网关核心职责重新定义

### 删除背景

在 v2.0 版本中，我们对网关的核心职责进行了重新定义：

**网关核心职责**：
- **代理转发**：将请求准确传递到目标 Provider
- **路由决策**：根据策略选择最优 Provider/Model
- **管理调用**：处理调用管理、限额、审计等

**网关不负责**：
- 保存对话内容
- 维护会话状态
- 解析消息语义

### 删除理由

会话业务域（session）原计划包含以下实体：
- `Conversation` — 对话会话
- `Message` — 消息记录
- `ResponseChunk` — 流式响应片段

这些实体被删除的原因：

| # | 理由 | 说明 |
|---|------|------|
| 1 | **代理本质** | 网关是请求代理，不是消息中间件。消息的存储、检索、语义理解不属于网关职责 |
| 2 | **状态无关** | 路由决策不需要了解对话历史。Provider 自身维护会话状态（如 OpenAI 的 `conversation_id`） |
| 3 | **架构简化** | 删除 session 域后，7 个业务域各有明确职责边界，无重叠 |
| 4 | **成本降低** | 不维护会话状态，简化网关复杂度，减少存储和计算开销 |

### 与 Provider 的职责划分

```
┌─────────────────────────────────────────────────────────────────┐
│                        LLM-Gateway（网关）                        │
│  职责：代理转发、路由决策、协议转换、限额管理、审计记录              │
│  不负责：对话历史、会话状态、消息语义                              │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼ 调用 Provider
┌─────────────────────────────────────────────────────────────────┐
│                     OpenAI / Anthropic                          │
│  职责：维护对话历史、理解上下文、管理会话状态                      │
│  网关通过 conversation_id 或 parent_message_id 与 Provider 交互    │
└─────────────────────────────────────────────────────────────────┘
```

### 变更影响

- **保留**：`CallLog`（调用日志）— 记录网关层面的调用元数据，用于审计和追溯
- **删除**：`Conversation`、`Message`、`ResponseChunk` — 不在网关层面管理
- **无影响**：路由、模型供给、安全控制、限额配额、审计合规、告警管理 6 个业务域

## 1. router/ — 路由（核心域）

### 责任

回答"怎么路由？"

- 路由决策：根据策略选择目标 Provider/Model
- 请求执行：发送请求到大模型，接收响应
- 协议转换：OpenAI ↔ Anthropic 格式转换
- 负载均衡：多 Provider/Key 的流量分配
- 故障转移：失败时自动切换
- 流式处理：SSE 流式响应的分块传输

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| RouteGroup | 路由分组 | 一组路由策略配置，支持负载均衡和故障转移 |
| RouteGroupProvider | 路由关联 | 路由分组与 Provider 的关联，含权重/优先级/健康状态 |

### 实体关系

```
RouteGroup
├── 聚合 RouteGroupProvider（一个分组包含多个路由关联）
├── 配置负载均衡策略（权重分配）
└── 配置故障转移策略（备用 Provider）

RouteGroupProvider
├── 关联 Provider（一个路由关联指向一个 Provider）
├── 持有权重配置（用于负载均衡流量分配）
├── 持有优先级配置（高优先级优先使用）
├── 持有健康状态（由健康检查更新）
└── 当 Provider 不可用时自动跳过
```

## 2. supply/ — 模型供给

### 责任

回答"有什么可用？"

- Provider 管理：模型提供商（OpenAI、Anthropic 等）
- Model 管理：模型列表和元数据
- ProviderApiKey 管理：Provider 调用凭证，多 Key 轮换
- 渠道健康检查：定期检测 Provider 可用性

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| Provider | 模型提供商 | 模型服务提供方，如 OpenAI、Anthropic |
| Model | AI 模型 | 具体的大模型，如 gpt-4o、claude-sonnet-4 |
| ProviderApiKey | Provider 凭证 | 网关调用 Provider 的凭据，管理员配置，支持多 Key 轮换 |

### 实体关系

```
Provider
├── 提供多个 Model（一个 Provider 下有多个可用模型）
├── 配置多个 ProviderApiKey（一个 Provider 支持多组凭证）
├── 由管理员创建/启用/禁用
├── 标识 BaseURL、状态（启用/禁用）
└── 被路由决策查询用于执行调用

Model
├── 必须归属一个 Provider（不能独立存在）
├── 标识模型能力（上下文长度、多模态、Tool Use 支持）
└── 可被路由关联引用（指定可用模型）

ProviderApiKey
├── 用于访问一个 Provider（凭证绑定到特定 Provider）
├── 支持多 Key 轮换（自动选择可用 Key）
├── 加密存储
├── 持有 RPM/TPM 限制（上游 Provider 限制）
└── 失效时由健康检查自动禁用
```

## 3. security/ — 安全控制

### 责任

回答"谁能访问？"

- 身份认证：验证请求者身份
- 访问授权：管理员/普通用户权限判断
- 敏感数据保护：PII 检测与脱敏
- IP/UA 过滤：黑名单/白名单控制

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| User | 系统用户 | 网关使用者，含角色枚举 |
| GatewayApiKey | 网关凭证 | 用户调用网关的凭证，用户自管理 |
| IpBlocklist | IP 黑名单 | 系统屏蔽的 IP 地址 |
| SensitiveDataRule | 敏感数据规则 | PII 检测与脱敏规则 |

### 实体关系

```
User
├── 持有 role: UserRole（枚举：ADMIN / USER）
├── 创建多个 GatewayApiKey（用户持有自己的凭证）
├── 操作产生 AuditLog（谁做了什么）
├── 登录触发身份认证
└── 密码 BCrypt 加密存储

UserRole（枚举常量）
├── ADMIN   — 管理员，可管理所有资源
└── USER    — 普通用户，只能管理自己的资源

GatewayApiKey
├── 被 User 创建（用户生成自己的 Key）
├── 用于请求认证（携带在请求头中）
├── 可设置 IP 白名单（限制访问来源）
├── 可设置模型白名单（限制可用模型）
├── 过期时间可配置
└── 哈希存储（不可还原）

IpBlocklist
├── 被系统全局应用（所有请求都检查）
├── 由管理员配置
├── 支持 IP/CIDR 格式
└── 命中时返回 403

SensitiveDataRule
├── 被应用到请求/响应进行脱敏
├── 包含检测规则（正则、关键词）
├── 定义脱敏方式（掩码、哈希、删除）
└── 覆盖 PII 类型：手机号、身份证、邮箱、银行卡等
```

## 4. quota/ — 限额配额

### 责任

回答"可以用多少？"

- Token 限额：用户/Key/用户×渠道多级限制
- 预扣与结算：请求前预扣，实际消耗后调整
- 限流控制：RPM/TPM 令牌桶
- 超限策略：拒绝/降级/切换

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| TokenLimit | Token 限额 | 用户/Key/渠道的 Token 用量上限 |
| RateLimitConfig | 限流配置 | RPM/TPM 请求次数限制 |
| UsageRecord | 用量记录 | API 调用消耗的 Token 统计记录 |

### 实体关系

```
TokenLimit
├── 约束 User（用户级限额）
├── 约束 GatewayApiKey（Key 级限额）
├── 可选约束 Provider（用户×渠道限额）
├── 超限时触发预设策略（REJECT → 402 / DOWNGRADE / SWITCH）
├── 支持周期重置（天/周/月/总量）
└── 预扣机制：请求前预估用量并冻结

RateLimitConfig
├── 约束 GatewayApiKey（Key 级 RPM/TPM）
├── 超限时返回 429 + Retry-After 头
├── 独立于 TokenLimit（两种不同的限制机制）
└── 支持 RPM（每分钟请求数）和 TPM（每分钟 Token 数）

UsageRecord
├── 归属 GatewayApiKey（记录 Key 的用量）
├── 记录输入 Token 数量
├── 记录输出 Token 数量
├── 用于限额计算
├── 支持按时间聚合（天/周/月统计）
└── 由路由执行调用后产生
```

## 5. audit/ — 审计合规

### 责任

回答"谁做了什么？"

- 操作审计：记录所有管理操作
- 不可篡改性：链式哈希，WORM 存储
- 合规报告：满足 SOX/GDPR/等保要求

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| AuditLog | 审计日志 | 管理操作记录 |
| CallLog | 调用日志 | API 调用元数据记录（用于追溯） |

### 实体关系

```
AuditLog
├── 记录操作者（User）
├── 记录操作类型（操作码）
├── 记录操作内容（变更前后数据）
├── 记录操作时间（时间戳）
├── 记录操作结果（成功/失败）
├── 记录客户端 IP（来源追溯）
├── 使用链式哈希（每条包含前一条哈希值）
├── WORM 存储（不可修改/删除）
└── 满足 SOX/GDPR/等保合规要求

CallLog
├── 归属 GatewayApiKey（记录凭证的调用）
├── 记录调用元数据：
│   ├── User
│   ├── Provider
│   ├── 请求时间、响应时间
│   ├── 状态码、错误信息
│   └── Trace ID（追踪标识）
├── 用于用量统计和审计追溯
└── 由路由执行调用后产生
```

## 6. proxy/ — 代理转发

### 责任

回答"怎么转发？"

- 协议转换：OpenAI ↔ Anthropic 格式互转
- 请求发送：将请求转发到 LLM Provider
- 响应处理：流式响应分块传输
- 错误处理：Provider 异常转换

### 实体

proxy 域通过 ProxyGateway 接口实现，不管理实体。核心接口：

| 接口 | 英文名 | 说明 |
|------|--------|------|
| ProxyGateway | 代理网关 | 转发请求到 LLM Provider 的能力接口 |

### 实体关系

```
ProxyGateway（接口）
├── 定义转发方法：forward(request) → response
├── 定义流式方法：forwardStream(request, consumer)
├── 由 OpenAIProxyGateway 实现（OpenAI 格式）
└── 由 AnthropicProxyGateway 实现（Anthropic 格式）

ProxyDomainService
├── 调用 ProxyGateway 执行实际转发
├── 编排认证、限额、路由流程
└── 不保存对话内容，不维护会话状态
```

## 7. alert/ — 告警管理

### 责任

回答"出了什么问题？"

- 规则定义：告警触发条件
- 模板管理：通知格式模板
- 通知发送：邮件、Webhook 等
- 历史记录：告警发送历史

### 实体

| 实体 | 英文名 | 说明 |
|------|--------|------|
| AlertRule | 告警规则 | 告警触发条件定义 |
| AlertTemplate | 告警模板 | 通知格式模板 |
| AlertNotification | 告警通知 | 告警发送记录 |

### 实体关系

```
AlertRule
├── 定义触发条件（阈值、表达式）
├── 关联 AlertTemplate（使用模板格式化通知）
├── 由领域事件触发
├── 触发后产生 AlertNotification
├── 可属于不同业务域：
│   ├── 安全告警（登录异常、额度超限）
│   ├── 路由告警（Provider 不可用、失败率上升）
│   ├── 供给告警（Key 余额不足、模型下线）
│   └── 系统告警（服务异常、配置变更）
└── 支持静默期配置（避免重复告警）

AlertTemplate
├── 定义通知格式（标题、内容结构）
├── 被多个 AlertRule 引用（模板复用）
├── 支持多种渠道（邮件、Webhook、短信）
├── 包含变量占位符
└── 支持多语言（中文/英文）

AlertNotification
├── 由 AlertRule 触发产生
├── 使用 AlertTemplate 格式化
├── 记录：
│   ├── 触发时间
│   ├── 告警内容
│   ├── 通知渠道
│   ├── 发送状态（成功/失败）
│   └── 确认状态（已确认/未确认）
└── 可被用户确认（Ack）
```

## 跨域关系总览 / Cross-Domain Relationships

### 错误类型定义

基于 LLM-Gateway 本质（路由 + 代理 + 控制），错误分为三类：

| 错误域 | 核心问题 | 错误类型 |
|--------|---------|---------|
| **proxy** | 代理转发失败 | Provider 调用超时、响应格式错误、连接失败 |
| **router** | 无法选择路由 | 无可用 Provider、所有 Provider 均不可用、路由策略失败 |
| **control** | 安全/资源控制拒绝 | 认证失败、授权失败、Token 超限、限流触发 |

### 错误响应结构

内部使用时，错误响应包含 Provider 原始信息：

```json
{
  "error": {
    "type": "rate_limit_error",
    "message": "Rate limit exceeded",
    "code": "PROVIDER_429",
    "provider": "openai",
    "raw_code": "insufficient_quota",
    "raw_message": "You exceeded your configured rate limit"
  }
}
```

| 字段 | 说明 |
|------|------|
| type | OpenAI 兼容错误类型 |
| message | 对用户友好的错误消息 |
| code | 内部统一错误码 |
| provider | Provider 来源 |
| raw_code | Provider 原始错误码 |
| raw_message | Provider 原始错误消息 |

### 错误与业务域关系

```
代理错误（proxy/）
├── Provider 连接失败
├── Provider 调用超时
├── Provider 响应格式错误
├── Provider API 限流（429）
└── Provider API 错误响应

路由错误（router/）
├── 无可用 Provider
├── 所有 Provider 均不可用
├── 路由策略无匹配
└── 负载均衡选择失败

控制错误（security/quota/）
├── 认证失败（AUTH_001）
├── Token 超限（AUTH_002）
├── IP 被拒绝（AUTH_003）
├── Token 限额超限（QUOTA_001）
└── 请求限流超限（QUOTA_002）
```

### 错误传播链

```
外部请求
    │
    ▼
┌─────────────────────────────────────┐
│  control — 控制层                   │
│  认证/授权/限流/限额                │
└─────────────────┬───────────────────┘
                  │ 检查通过
                  ▼
┌─────────────────────────────────────┐
│  router — 路由层                     │
│  选择可用 Provider                  │
└─────────────────┬───────────────────┘
                  │ 路由失败
                  ▼
        错误：无可用 Provider
                  │
                  ▼
┌─────────────────────────────────────┐
│  proxy — 代理层                     │
│  转发请求到 Provider                │
└─────────────────┬───────────────────┘
                  │ 调用失败
                  ▼
        错误：Provider 响应异常
```

### 核心业务链路

```
请求入口
    │
    ▼
┌─────────────────────────────────────────────┐
│  security — 安全控制                         │
│  User ──持有──► GatewayApiKey               │
│       ──受限于──► TokenLimit (quota/)       │
└─────────────────────┬───────────────────────┘
                      │ 认证通过
                      ▼
┌─────────────────────────────────────────────┐
│  quota — 限额配额                            │
│  GatewayApiKey ──受控于──► TokenLimit       │
│                 ──受控于──► RateLimitConfig │
└─────────────────────┬───────────────────────┘
                      │ 限额检查通过
                      ▼
┌─────────────────────────────────────────────┐
│  router — 路由（核心）                       │
│  RouteGroup ──包含──► RouteGroupProvider   │
│                       │                     │
│                       ▼                     │
│                   Provider                  │
│                       │                     │
│                       ▼                     │
│                   Model                    │
└─────────────────────┬───────────────────────┘
                      │
      ┌───────────────┼───────────────┐
      ▼               ▼               ▼
┌──────────┐   ┌──────────┐   ┌──────────┐
│  audit   │   │  alert   │
│ 谁做了什么│   │出了什么问题│
│           │   │           │
│ AuditLog │   │ AlertRule │
│  CallLog │   │ AlertNotif│
└──────────┘   └──────────┘
```

### 关键业务语义

| 业务动作 | 关系描述 |
|---------|---------|
| 用户持有凭证 | User 创建/拥有 GatewayApiKey |
| 凭证受限额约束 | GatewayApiKey 被 TokenLimit 限制 |
| 调用产生用量 | CallLog 产生 UsageRecord |
| 调用触发告警 | CallLog 触发 AlertRule |
| 路由选择 Provider | RouteGroup 包含 RouteGroupProvider |
| Provider 提供模型 | Provider 提供 Model |
| 凭证用于调用 | ProviderApiKey 用于 Provider 调用 |
| 操作产生审计 | User 操作产生 AuditLog |
| 告警使用模板 | AlertRule 使用 AlertTemplate 格式化通知 |

### 业务一致性约束

| 约束 | 说明 |
|------|------|
| RouteGroup 必须关联至少一个 RouteGroupProvider | 路由分组不能为空 |
| RouteGroupProvider 引用的 Provider 必须存在 | 路由关联必须指向有效 Provider |
| Model 必须归属于一个 Provider | 模型不能独立存在 |
| ProviderApiKey 必须关联一个 Provider | 凭证不能独立存在 |
| TokenLimit 必须指定限制类型和周期 | 限额不能无限制 |
| GatewayApiKey 必须归属于一个 User | 凭证不能是无主之物 |
| AuditLog.previous_hash 必须指向前一条记录 | 形成链式校验 |
| AlertRule 必须关联一个 AlertTemplate | 告警必须有格式化模板 |
