# 容灾方案设计（Cluster 与 Channel 级失败转移）

> 状态：已落地，本文档为 `resilience-architecture` change 的最终设计文档，与实现对齐。
> 关联：补齐 supply 域缺失的「Channel 级运行时失败转移」，并引入 Cluster 故障域分组与应用级容灾画像。
> 实现参考：delta spec `openspec/changes/resilience-architecture/specs/`、设计探讨 `docs/superpowers/specs/2026-06-19-resilience-architecture-design.md`。

## 一、背景与现状诊断

现有供给域层次：

```
Provider ─┬─ Channel ─┬─ ChannelEndpoint（URL + protocol）
          │           └─ ChannelCredential（多个 API Key）
          │   │
          │   └─ ModelInstance（Channel × Model，带 priority/weight/state）
          │
          └─ Model（规格，如 gpt-4o）
```

调用方层次（已重构）：`UserApiKey → Application → ApplicationChannel → Channel`，权限锚点从「人/团队」转为「应用」（`resilience-architecture` change D1）。Application 升级为权限+行为双聚合根（Key 归属 + 渠道可见性 + 容灾画像）。

### 容灾栈层级

| 层级 | 组件 | 转移粒度 | 触发 |
|------|------|---------|------|
| L0 Key 级 | `KeyFailoverInvoker` | 同 Channel 换 Credential | 单 Key 调用抛 `ProviderException` |
| L1 Channel 级 | `ChannelFailoverInvoker` | 同模型换 Channel（可跨供应商/跨故障域） | 候选调用失败按错误分流决策 |
| L2 模型级 | `DegradationService` | 换能力近似模型（降级链） | L1 全耗尽且画像门禁通过 |
| 路由级 | `RouterChain` | 初始选实例时按权限/健康/域/优先级过滤 | 仅首次选路，产出候选列表 |
| L3 兜底 | — | 抛错给客户端 | L1 全耗尽且 L2 未启用/无备选 |

### 原根因性错配（本 change 已修正）

1. **路由器顺序倒置（已修正）**：原 `RouterChain` 为 `Permission(@100) → Priority(@200) → Health(@300) → LoadBalance(@9999)`，Priority 先于 Health 执行，且 `PriorityRouter` 是 `isForce=true` 只保留 priority 最小组。后果：最小 priority 组被熔断过滤光后直接 force 返回空 → 抛 `ResourceNotFoundException`，**次优先级的健康渠道永无机会被尝试**。已修正为 `Permission(@100) → Health(@200) → ClusterAffinity(@250) → Priority(@300) → PinnedModel(@350) → LoadBalance(@9999)`（见第五节）。

2. **熔断 key 不一致（已修正）**：`HealthRouter` 原用 `channelId`，`KeyFailoverInvoker` 用 `endpointId`。已统一为 `endpointId`：`HealthRouter` 按入站协议经 `EndpointResolver` 从 `channelId` 派生 `endpointId` 后查 `ChannelEndpointCircuitBreakerManager`，与 `KeyFailoverInvoker`（用 `RoutingContext.channelEndpointId()`）共享同一 manager bean（D11，运行时派生方案，不加 DB 字段）。

3. **健康追踪粒度错配（已修正）**：原 `ProviderHealthTracker` 按 `providerCode` 追踪，粒度过粗。已引入 Cluster 域级健康聚合（`ClusterHealthAggregator`，按端点熔断状态聚合 HEALTHY/DEGRADED/DOWN）+ `ClusterAffinityRouter` 驱动域级路由。

4. **降级链语义错位（已修正）**：原 `degrade(reason)` 不分流 `reason`。已引入 `ErrorClassifier` 错误分流表按 `ProviderErrorType` 映射 L1/L2/NONE（见第四节），`DegradationService.degrade(reason, profile)` 受画像门禁约束。

## 二、容灾目标：四层容灾栈

```
L0 Key 级      同 Channel 换 Credential              ← 已有，处理单 Key 失效
L1 Channel 级  同模型换 Channel（可跨供应商）         ← 本方案核心，对用户透明
L2 模型级      换能力近似模型（降级链）               ← 降级为应用可选兜底，非主路径
L3 兜底        抛错给客户端
```

核心原则：**优先在同模型内换故障域（透明），耗尽后才换模型（非透明降级）**。L1 是当前最大缺口，也是 Cluster 概念的落脚点。

> 关于「同一供应商下模型级失败转移是否有必要」：作为容灾手段**无必要**——AUTH/QUOTA/账号限流/网络/宕机都是共因故障，换同供应商模型无效；模型级降级的真正价值是「能力降级兜底」，应按应用开关启用（客服场景救命，CodeX 场景有害），而非全局兜底。

## 三、Cluster 定位：故障域分组

Cluster = Channel 的故障域分组，同组 Channel 共享共因特征（同供应商/同账号/同区域/同专线）。

```
Cluster(故障域 openai-us)
 ├─ Channel A (provider=openai, region=us)
 └─ Channel B (provider=openai, region=us)   ← 与 A 共因，一起挂
Cluster(故障域 openai-sg)
 └─ Channel C (provider=openai-proxy, region=sg)  ← 不同故障域，容灾目标
```

转移规则：**故障域内优先 → 整域故障才跨域**。Cluster 为显式实体（`clusters` 表，见第五节），`Channel.clusterId` 关联故障域。

## 四、错误分流表：L1/L2 路由决策

`ErrorClassifier.classify(errorType)` 按 `ProviderErrorType` 映射到 `FailoverDecision`（L1/L2/NONE），指导转移层级选择：

| 错误类型 | 转移决策 | 理由 |
|---------|---------|------|
| `INVALID_REQUEST` | **NONE**（不转移，直接抛） | 请求级错误换哪都无效，避免雪崩 |
| `AUTHENTICATION_ERROR` | L1（换渠道） | 共因故障：同账号换 Key/模型无效，换账号有效 |
| `RATE_LIMIT_ERROR` | L1（换渠道） | 共因故障：账号级/渠道级限流，换渠道保透明 |
| `QUOTA_EXCEEDED` | L1（换渠道） | 共因故障：配额账号级共用 |
| `TIMEOUT_ERROR` | L1（换渠道） | 共因故障：端点级超时 |
| `UPSTREAM_ERROR` | L1（换渠道） | 共因故障：上游服务异常 |
| `SERVICE_UNAVAILABLE` | L1（换渠道） | 共因故障：上游不可用 |
| `NETWORK_ERROR` | L1（换渠道） | 共因故障：域名/网络级故障 |
| `UNKNOWN_ERROR` | L2（换模型降级） | 模型能力问题，换模型有效 |
| `null` 输入 | NONE（直接抛） | 编程错误或未分类，不转移 |
| 未在表中显式映射的新增枚举 | L2（兜底防御性降级） | 防御性降级 |

硬规则：**`INVALID_REQUEST` 绝不转移**（NONE），所有场景一致。共因故障（AUTH/RATE_LIMIT/QUOTA/TIMEOUT/UPSTREAM/SERVICE_UNAVAILABLE/NETWORK）统一走 L1 换渠道——这些故障换同供应商模型无效，换渠道（可跨供应商/跨故障域）有效。`UNKNOWN_ERROR` 走 L2 换模型——模型能力问题换渠道无效，换模型有效。

> 与设计探讨的差异：原探讨设想 `RATE_LIMIT_ERROR` 区分账号级/模型级、`UNKNOWN_ERROR` 走 L1 限量转移、`errorRoutingOverride` 应用级覆盖。实现简化为统一分流表（共因→L1，模型能力→L2），不提供应用级覆盖——简化降低配置心智成本，分流决策由机制层统一保证正确性。L2 仍受画像门禁（`enableL2ModelDegradation`/`degradationMaxDepth`）约束，画像关闭 L2 时即使 `UNKNOWN_ERROR` 也不降级（见第六节）。

## 五、数据模型

### 5.1 容灾画像实体（已实现）

`ResilienceProfile` 聚合根，承载四层容灾栈的开关与参数。画像纯数据库管理 + CRUD + 控制台管理，预设档位由初始化数据（`V56__seed_resilience_profiles.sql`）写入。

```sql
CREATE TABLE resilience_profiles (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    code            VARCHAR(64)  NOT NULL UNIQUE,   -- 'default' / 'strict' / 'aggressive' / 'batch'
    name            VARCHAR(128) NOT NULL,
    mode            VARCHAR(16)  NOT NULL,           -- STANDARD / STRICT / AGGRESSIVE
    enable_l2_model_degradation BOOLEAN NOT NULL DEFAULT TRUE,
    degradation_max_depth       INT     NOT NULL DEFAULT 2,
    enable_session_affinity     BOOLEAN NOT NULL DEFAULT FALSE,
    session_affinity_ttl_minutes INT    NOT NULL DEFAULT 30,
    enable_pinned_model         BOOLEAN NOT NULL DEFAULT FALSE,
    pinned_model_id             BIGINT,              -- 锁定模型 ID（可空）
    timeout                     INT     NOT NULL DEFAULT 0,  -- 0 表示用渠道默认
    created_by BIGINT, created_at TIMESTAMP, updated_by BIGINT, updated_at TIMESTAMP
);
```

对应领域实体（遵循 `@DomainEntity` + Getter/Setter 纯模型约束）：

```java
@Data @EqualsAndHashCode(callSuper = true) @DomainEntity
public class ResilienceProfile extends BaseEntity {
    private String code;
    private String name;
    private ResilienceMode mode;                  // STANDARD / STRICT / AGGRESSIVE
    private boolean enableL2ModelDegradation;
    private int degradationMaxDepth;              // 0 表示禁用降级
    private boolean enableSessionAffinity;
    private int sessionAffinityTtlMinutes;        // 默认 30
    private boolean enablePinnedModel;
    private Long pinnedModelId;                   // 可空
    private int timeout;                          // 0 表示用渠道默认
    // 审计字段继承自 BaseEntity
}
```

> 与设计探讨的字段差异：实现精简了画像字段——L1 恒开（无 `enableL1ChannelFailover` 开关，L1 是核心容灾手段不可关）、无 `transferMode`/`qualityFloor`/`costStrategy`/`clusterAffinity`/`errorRoutingOverride` 字段、`pinnedModelCodes`（字符串列表）改为 `pinnedModelId`（单一模型 ID，配合 `enablePinnedModel` 开关）。转移模式（FAST/QUEUED）与成本策略等未在本轮实现；错误分流表统一由 `ErrorClassifier` 机制层处理，不提供应用级覆盖（见第四节）。

### 5.2 应用身份载体：Application 聚合根（已实现）

`resilience-architecture` change D1/D4 将权限锚点从「人/团队」转为「应用」，Application 升级为权限+行为双聚合根（Key 归属 + 渠道可见性 + 容灾画像）。容灾画像的应用身份落在 Application 上。

```
Application（聚合根）─ resilienceProfileId → ResilienceProfile
```

- `applications.resilience_profile_id` —— **应用身份载体**。每个应用挂各自画像。
- 全局 `default` profile（`code='default'`）—— 兜底。

**解析链 `Application → Global`**（`ResilienceResolver`，已移除 Team 中间层）：
1. 按 `applicationId` 查 `Application`；不存在则 fail-fast 抛 `GatewayRequestException`（`APPLICATION_NOT_FOUND`）。
2. `Application.resilienceProfileId` 非空时，按 ID 查画像；命中则返回应用级画像。
3. `Application` 未挂画像、或画像已被删（`findById` 返回 null）时，回退全局 `default` 画像。
4. `default` 画像不存在时 fail-fast 抛 `GatewayRequestException`（`RESILIENCE_DEFAULT_PROFILE_MISSING`）。

绑定端点：`PUT /api/v1/applications/{id}/resilience`（body `resilienceProfileId`，null 时解绑回退 default）。

> 与设计探讨的差异：原探讨设想「MVP 不引入 Application 实体，画像绑 API Key，Team 作可选默认，三级解析链 Key → Team → Global」。实现时 Team 整体移除（D1/D6），权限锚点改为 Application，解析链简化为 Application → Global（无中间层）。Application 既是权限聚合根又是容灾配置载体，不再「为容灾单独引入」——它在权限重构中已建立，容灾画像自然挂其上。

### 5.3 Cluster 显式实体（已实现，不经软分域阶段）

`resilience-architecture` change D10 合并原 P2/P3，直接建 Cluster 显式实体，不经软字段阶段。

```sql
CREATE TABLE clusters (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    code            VARCHAR(64)  NOT NULL UNIQUE,   -- 'openai-us' / 'claude-bedrock'
    name            VARCHAR(128) NOT NULL,
    provider_id     BIGINT       NOT NULL,           -- 归属供应商（物理 ID，无 FK 约束）
    region          VARCHAR(64),                     -- 'us-east' / 'sg'，用于就近路由
    priority        INT          NOT NULL,           -- 数值越小越优先，跨域转移排序
    health_status   VARCHAR(16),                     -- 域级健康聚合状态（运行时聚合，非持久化驱动）
    created_by BIGINT, created_at TIMESTAMP, updated_by BIGINT, updated_at TIMESTAMP
);

ALTER TABLE channels ADD COLUMN cluster_id BIGINT;   -- FK 指向 clusters.id
```

对应领域实体：`Cluster`（`code/name/providerId/region/priority/healthStatus`），`healthStatus` 为 `ClusterHealthStatus` 枚举（`HEALTHY`/`DEGRADED`/`DOWN`）。

Cluster 管理 API：`POST/PUT/GET /api/v1/resilience/clusters`（不提供 delete，Cluster 关联 Channel 的 clusterId，删除需级联清理）。

### 5.4 域级健康聚合（已实现）

`ClusterHealthAggregator` 依据一个故障域内各端点的熔断状态，聚合出域级健康状态：

| 域内端点熔断状态 | 聚合结果 |
|----------------|---------|
| 全部 CLOSED | `HEALTHY` |
| 全部 OPEN | `DOWN`（共因故障，整域不可用） |
| 部分 OPEN（混合 CLOSED/OPEN） | `DEGRADED`（容量受损但仍可用） |
| 任一 HALF_OPEN | **不判 DOWN**（视为正在恢复：仍有 OPEN 则 DEGRADED，否则 HEALTHY） |
| 空端点集合 | 保守返回 `HEALTHY`（无故障证据，避免误杀空域） |

只读查询：通过 `CircuitBreaker.getState()` 读取熔断状态，**不调用** `isAvailable`（避免触发 `OPEN→HALF_OPEN` 状态迁移副作用）。纯计算组件，不持久化 `Cluster.healthStatus`，路由侧实时聚合判断域是否 DOWN。

### 5.5 路由器链与熔断修正（已实现）

路由器顺序修正为 `Permission(@100) → Health(@200) → ClusterAffinity(@250) → Priority(@300) → PinnedModel(@350) → LoadBalance(@9999)`：先按权限过滤、再剔除熔断端点、再按域聚合过滤 DOWN 域、再在存活候选里按 priority 分组、再按画像锁定模型、最后透传候选列表。

- `PermissionRouter`（@100，isForce=true）：按 `ApplicationChannel` 授权过滤应用可见渠道，再过滤活跃 Channel（`state.isRoutable()`）。D9：ADMIN 退管理面，数据面无特权旁路，`applicationId` 为 null 时返回空集。
- `HealthRouter`（@200，isForce=true）：按端点粒度过滤熔断中实例。熔断 key 统一为 `endpointId`（D11 运行时派生：按入站协议经 `EndpointResolver` 从 `channelId` 派生 `endpointId`，与 `KeyFailoverInvoker` 共享同一 `ChannelEndpointCircuitBreakerManager`）。
- `ClusterAffinityRouter`（@250，isForce=false）：按域聚合判断——域内全部端点熔断（Cluster DOWN）则过滤整域实例，强制跨域转移；DEGRADED/HEALTHY 域保留。边界：protocol 为 null / channel 未关联 cluster / endpoint 派生失败均保守保留。就近路由（按 region 偏好择域）依赖请求级 region 上下文，当前未实现，仅实现 DOWN 域过滤核心语义。
- `PriorityRouter`（@300，isForce=true）：按 priority 分组，只保留 priority 最小的组。
- `PinnedModelRouter`（@350，isForce=false）：画像 `enablePinnedModel=true` 且 `pinnedModelId` 非空时，仅保留 `modelId == pinnedModelId` 的实例（strict 档位锁定模型语义）。
- `LoadBalanceRouter`（@9999，isForce=false）：降级为透传（候选列表产出后不再收敛到单实例），供 L1 故障转移逐个尝试。

`InstanceSelector.select` 返回**按 priority 升序排序的候选列表**（而非单实例），供 `ChannelFailoverInvoker` 逐个尝试。

## 六、应用级容灾画像与档位推导（已实现）

管理员面向两字段：**容灾模式档位**（`STANDARD`/`STRICT`/`AGGRESSIVE`）+ **降级兜底**（开关 + 深度）。其余专家字段（会话亲和/模型锁定/超时）由档位自动推导，折叠在「高级」。

### 档位语义与字段推导（`ResilienceProfileApplier`）

| 档位 | enableL2ModelDegradation | degradationMaxDepth | timeout | 对应场景 |
|------|--------------------------|---------------------|---------|---------|
| `STANDARD`（标准） | true | 2（浅降级） | 0（用渠道默认） | 通用默认，平衡可用性与质量 |
| `STRICT`（严格） | false | 0（L2 关闭） | 60 | 不可降级场景，宁可报错不可换模型（Claude Code/CodeX） |
| `AGGRESSIVE`（激进） | true | 3（深降级） | 15（短超时） | 可用性优先，质量次之（客服/HelpDesk） |

`BATCH`（批量）为 `STANDARD` 的变体（不单列档位），由「容灾模式=STANDARD + 高级里切转移模式=QUEUED」实现——转移模式（FAST/QUEUED）本轮未实现，BATCH 当前等价于 STANDARD。

`apply` 不修改 base（不可变），返回推导后的新 `ResilienceProfile`：覆盖字段 `mode`/`enableL2ModelDegradation`/`degradationMaxDepth`/`timeout`，保留字段 `code`/`name`/`enableSessionAffinity`/`sessionAffinityTtlMinutes`/`enablePinnedModel`/`pinnedModelId`。

### 五场景映射

| 场景 | 推荐档位 | L1 | L2 | 会话亲和 | 锁模型 | 超时 |
|------|---------|----|----|---------|--------|------|
| 1) 多 agent 大脑 | STANDARD + 高级开亲和 | ✅ | 浅(2) | ✅ | 否 | 渠道默认 |
| 2) 客服/HelpDesk | AGGRESSIVE | ✅ | 深(3) | ❌ | 否 | 15s |
| 3) Claude Code/CodeX | STRICT + 高级锁模型 | ✅ | ❌ | ❌ | Claude 系列 | 60s |
| 4) IPD 文档生成 | STANDARD（BATCH 变体待转移模式实现） | ✅ | 浅(2) | ❌ | 否 | 渠道默认 |
| 5) 运营流程自动化 | STANDARD | ✅ | 浅(2) | ❌ | 否 | 渠道默认 |

### 对照场景一：Claude Code/CodeX（验证 L1，禁降级）

档位 `STRICT`：L2 关闭（`enableL2ModelDegradation=false`），超时 60s。高级配置启用模型锁定（`enablePinnedModel=true`，`pinnedModelId` 指向 Claude 系列模型），`PinnedModelRouter` 强制候选仅含锁定模型渠道。

供给侧配套：为 pinned Claude 模型配置多供应商/多故障域 Channel（Anthropic 官方 / AWS Bedrock / 中转商），挂不同 `clusterId`。L1 转移按域内→跨域逐个尝试，全 Claude 渠道耗尽直接抛错（L2 关闭），让 Code 层提示用户而非静默降级到 GPT。**这正是 L1 作为「不可降级场景唯一容灾手段」的价值兑现。**

### 对照场景二：客服/HelpDesk（验证 L2，全开）

档位 `AGGRESSIVE`：L2 深降级（`enableL2ModelDegradation=true`，`degradationMaxDepth=3`），短超时 15s。L1 全渠道耗尽后自动进 L2 降级链（gpt-4o → gpt-4o-mini → 兜底弱模型）。

两场景 `INVALID_REQUEST` 都 NONE（机制层硬规则），但 L2 开关相反——CodeX 宁可报错不可降级，客服宁可降级不可不可用。

### 画像门禁 L2 降级（已实现）

`DegradationService.degrade(reason, profile)` 在 `profile != null` 时受画像字段约束：

- `enableL2ModelDegradation=false` → 不降级，返回 null
- `degradationMaxDepth <= 0` → 不降级，返回 null
- 按 errorType 分流：仅 `FailoverDecision.L2` 类错误（`UNKNOWN_ERROR`，模型能力问题）触发模型降级；`L1`（共因故障）/`NONE`（请求级错误）不换模型
- 深度上限取 `profile.degradationMaxDepth`

### 画像解析 fail-open（已实现）

`InstanceSelector` 解析容灾画像时 fail-open：`applicationId` 为 null 或画像解析抛异常时降级为 null profile，不阻断路由——仅影响画像化决策（模型锁定/L2 门禁），不影响基础路由（权限/健康/域/优先级）。

## 七、运行时侵入点（已实现）

1. **认证后**（`ApiKeyAuthInterceptor` 解析 apiKeyId → applicationId）：`InstanceSelector` 调 `ResilienceResolver.resolve(applicationId)`，按解析链 `Application → Global` 得出生效画像（fail-open），塞入 `RoutingRequest`。
2. **`RoutingRequest`** 携带 `resilienceProfile` + `applicationId` + `protocol`，贯穿 RouterChain：
   - `PinnedModelRouter`（@350）：画像 `enablePinnedModel=true` 且 `pinnedModelId` 非空时，仅保留锁定模型实例（STRICT 档位场景关键）
   - `ClusterAffinityRouter`（@250）：按域聚合过滤 DOWN 域实例（Cluster 显式实体 + `clusterId`）
   - `LoadBalanceRouter`（@9999）：降级为透传，产出候选列表
3. **`ChannelFailoverInvoker`（新建，替代 DegradationInvoker 回路）**：候选内逐个试，按 `ErrorClassifier.classify(errorType)` 决定 L1/L2/NONE，L1 全耗尽才进 L2（受画像门禁）。

```
ChannelFailoverInvoker.invoke(候选列表, request, profile):
  lastException = null
  for i, instance in 候选列表:                // 已按 priority 升序排序
    ctx = resolve(同模型, instance.channelId)
    try: return keyFailoverInvoker.invoke(ctx, request)   // L0 在内部跑
    catch ProviderException e:
      lastException = e
      decision = errorClassifier.classify(e.errorType)    // L1 / L2 / NONE
      if decision == NONE: throw e                        // 请求级错误直接抛
      publishFailoverEvent(候选[i], 候选, i, applicationId, e.errorType, decision)  // 发布转移事件
      // L1/L2 均继续试下一候选（L2 决策仅记录，不提前跳出）
  // L1 候选全部耗尽，进入 L2 模型降级
  l2Signal = tryL2Degradation(request, lastErrorType, profile, lastException)  // 受画像门禁
  if l2Signal != null:
      throw l2Signal   // L2DegradationRequiredException 携带 fallbackModel，由上层重路由
  throw lastException   // L2 未触发或 degrade 返回 null
```

> 与设计探讨伪代码的差异：原探讨设想「同 cluster 还有候选 continue 域内续命，否则跳到下一 cluster」的显式跨域跳转。实现简化为候选列表已按 priority 排序（`InstanceSelector.select` 产出），L1 逐个尝试即可自然跨域——候选顺序已由 RouterChain 保证（DOWN 域在路由阶段被 `ClusterAffinityRouter` 过滤，存活候选按 priority 排序）。原探讨设想「L1 全耗尽且 `enableL2` 开启时 Invoker 内部调 degrade」；实现改为 L2 降级成功时抛 `L2DegradationRequiredException` 携带 fallbackModel，由 `ChatDispatchServiceImpl` 上层重路由到 fallbackModel（而非 Invoker 内部直接调用），保持 Invoker 职责单一。无论 classify 返回 L1 还是 L2，均继续试下一候选；仅当全部候选耗尽才进 L2（L2 决策不提前跳出 L1 回路，避免误判单候选能力问题就降级）。

流式边界：**只在首字节前转移**，首字节后失败不换渠道（继承现有 `KeyFailoverInvoker.invokeStream` 约束）。

恢复机制：L1 复用 `CircuitBreaker` half-open（`OPEN` 超时后自动转 `HALF_OPEN` 试探放行，成功转 `CLOSED`，失败转 `OPEN`）；Cluster 域级恢复由 `ClusterHealthAggregator` 实时聚合——域内任一端点 `HALF_OPEN` 即不判 DOWN（视为正在恢复），端点 `HALF_OPEN` 成功转 `CLOSED` 后域自然回到 HEALTHY/DEGRADED。

## 八、转移事件流（D12，已实现）

容灾可观测性读侧：新建独立 `FailoverEvent` domain 记录每次候选转移，供控制台总览页轮询渲染。

### 事件发布与持久化

`ChannelFailoverInvoker` 在 L1/L2 决策换下一候选前，经既有 `DomainEventPublisher` 发布 `FailoverOccurredEvent`（DomainEvent），由 `FailoverEventListener` 持久化为 `FailoverEvent` 实体。

- **监听机制**：`FailoverEventListener` 用 **`@EventListener`**（非 `@TransactionalEventListener`）。原因：调用链 `ChatDispatchServiceImpl.dispatch` 无 `@Transactional`，整个请求处理不开启事务，`@TransactionalEventListener(AFTER_COMMIT)` 在无事务上下文时静默丢弃事件（`fallbackExecution` 默认 false），导致转移事件全部丢失。改为 `@EventListener` 后无事务上下文下事件仍被处理。
- **同步处理**：项目未配置 `@EnableAsync`，`@EventListener` 在同一线程内同步调用监听器完成持久化（发布即持久化），调用链在持久化完成后才继续。可观测性持久化开销在毫秒级，对 10k QPS 调用链影响可接受（参照既有 `AuditEventListener` 范式）。
- **可靠性边界**：发布后持久化前进程崩溃则事件丢失（可观测性数据可接受，非计费/审计关键路径）。监听器捕获持久化异常仅记日志，不阻断业务。
- **clusterId 过滤填充**：`RoutingContext` 不携带 clusterId，`ChannelFailoverInvoker` 经 `ChannelGateway.findById(channelId)` 反查 `Channel.clusterId` 填充冗余 `fromClusterId`/`toClusterId` 字段，使 clusterId 过滤生效（转移是失败路径非每次请求都转移，额外查询开销可接受）。

### 事件字段

`FailoverEvent`：`traceId`（串联同请求多次转移，当前调用链暂未透传，OpenTelemetry 接入后填充）、`applicationId`、`fromChannelId`/`fromEndpointId`、`toChannelId`/`toEndpointId`（exhausted 时为 null）、`fromClusterId`/`toClusterId`（冗余，反查填充）、`errorType`（`ProviderErrorType` 枚举名）、`decision`（`L1`/`L2`）、`exhausted`（候选是否全部耗尽）、`occurredAt`。

### 查询端点（`ResilienceEventController`）

- `GET /api/v1/resilience/events` — 转移事件流查询（分页 + `since`/`applicationId`/`clusterId` 过滤，按 `occurredAt` 倒序）。`limit` 默认 100，上限 500。`clusterId` 过滤基于冗余 `fromClusterId`/`toClusterId` 字段匹配（任一命中即返回）。
- `GET /api/v1/resilience/events/exhausted` — 耗尽告警查询（`exhausted=true` 近期事件，按 `occurredAt` 倒序）。`since` 不传时由 Service 层补默认窗口最近 1 小时，`limit` 默认 50。

前端总览页 10s 轮询渲染转移事件流与耗尽告警。

> 与设计探讨的差异：D12 原设想 `@TransactionalEventListener(AFTER_COMMIT)` 异步持久化。实现中发现调用链无事务 + 未配 `@EnableAsync`，改为 `@EventListener` 同步持久化（设计 doc D12 已同步更新此事实）。不复用 CallLog——调用结果语义与转移动作语义不同维度，混表职责模糊、查询复杂。
