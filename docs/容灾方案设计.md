# 容灾方案设计（Cluster 与 Channel 级失败转移）

> 状态：设计探讨定稿，待进入 Comet change 落地。
> 关联：补齐 supply 域缺失的「Channel 级运行时失败转移」，并引入 Cluster 故障域分组与应用级容灾画像。

## 一、背景与现状诊断

现有供给域层次：

```
Provider ─┬─ Channel ─┬─ ChannelEndpoint（URL + protocol）
          │           └─ ChannelCredential（多个 API Key）
          │   │
          │   └─ ModelInstance（Channel × Model，带 priority/weight/state）
          │
          └─ Model（规格，如 gpt-4o）
```

调用方层次：`UserApiKey → User → Team → Channels`，权限边界在 Team（`UserTeam` 成员 + `TeamChannel` 可见渠道），**无 Application 实体**。

### 现有三层失败转移

| 层级 | 组件 | 转移粒度 | 触发 |
|------|------|---------|------|
| Key 级 | `KeyFailoverInvoker` | 同 Channel 换 Credential | 单 Key 调用抛 `ProviderException` |
| 模型级 | `DegradationInvoker` + `DegradationService` | 换另一个模型（降级链） | Key 全部失败后按模型名查 fallbacks |
| 路由级 | `RouterChain`（Priority/Health） | 初始选实例时按 priority 分组 | 仅首次选路，非运行时 |

### 三个根因性错配（Channel 级容灾缺失的根因）

1. **路由器顺序倒置**：`RouterChain` 为 `Permission(@100) → Priority(@200) → Health(@300) → LoadBalance(@9999)`，Priority 先于 Health 执行，且 `PriorityRouter` 是 `isForce=true` 只保留 priority 最小组。后果：最小 priority 组被熔断过滤光后直接 force 返回空 → 抛 `ResourceNotFoundException`，**次优先级的健康渠道永无机会被尝试**。`ModelInstance.priority` 注释写的「同模型多渠道选择」在运行时失效。

2. **熔断 key 不一致**：`HealthRouter` 用 `channelId`，`KeyFailoverInvoker` 用 `endpointId`。两处用不同 key，路由阶段健康判断与调用阶段熔断是两套独立熔断器，互不可见。

3. **健康追踪粒度错配**：`ProviderHealthTracker` 按 `providerCode`（如 "openai"）追踪，只喂给模型级降级判断备选模型可用性，既不驱动 Channel 级路由，粒度也过粗。

4. **降级链语义错位**：`degrade(reason)` 不分流 `reason`，共因故障（AUTH/QUOTA/账号限流/网络/宕机）被当成「换模型」处理，而换模型对这些故障无效。

## 二、容灾目标：四层容灾栈

```
L0 Key 级      同 Channel 换 Credential              ← 已有，处理单 Key 失效
L1 Channel 级  同模型换 Channel（可跨供应商）         ← 本方案核心，对用户透明
L2 模型级      换能力近似模型（降级链）               ← 降级为应用可选兜底，非主路径
L3 兜底        抛错给客户端
```

核心原则：**优先在同模型内换故障域（透明），耗尽后才换模型（非透明降级）**。L1 是当前最大缺口，也是 Cluster 概念的落脚点。

> 关于「同一供应商下模型级失败转移是否有必要」：作为容灾手段**无必要**——AUTH/QUOTA/账号限流/网络/宕机都是共因故障，换同供应商模型无效；模型级降级的真正价值是「能力降级兜底」，应按应用开关启用（客服场景救命，CodeX 场景有害），而非全局兜底。

## 三、Cluster 定位：故障域分组

Cluster = Channel 的故障域分组，同组 Channel 共享共因特征（同供应商/同账号/同区域/同专线）。

```
Cluster(故障域 openai-us)
 ├─ Channel A (provider=openai, region=us)
 └─ Channel B (provider=openai, region=us)   ← 与 A 共因，一起挂
Cluster(故障域 openai-sg)
 └─ Channel C (provider=openai-proxy, region=sg)  ← 不同故障域，容灾目标
```

转移规则：**故障域内优先 → 整域故障才跨域**。Cluster 不强依赖新实体，软分域优先（见数据模型）。

## 四、错误分流表：L1/L2 路由决策

失败后按 `ProviderErrorType` 决定走哪层（默认分流，可被应用画像 `errorRoutingOverride` 覆盖）：

| 错误类型 | 故障域判定 | 转移层 | 理由 |
|---------|-----------|--------|------|
| `AUTHENTICATION_ERROR` | 当前 Channel 账号 | L1 换 Channel | 同账号换 Key/模型无效，换账号有效 |
| `QUOTA_EXCEEDED` | 当前 Channel 账号 | L1 换 Channel | 配额账号级共用 |
| `RATE_LIMIT_ERROR` | 判定账号级/模型级 | 账号级→L1；模型级→L1 先换渠道，渠道同型限流再 L2 | 优先换渠道保透明 |
| `NETWORK_ERROR` | 当前 endpoint 域名 | L1 换 Channel | 域名级故障 |
| `SERVICE_UNAVAILABLE`/`UPSTREAM_ERROR` | 当前 Channel（可能供应商级） | L1 换 Channel，同供应商连续失败→跨供应商 L1 | 先域内，再跨域 |
| `TIMEOUT_ERROR` | 当前 endpoint | L1 换 Channel | |
| `INVALID_REQUEST` | 请求本身 | **不转移**，直接抛 | 请求级错误换哪都无效，避免雪崩 |
| `UNKNOWN_ERROR` | 保守按 Channel | L1 换 Channel（限量） | |

硬规则：**`INVALID_REQUEST` 绝不转移**，所有场景一致（含应用覆盖）。

## 五、数据模型

### 5.1 容灾画像模板表

```sql
CREATE TABLE resilience_profiles (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    code            VARCHAR(64)  NOT NULL UNIQUE,   -- 'claude-code' / 'helpdesk' / 'default'
    name            VARCHAR(128) NOT NULL,
    -- 层级开关
    enable_l1_channel_failover  BOOLEAN NOT NULL DEFAULT TRUE,
    enable_l2_model_degradation BOOLEAN NOT NULL DEFAULT TRUE,
    degradation_max_depth       INT     NOT NULL DEFAULT 2,
    -- 转移行为
    transfer_mode   VARCHAR(16)  NOT NULL DEFAULT 'FAST',  -- FAST 立即转移 / QUEUED 排队延迟
    session_affinity BOOLEAN     NOT NULL DEFAULT FALSE,
    -- 模型约束
    pinned_model_codes JSON,        -- 锁定模型，候选仅含这些模型渠道
    quality_floor       VARCHAR(32), -- 降级下限能力档
    -- 时间/成本
    timeout_seconds     INT,
    cost_strategy       VARCHAR(32), -- COST_OPTIMIZED / LATENCY_OPTIMIZED / null
    cluster_affinity    VARCHAR(32), -- NEAREST 就近 / PINNED 指定域 / null
    -- 错误分流覆盖（覆盖默认错误分流表）
    error_routing_override JSON,
    created_by BIGINT, created_at TIMESTAMP, updated_by BIGINT, updated_at TIMESTAMP
);
```

对应领域实体（遵循 `@DomainEntity` + Getter/Setter 纯模型约束）：

```java
@Data @EqualsAndHashCode(callSuper = true) @DomainEntity
public class ResilienceProfile extends BaseEntity {
    private String code;
    private String name;
    private boolean enableL1ChannelFailover = true;
    private boolean enableL2ModelDegradation = true;
    private int degradationMaxDepth = 2;
    private TransferMode transferMode = TransferMode.FAST;
    private boolean sessionAffinity = false;
    private List<String> pinnedModelCodes;
    private String qualityFloor;
    private Integer timeoutSeconds;
    private CostStrategy costStrategy;
    private ClusterAffinity clusterAffinity;
    private Map<ProviderErrorType, FailoverLayer> errorRoutingOverride;

    public enum TransferMode { FAST, QUEUED }
    public enum CostStrategy { COST_OPTIMIZED, LATENCY_OPTIMIZED }
    public enum ClusterAffinity { NEAREST, PINNED }
    public enum FailoverLayer { L1_CHANNEL, L2_MODEL, NONE }
}
```

### 5.2 应用身份载体决策（关键）

经探讨定论：**容灾画像的应用身份落在 API Key 上，Team 仅作可选默认，MVP 不引入 Application 实体。**

理由：Team（组织轴：谁）与 Application（消费轴：什么）是正交维度。合并崩塌的杀手场景——「研发中心」一个团队同时跑 Claude Code（禁降级、锁 Claude）与 IPD 文档生成（可降级、成本优化、超时 120s）这两个镜像相反画像——证明容灾诉求按「调用场景」切，而 Team 按「人」切，颗粒度对不齐。且一个 API Key 本身就是一个应用的凭证，容灾画像绑 Key 即等于绑应用，无需独立 Application 实体。

```
Application  ≈  API Key + ResilienceProfile
```

- `user_api_keys.resilience_profile_id` —— **应用身份载体**（主）。每个 Key=一个应用，挂各自画像。
- `teams.resilience_profile_id` —— **可选默认**（回退兜底，非身份归属）。同团队多数 Key 行为相近时设默认，Key 不显式配则继承；Key 显式配置即覆盖，正好绕开「一团队多场景」冲突。
- 全局 `default` profile（`code='default'`）—— 兜底。

三级解析链 `Key → Team → Global` 是**覆盖关系**而非合并关系。Team 不是 Application 的身份，而是「应用未显式表态时的猜测默认」。

> Application 实体的引入时机：**不是为容灾，而是为聚合**。当出现应用级配额/预算池、应用级用量成本看板、应用级密钥轮换吊销等诉求时（属 `quota`/`audit` 域），再引入 `applications` 表让 Key 挂 `application_id`、Application 挂画像——届时它是聚合根，而非容灾配置载体。MVP 容灾阶段不建。

### 5.3 Cluster 软分域

```sql
ALTER TABLE channels ADD COLUMN cluster_code VARCHAR(64);  -- 软分域，可空，如 'openai-us'、'claude-bedrock'
```

阶段一不建 `clusters` 表，靠 `cluster_code` 软字段做故障域分组。阶段三（P3）若有多区域/多供应商容灾运维诉求，再升级为显式 `clusters` 实体（`code/name/provider_id/region/priority/health_status`）+ 域级健康聚合。

### 5.4 路由器与熔断修正

- 路由器顺序修正为 `Permission(@100) → Health(@200) → Priority(@300) → Cluster/Pinned(@400) → LoadBalance(@9999)`：先过滤熔断渠道，再在存活渠道里按 priority 分组。
- 熔断 key 统一为 `endpointId`，`HealthRouter` 改用 endpoint 级熔断。
- `InstanceSelector.select` 改为返回**按 (cluster_code, priority) 排序的候选列表**，供 L1 转移回路逐个尝试。

## 六、应用级容灾画像与五场景映射

| 场景 | L1 | L2 | 会话亲和 | 锁模型 | 超时 | 成本策略 | 转移模式 |
|------|----|----|---------|--------|------|---------|---------|
| 1) 多 agent 大脑 | ✅ | ❌ | ✅ | 否 | 中 | 中 | FAST |
| 2) 客服/HelpDesk | ✅ | ✅(深3) | ❌ | 否 | 15s | LATENCY | FAST |
| 3) Claude Code/CodeX | ✅ | ❌ | ❌ | Claude系列 | 60s | 否 | FAST |
| 4) IPD 文档生成 | ✅ | ✅(浅1) | ❌ | 否 | 120s | COST | QUEUED |
| 5) 运营流程自动化 | ✅(步骤级) | 步骤关键度可配 | ❌ | 视步骤 | 中 | 中 | FAST |

### 对照场景一：Claude Code/CodeX（验证 L1，禁降级）

```yaml
- code: claude-code
  name: "Claude Code/CodeX 研发"
  enable_l1_channel_failover: true       # 多供应商 Claude 渠道高可用
  enable_l2_model_degradation: false     # 禁降级——换模型=代码质量崩
  degradation_max_depth: 0
  transfer_mode: FAST
  session_affinity: false
  pinned_model_codes: ["anthropic/claude-sonnet-4", "anthropic/claude-opus-4"]
  timeout_seconds: 60
  cost_strategy: null                    # 研发要质量不计成本
  cluster_affinity: PINNED
  error_routing_override:
    AUTHENTICATION_ERROR: L1_CHANNEL
    QUOTA_EXCEEDED: L1_CHANNEL
    RATE_LIMIT_ERROR: L1_CHANNEL
    NETWORK_ERROR: L1_CHANNEL
    SERVICE_UNAVAILABLE: L1_CHANNEL
    UPSTREAM_ERROR: L1_CHANNEL
    INVALID_REQUEST: NONE                # 请求级错误直接抛给 Code 层
    TIMEOUT_ERROR: L1_CHANNEL
```

供给侧配套：为 pinned Claude 模型配置多供应商/多故障域 Channel（Anthropic 官方 / AWS Bedrock / 中转商），挂不同 `cluster_code`。L1 转移按域内→跨域逐个尝试，全 Claude 渠道耗尽直接抛错（L2 关闭），让 Code 层提示用户而非静默降级到 GPT。**这正是 L1 作为「不可降级场景唯一容灾手段」的价值兑现。**

### 对照场景二：客服/HelpDesk（验证 L2，全开）

```yaml
- code: helpdesk
  name: "客服/HelpDesk 问答"
  enable_l1_channel_failover: true
  enable_l2_model_degradation: true      # 积极降级，可用性优先
  degradation_max_depth: 3
  transfer_mode: FAST
  session_affinity: false
  pinned_model_codes: null
  quality_floor: "STANDARD"              # 降级下限，不到 mini 兜底
  timeout_seconds: 15
  cost_strategy: LATENCY_OPTIMIZED
  cluster_affinity: NEAREST
  error_routing_override:
    AUTHENTICATION_ERROR: L1_CHANNEL
    QUOTA_EXCEEDED: L1_CHANNEL
    RATE_LIMIT_ERROR: L1_CHANNEL
    NETWORK_ERROR: L1_CHANNEL
    SERVICE_UNAVAILABLE: L1_CHANNEL
    UPSTREAM_ERROR: L1_CHANNEL
    INVALID_REQUEST: NONE
    TIMEOUT_ERROR: L1_CHANNEL
```

L1 全渠道耗尽后自动进 L2 降级链（gpt-4o → gpt-4o-mini → 兜底弱模型）。两场景 `INVALID_REQUEST` 都 NONE（机制层硬规则），但 L2 开关相反——CodeX 宁可报错不可降级，客服宁可降级不可不可用。

## 七、运行时侵入点（最小改动）

1. **认证后**（`ApiKeyAuthInterceptor` 已解析 apiKeyId）：调 `ResilienceResolver.resolve(apiKeyId)`，按三级解析链得出生效画像，塞入请求上下文。
2. **`RoutingRequest`** 增加 `resilienceProfile`，贯穿 RouterChain：
   - 新增 `PinnedModelRouter`：`pinnedModelCodes` 非空时强制只留这些模型实例（场景3 关键）
   - 新增 `ClusterAffinityRouter`（P2）：按 `clusterAffinity` + `cluster_code` 排序
   - `LoadBalanceRouter` 据 `costStrategy` / `sessionAffinity` 选实例
3. **`ChannelFailoverInvoker`（新建，替代 DegradationInvoker 回路）**：按 `errorRoutingOverride[errorType]` 决定 L1/L2/NONE，按 `enableL2`/`maxDepth` 门禁降级。

```
ChannelFailoverInvoker.invoke(候选列表, request, profile):
  for instance in 候选列表:               // 已按 cluster+priority 排序
    ctx = resolve(同模型, instance.channelId)
    try: return keyFailoverInvoker.invoke(ctx, request)   // L0 在内部跑
    catch ProviderException e:
      layer = profile.errorRoutingOverride[e.errorType]   // 默认表兜底
      if layer == NONE: throw e
      标记 instance.endpoint 熔断
      if 同 cluster 还有候选: continue                      // 域内续命
      else: 跳到下一 cluster                                // 跨域
  // L1 全耗尽
  if profile.enableL2ModelDegradation:
    return degradationService.degrade(model, reason, profile.maxDepth)  // L2 兜底
  throw lastException
```

流式边界：**只在首字节前转移**，首字节后失败不换 Channel（继承现有 `KeyFailoverInvoker.invokeStream` 约束）。

恢复机制：L1 复用 `CircuitBreaker` half-open；L2 保留 `DegradationService.recoveryCheck` 定时探测回切；P3 Cluster 级恢复（域内任一 Channel half-open 成功→Cluster 解除 DOWN）。

## 八、阶段化路线图

| 阶段 | 范围 | 价值 | 改动 |
|------|------|------|------|
| P0 修根因 | 路由器顺序修正 + 熔断 key 统一 | 次优先级渠道能被选，熔断生效 | 小，bugfix 级 |
| P1 L1 转移回路 | `ChannelFailoverInvoker` + 候选列表路由 + 错误分流表 | 补齐 Channel 级透明容灾（核心） | 中 |
| P2 软分域 + 画像 | `cluster_code` + `ResilienceProfile` + 三级解析链 + 两对照场景 | 共因隔离 + 应用级差异化容灾 | 中 |
| P3 显式 Cluster | `clusters` 表 + 域级健康聚合 + 控制台管理 | 多区域/多供应商运维可视 | 大 |
| P4 降级链语义修正 | `degrade(reason)` 分流 + 定位 L2 兜底 | 修正设计债 | 中（可与 P1 合并） |

建议起步：P0 + P1（修根因 + L1 转移回路）立即补最痛缺口；P2 引入画像与软分域，落地两个对照场景验证 L1/L2 两条路径。
