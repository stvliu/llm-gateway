# 容灾方案设计（Cluster 与 Channel 级失败转移）

> 状态：已落地，本文档为容灾架构的最终设计文档，与实现对齐。
> 关联：supply 域「Channel 级运行时失败转移」+ Cluster 故障域分组 + 应用级超时与渠道优先级。
> 实现参考：delta spec `openspec/changes/simplify-resilience-architecture/specs/`（本 change 对容灾架构做了简化：四层→三层、删 L2 降级/DomainHealth/PinnedModel/会话亲和/ResilienceProfile 实体、Cluster 语义改造、L1 共因跳过、应用级 ApplicationChannel.priority 与 timeout 下沉）。
> 历史脉络：初版由 `resilience-architecture` change 落地四层容灾栈；`simplify-resilience-architecture` change 删 L2 与域级聚合等复杂度，容灾止于通道（L0/L1），降级决策还给应用。

## 一、背景与现状诊断

现有供给域层次：

```
Provider ─┬─ Channel ─┬─ ChannelEndpoint（URL + protocol）
          │           └─ ChannelCredential（多个 API Key）
          │   │
          │   └─ ModelInstance（Channel × Model，带 weight/state；priority 字段保留但已不决定转移顺序，见 follow-up）
          │
          └─ Model（规格，如 gpt-4o）
```

调用方层次：`UserApiKey → Application → ApplicationChannel → Channel`，权限锚点为「应用」。Application 是权限+行为双聚合根（Key 归属 + 渠道可见性 + 应用级超时）。

### 容灾栈层级（三层）

| 层级 | 组件 | 转移粒度 | 触发 |
|------|------|---------|------|
| L0 Key 级 | `KeyFailoverInvoker` | 同 Channel 换 Credential | 单 Key 调用抛 `ProviderException` |
| L1 Channel 级 | `ChannelFailoverInvoker` | 同模型换 Channel（可跨供应商/跨故障域 + clusterId 共因跳过） | 候选调用失败按错误分流决策 |
| 路由级 | `RouterChain` | 初始选实例时按权限/健康/优先级过滤 | 仅首次选路，产出候选列表 |
| L3 兜底 | — | 抛错给客户端 | L1 全耗尽 |

> 本 change 删除了 L2 模型级降级层。降级是「有损的最后手段」，覆盖的模型能力问题大多能被请求阶段能力匹配前置消解；降级链人工预配置、有损、静默，与「下游是应用而非人」「Token 成本透明」原则冲突。**容灾止于通道（L0/L1），降级决策还给应用**——应用如需换模型能力，由应用自身决定，不依赖网关运行时降级。

### 已修正的根因性错配

1. **路由器顺序倒置（已修正）**：原 `RouterChain` 为 `Permission → Priority → Health → LoadBalance`，Priority 先于 Health 且 `PriorityRouter` 是 `isForce=true` 只保留 priority 最小组。后果：最小 priority 组被熔断过滤光后直接 force 返回空，次优先级健康渠道永无机会。已修正为 `Permission(@100) → EndpointHealth(@200) → Priority(@300) → LoadBalance(@9999)`，且 `PriorityRouter` 改为排序器（输出完整候选列表不收敛）。

2. **熔断 key 不一致（已修正）**：`HealthRouter` 原用 `channelId`，`KeyFailoverInvoker` 用 `endpointId`。已统一为 `endpointId`：`HealthRouter` 按入站协议经 `EndpointResolver` 从 `channelId` 派生 `endpointId` 后查 `ChannelEndpointCircuitBreakerManager`，与 `KeyFailoverInvoker`（用 `RoutingContext.channelEndpointId()`）共享同一 manager bean（运行时派生方案，不加 DB 字段）。

3. **错误分流不分 reason（已修正）**：引入 `ErrorClassifier` 错误分流表按 `ProviderErrorType` 映射 `FailoverDecision`（L1/NONE），指导转移决策。

### 本 change 删除的复杂度

- **L2 模型降级层**：`DegradationService`/`DegradationServiceImpl`/`DegradationProperties`/`DegradationEvent`/`DegradationRecoveredEvent`/`L2DegradationRequiredException` 整删，`@Scheduled recoveryCheck` 删除。`FailoverDecision` 枚举收敛为 L1/NONE（删 L2）。
- **DomainHealth 域级聚合路由**：`ClusterHealthAggregator`/`ClusterHealthStatus` 枚举/`ClusterAffinityRouter` 整删。整域故障靠端点级熔断自然收敛 + L1 转移阶段 clusterId 共因跳过处理。
- **PinnedModel + 会话亲和**：`PinnedModelRouter`、`SessionAffinityStore`/`SessionAffinityConfig`、`enablePinnedModel`/`pinnedModelId`/`enableSessionAffinity`/`sessionAffinityTtlMinutes` 整删。LLM 调用多为无状态，会话亲和收益依赖上游 prompt caching 且不确定；模型锁定由应用侧选择模型实现，不需网关运行时锁定。
- **ResilienceProfile 实体**：删 L2/PinnedModel/会话亲和后只剩 `timeout` 一个字段，不配独立实体。`ResilienceProfile`/`ResilienceProfileGateway`/Impl/`ResilienceProfileController`/`ResilienceProfileApplier`/`ResilienceResolver`/`resilience_profiles` 表/`resilience_profile_id` 列/`PUT /applications/{id}/resilience` 端点整删。`timeout` 直接挂 `Application` 字段。

## 二、容灾目标：三层容灾栈

```
L0 Key 级      同 Channel 换 Credential              ← 已有，处理单 Key 失效
L1 Channel 级  同模型换 Channel（可跨供应商/跨故障域）  ← 本方案核心，对用户透明
L3 兜底        抛错给客户端
```

核心原则：**优先在同模型内换故障域（透明），耗尽后抛错给应用（应用自行决定是否换模型）**。L1 是 Channel 级失败转移的核心，也是 Cluster 概念的落脚点。

> 关于「同一供应商下模型级失败转移是否有必要」：作为容灾手段**无必要**——AUTH/QUOTA/账号限流/网络/宕机都是共因故障，换同供应商模型无效。模型级降级的真正价值是「能力降级兜底」，应由应用按自身场景决定（客服场景救命，CodeX 场景有害），而非网关全局兜底。故 L2 删除，降级决策还给应用。

## 三、Cluster 定位：跨供应商故障独立性分组

Cluster = Channel 的故障域分组，同组 Channel 共享共因特征。**本 change 将 Cluster 语义从「供应商内分组（region/priority/healthStatus 膨胀）」改造为「跨供应商的故障独立性分组」**：分组可跨供应商（如 OpenAI 官方 + Azure-OpenAI 同域，因 Azure-OpenAI 底层依赖 OpenAI 模型共因），也可供应商内细分（同供应商多账号异域）。

```
Cluster(故障域 openai-primary)
 ├─ Channel A (provider=openai)        ← 共因
 └─ Channel B (provider=azure-openai)  ← 与 A 共因（底层依赖 OpenAI 模型），即使 provider 不同也归同域
Cluster(故障域 openai-backup)
 └─ Channel C (provider=openai, 别的账号)  ← 不同故障域（账号独立），容灾目标
```

转移规则：**L1 共因失败时跳过同 clusterId 候选，直接尝试异 clusterId 候选**（见第七节共因跳过）。Cluster 为显式实体（`clusters` 表，见第五节），`Channel.clusterId` 关联故障域。

### Cluster 与 providerId 正交

- `providerId` — 供应商标识（客观，管理面/计费/统计用），**不作共因依据**。
- `clusterId` — 故障域归属（运维判断，L1 共因跳过依据）。
- 两者正交：一个供应商的渠道可分属多域，一个域可含多供应商渠道。共因判断看 `clusterId` 不看 `providerId`。

## 四、错误分流表：L1/NONE 路由决策

`ErrorClassifier.classify(errorType)` 按 `ProviderErrorType` 映射到 `FailoverDecision`（L1/NONE），指导转移决策：

| 错误类型 | 转移决策 | 理由 |
|---------|---------|------|
| `INVALID_REQUEST` | **NONE**（不转移，直接抛） | 请求级错误换哪都无效，避免雪崩 |
| `AUTHENTICATION_ERROR` | L1（换渠道） | 共因故障：同账号换 Key/模型无效，换账号有效 |
| `RATE_LIMIT_ERROR` | L1（换渠道） | 共因故障：账号级/渠道级限流，换渠道保透明 |
| `QUOTA_EXCEEDED` | L1（换渠道） | 共因故障：配额账号级共用 |
| `TIMEOUT_ERROR` | L1（换渠道） | 共因故障：端点级超时 |
| `UPSTREAM_ERROR` | L1（换渠道） | 共因故障：上游服务异常 |
| `SERVICE_UNAVAILABLE` | L1（换渠道） | 共因故障：上游不可用 |
| `NETWORK_ERROR` | L1（换渠道） | 共因故障：域名/网络级故障 |
| `UNKNOWN_ERROR` | **NONE**（不转移直接抛） | 未分类错误不转移，降级决策还给应用 |
| `null` 输入 | NONE（直接抛） | 编程错误或未分类，不转移 |
| 未在表中显式映射的新增枚举 | **NONE**（兜底不转移直接抛） | 防御性兜底，不转移 |

硬规则：**`INVALID_REQUEST` 绝不转移**（NONE），所有场景一致。共因故障（AUTH/RATE_LIMIT/QUOTA/TIMEOUT/UPSTREAM/SERVICE_UNAVAILABLE/NETWORK）统一走 L1 换渠道——这些故障换同供应商模型无效，换渠道（可跨供应商/跨故障域）有效。`UNKNOWN_ERROR` 改为 NONE（本 change 删 L2 后，未分类错误不再走模型降级，直接抛给应用，由应用决定是否换模型）。

> `FailoverDecision` 枚举收敛为 L1/NONE（删除 L2）。分流决策由机制层 `ErrorClassifier` 统一保证正确性，不提供应用级覆盖，简化配置心智成本。

## 五、数据模型

### 5.1 应用身份载体：Application 聚合根（已实现）

Application 是权限+行为双聚合根（Key 归属 + 渠道可见性 + 应用级超时）。**本 change 删除 `resilienceProfileId` 关联，新增 `timeout` 字段**（承接原 ResilienceProfile.timeout 语义）。

```
Application（聚合根）
  - code / name / description / state / timeout / quotaBudgetId / dashboardId + 审计
```

- `applications.timeout` —— **应用级超时秒数**。0 表示用渠道默认；非 0 时由 `RoutingResolver` 注入运行时，覆盖 `channel.getTimeout()`（见第七节）。
- 容灾画像实体退场：原 `Application.resilienceProfileId` → `ResilienceProfile` 关联整删，timeout 直接挂 Application。

**API**: `POST/PUT/GET/DELETE /api/v1/applications`（timeout 在创建/更新请求体直接配置，无独立容灾画像绑定端点）。

### 5.2 ApplicationChannel：应用级渠道授权与转移顺序（已实现）

`ApplicationChannel` 关联实体决定应用可见的渠道集合，并承载**应用级转移顺序（priority）**。

```
ApplicationChannel
  - applicationId / channelId / priority + 审计
  - 唯一约束 (application_id, channel_id)
```

- `priority` — 应用级转移顺序，数值越小越先试。同一渠道对不同应用可有不同 priority（渠道A 对客服应用 priority=1，对内部工具 priority=3）。**完全取代原全局 `ModelInstance.priority`**（ModelInstance.priority 退场，见 follow-up）。无主备之分，只有先后次序——所有候选资格平等，区别仅在尝试顺序。为 null 时回退默认值 100。
- 转移顺序由管理员通过前端配置，跨供应商是 priority 排序的自然结果。

**API**（gap2 新增管理端保存）:
- `GET /api/v1/applications/{id}/channels` — 查询应用授权的渠道列表（每项含 `channelId` 与 `priority`）
- `PUT /api/v1/applications/{id}/channels` — 更新应用渠道授权（先清空旧关联，再批量保存新关联含 priority；HTTP 204）
  - Request Body: `{ "channels": [{ "channelId": 1, "priority": 1 }, { "channelId": 2, "priority": 2 }] }`

### 5.3 Cluster 显式实体（已实现，语义改造 + 瘦身）

`Cluster` 实体名保留，语义从「供应商内分组」改造为「跨供应商故障独立性分组」，字段瘦身。

```sql
CREATE TABLE clusters (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    code            VARCHAR(64)  NOT NULL UNIQUE,   -- 'openai-primary' / 'azure-openai-shared' / 'overseas-line'
    name            VARCHAR(128) NOT NULL,
    description     VARCHAR(255),                    -- 共因特征说明（如 "Azure-OpenAI 底层依赖 OpenAI 模型，共因"）
    provider_id     BIGINT       NOT NULL,           -- 供应商标识（客观，不作共因依据；与 clusterId 正交）
    created_by BIGINT, created_at TIMESTAMP, updated_by BIGINT, updated_at TIMESTAMP
    -- 删除 region（就近路由未实现）/ priority（转移顺序归 ApplicationChannel.priority）/ health_status（域级聚合已删）
);

ALTER TABLE channels ADD COLUMN cluster_id BIGINT;   -- FK 指向 clusters.id（字段名保留不变）
```

对应领域实体：`Cluster`（`code/name/description/providerId` + 审计）。`ClusterHealthStatus` 枚举随 `healthStatus` 字段移除而退场。

Cluster 管理 API：`POST/PUT/GET /api/v1/resilience/clusters`（不提供 delete，Cluster 关联 Channel 的 clusterId，删除需级联清理）。

### 5.4 路由器链（已实现，删 ClusterAffinity/PinnedModel，Priority 改排序器）

路由器顺序为 `Permission(@100) → EndpointHealth(@200) → Priority(@300) → LoadBalance(@9999)`：先按权限过滤、再剔除熔断端点、再在存活候选里按 priority 排序输出完整列表、最后透传候选列表。

- `PermissionRouter`（@100，isForce=true）：按 `ApplicationChannel` 授权过滤应用可见渠道，再过滤活跃 Channel（`state.isRoutable()`）。`applicationId` 为 null 时返回空集。
- `HealthRouter`（@200，isForce=true）：按端点粒度过滤熔断中实例。熔断 key 统一为 `endpointId`（运行时派生：按入站协议经 `EndpointResolver` 从 `channelId` 派生 `endpointId`，与 `KeyFailoverInvoker` 共享同一 `ChannelEndpointCircuitBreakerManager`）。
- `PriorityRouter`（@300，isForce=true）：**排序器**（非选择器）——按应用级 `ApplicationChannel.priority` 升序输出完整候选列表，SHALL NOT 收敛到最优组（修复原选择器 isForce=true 导致备候选被丢、L1 换不到备的缺陷）。排序键为 `RoutingRequest.channelPriorityMap.get(channelId)`，null 回退默认值 100。
- `LoadBalanceRouter`（@9999，isForce=false）：降级为透传（候选列表产出后不再收敛到单实例），供 L1 故障转移逐个尝试。

> 删除的路由器：`ClusterAffinityRouter`（@250，域级预判与端点级 HealthRouter 等价，删除域级聚合后无意义）、`PinnedModelRouter`（@350，模型锁定由应用侧选模型实现）。

`InstanceSelector.select` 返回**按 ApplicationChannel.priority 升序排序的候选列表**（而非单实例），供 `ChannelFailoverInvoker` 逐个尝试。

## 六、应用级超时与渠道优先级（已实现）

本 change 删除容灾画像实体与档位推导（ResilienceProfileApplier 退场），改为两个应用级直接配置项：

1. **应用级超时 `Application.timeout`**：0 表示用渠道默认；非 0 时由 `RoutingResolver` 注入运行时，覆盖 `channel.getTimeout()`。timeout 通过应用 CRUD 端点直接配置，无独立画像绑定端点。
2. **应用级渠道优先级 `ApplicationChannel.priority`**：管理员通过 `PUT /api/v1/applications/{id}/channels` 配置各渠道 priority，定义 L1 转移先后次序。`InstanceSelector` 查 `ApplicationChannelGateway.findByApplicationId` 构建 `channelPriorityMap` 填入 `RoutingRequest`，供 `PriorityRouter` 排序。

> 原容灾画像档位（STANDARD/STRICT/AGGRESSIVE/BATCH）、L2 门禁（`enableL2ModelDegradation`/`degradationMaxDepth`）、会话亲和、模型锁定等专家字段全部退场。管理员不再面对「选容灾模式档位」，改为直接配应用 timeout 与渠道 priority。容灾栈对管理员藏起来（L0/L1 是内部机制），见 `docs/容灾管理范式.md`。

## 七、运行时侵入点（已实现）

1. **认证后**（`ApiKeyAuthInterceptor` 解析 apiKeyId → applicationId）：`InstanceSelector.select` 构建应用级 `channelPriorityMap` 填入 `RoutingRequest`，贯穿 RouterChain。
2. **`RoutingRequest`** 携带 `applicationId` + `protocol` + `channelPriorityMap`（无 `resilienceProfile` 字段，画像退场）：
   - `HealthRouter`（@200）：按 endpointId 过滤熔断端点
   - `PriorityRouter`（@300）：按应用级 priority 升序排序输出完整列表
   - `LoadBalanceRouter`（@9999）：降级为透传，产出候选列表
3. **`RoutingResolver`**：从 `Application.getTimeout()` 读取应用级超时，非 0 时覆盖 `channel.getTimeout()` 作为本次请求超时。
4. **`ChannelFailoverInvoker`**：候选内逐个试，按 `ErrorClassifier.classify(errorType)` 决定 L1/NONE，L1 共因失败时跳过同 clusterId 候选（共因跳过），全耗尽抛最后异常（不再进 L2）。

```
ChannelFailoverInvoker.invoke(候选列表, request, applicationId, traceId):
  lastException = null
  共因跳过集合 skippedClusterIds = {}   // 本次请求内有效，不持久化
  for i, instance in 候选列表:                // 已按 ApplicationChannel.priority 升序排序
    if instance.clusterId in skippedClusterIds: continue   // 共因跳过同域候选
    ctx = resolve(同模型, instance.channelId)
    try: return keyFailoverInvoker.invoke(ctx, request)    // L0 在内部跑
    catch ProviderException e:
      lastException = e
      decision = errorClassifier.classify(e.errorType)     // L1 / NONE
      if decision == NONE: throw e                         // 请求级错误直接抛
      if decision == L1:
        skippedClusterIds.add(instance.clusterId)          // 标记共因跳过（仅本次请求）
        publishFailoverEvent(候选[i], 候选, applicationId, e.errorType, decision, commonCauseSkip=true)
        continue                                            // 跳过同域，尝试异域候选
  throw lastException   // L1 候选全耗尽，抛最后异常（不再进 L2 模型降级）
```

> 与原四层伪代码的差异：删除 L2 降级回路（`tryL2Degradation`/`L2DegradationRequiredException`），L1 全耗尽直接抛最后异常。新增 clusterId 共因跳过：L1 决策成立时标记当前候选 clusterId，跳过候选列表中同 clusterId 的后续候选，直接尝试异 clusterId 候选。共因跳过标记仅本次请求内有效，不持久化（防误杀扩散）；整域已熔断由端点级熔断器客观剔除，共因跳过处理「单点共因但故障域未全熔断」中间态。

流式边界：**只在首字节前转移**，首字节后失败不换渠道（继承现有 `KeyFailoverInvoker.invokeStream` 约束）。

恢复机制：L1 复用 `CircuitBreaker` half-open（`OPEN` 超时后自动转 `HALF_OPEN` 试探放行，成功转 `CLOSED`，失败转 `OPEN`）。Cluster 域级恢复靠端点级熔断器自然收敛——域内端点 HALF_OPEN 成功转 CLOSED 后，该域渠道自然重新进入候选（不再有域级健康聚合器）。

## 八、转移事件流（已实现）

容灾可观测性读侧：独立 `FailoverEvent` domain 记录每次候选转移，供控制台总览页轮询渲染。

### 事件发布与持久化

`ChannelFailoverInvoker` 在 L1 决策换下一候选前，经既有 `DomainEventPublisher` 发布 `FailoverOccurredEvent`（DomainEvent），由 `FailoverEventListener` 持久化为 `FailoverEvent` 实体。

- **监听机制**：`FailoverEventListener` 用 **`@EventListener`**（非 `@TransactionalEventListener`）。原因：调用链 `ChatDispatchServiceImpl.dispatch` 无 `@Transactional`，整个请求处理不开启事务，`@TransactionalEventListener(AFTER_COMMIT)` 在无事务上下文时静默丢弃事件。改为 `@EventListener` 后无事务上下文下事件仍被处理。
- **同步处理**：项目未配置 `@EnableAsync`，`@EventListener` 在同一线程内同步调用监听器完成持久化（发布即持久化），调用链在持久化完成后才继续。可观测性持久化开销在毫秒级，对 10k QPS 调用链影响可接受。
- **可靠性边界**：发布后持久化前进程崩溃则事件丢失（可观测性数据可接受，非计费/审计关键路径）。监听器捕获持久化异常仅记日志，不阻断业务。
- **clusterId 填充**：`clusterId` 从 `RoutingContext` 直取（`RoutingContext` 已携带 clusterId，由 `RoutingResolver` 填充），填充冗余 `fromClusterId`/`toClusterId` 字段使 clusterId 过滤生效。**本 change 删除了原经 `ChannelGateway.findById` 反查 `Channel.clusterId` 的方案**（gap1：clusterId 从 RoutingContext 直取，删 ChannelGateway 反查，避免转移路径额外查询）。

### 事件字段

`FailoverEvent`：`traceId`（串联同请求多次转移）、`applicationId`、`fromChannelId`/`fromEndpointId`、`toChannelId`/`toEndpointId`（exhausted 时为 null）、`fromClusterId`/`toClusterId`（冗余，从 RoutingContext 直取填充）、`errorType`（`ProviderErrorType` 枚举名）、`decision`（`L1`/`NONE`，L2 已删）、`exhausted`（候选是否全部耗尽）、`commonCauseSkip`（是否共因跳过标记，区分「真实失败转移」与「共因跳过转移」）、`occurredAt`。

### 查询端点（`ResilienceEventController`）

- `GET /api/v1/resilience/events` — 转移事件流查询（分页 + `since`/`applicationId`/`clusterId` 过滤，按 `occurredAt` 倒序）。`limit` 默认 100，上限 500。`clusterId` 过滤基于冗余 `fromClusterId`/`toClusterId` 字段匹配（任一命中即返回）。
- `GET /api/v1/resilience/events/exhausted` — 耗尽告警查询（`exhausted=true` 近期事件，按 `occurredAt` 倒序）。`since` 不传时由 Service 层补默认窗口最近 1 小时，`limit` 默认 50。
